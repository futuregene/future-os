# 发送后输入框残留已发送的那一行（2026-09-24）

## 范围与复现

桌面端（macOS 26.6.2，Apple M3 Ultra，Tauri/WKWebView）反馈：发出消息后，输入框
仍保留刚发出消息的最后一行，其上还画着空态提示。报告者附了输入框截图。

该提示词是两行（中间用 Shift+Enter 换行），文中含一个 `/skill` 提及；`agent.db`
显示 agent 在 16:38:23.489 收到它（`run-20260924-163823-b18a33`），截图在约 7 秒
后拍下，因此输入框有数秒时间可以收敛。

浏览器内核下无法复现：在无头截图 harness（真实 Chrome、真实按键事件）里重放同一
序列，输入框重绘正常；清空路径本身由 `Composer.delivery.test.tsx` 覆盖。缺陷在
帧呈现，而不在应用状态。

## 截图显示的

按报告者的 PNG 实测（1804×762，2× 窗口）：

- 输入框卡片占 y 533–742；其中编辑区盒子为 y 550–670。
- 该盒子内恰好画了两行文字：提示在 y 562–593（墨色 `#8a94a6` = `ink-muted`，
  另有 88 px 的 `#172033` 是首字符前的光标），残留行在 y 605–632（墨色
  `#172033`，另有 615 px 的主色蓝 `#2563eb`，即药丸）。
- 残留行的字形范围（x 177–1275）与上方已发送气泡里同一行的宽度完全一致
  （x 545–1643，1098 px）：同一段文字、同一字体、仍在其在编辑区内的旧位置。
- 那一刻编辑区的 DOM 是空的。提示只在编辑区为空时渲染，而这正是应用对该状态的
  自身标记（`{empty ? …}`，`empty` 由 MutationObserver 同步），并且光标位于第一
  行行首——清空后光标落点——而不是残留文字末尾。
- 原先的第一行已被抹掉，且其整体范围都落在提示挂载后的盒子内（提示文字在 1× 下宽
  336.2 px，原第一行约 276 px）：提示的挂载重绘了那块矩形，而清空自己的重绘从未
  到达编辑区——残留的第二行位于该矩形之下，因而存活下来。

## 诊断

macOS 26 上的 WKWebView 会呈现"部分更新"的帧：新帧的若干区域与旧帧的若干区域
共存，而 DOM 与命中测试都是最新的（tauri-apps/wry#1848）。因此 DOM 正确而像素不
正确是可能的。同类问题在桌面端源码里已有记录：消息悬停控件（`MessageBlock.tsx`
中的 `will-change` 注释）。

因此修法不能依赖编辑区自身的失效被真正绘制；必须由"总会伴随重置发生"的东西把
整个盒子标脏。

## 修正

- 空态提示现在覆盖编辑区整个盒子（`inset-0` 加上编辑区自己的 `px-2 py-1`），而
  不再只是文字自身的宽度（`left-2 top-1`）。它的挂载——清空使编辑区变空时必然
  发生——会把盒子的每个像素标脏，随后的重绘就会抹掉清空遗留下来的像素；草稿恢复
  使它卸载时同理。
- 由于提示现在覆盖在编辑区之上，它必须保持 `pointer-events-none`，并保留编辑区
  的内边距，使文字位置不变。

## 验证（无头 harness，非原生 WKWebView）

- 提示的盒子等于编辑区的盒子（409,743，750×56），其文字行位置不变
  （417,748，336.2×17）。
- 整个输入框卡片的 2× 截图与改动前逐像素一致：2,291,520 个像素中 0 个不同。
- 命中测试仍能穿过提示到达编辑区（`elementFromPoint` 返回 `role=textbox`；
  在盒子下半部点击可获得焦点）。

## 未验证

- 未在原生 WKWebView 上复现：该机制依赖"呈现缺陷是区域局部的"以及"提示挂载会标脏
  编辑区盒子"——后者由报告者的截图在较小矩形上得到印证，而非整个盒子。
- 提示只在编辑区跨越空态时抖动（清空进、草稿恢复出）。对于"以文字替换文字"的重置，
  仍只有编辑区自身的失效在请求重绘；那条路径的下一手是给编辑区一个合成层，但必须
  同时标脏编辑区自己的层（被提升为合成层后，它不再绘制进提示所在的层——见
  `MentionEditor.tsx` 中的注释）。
