# 粘贴与换行后的 Composer 光标可见性

> 本文是历史快照 [Composer caret visibility after paste and newline](./composer-caret-scroll-20260913.md)（2026-09-13，commit `717ed66c`）的忠实逐段中文翻译，保留原文结论、时间与 commit 边界；译文不是新的复核结论。

## 已确认的缺陷与范围

基线：`ae7c959b`（相关编辑处理器与更早 `c0c4d8e4` 验证相比未变）。Windows Chrome 153、实际桌面 Composer、MentionEditor 与产品 CSS；Tauri IPC/send 回调打桩。无模型调用或生产聊天数据访问。这**不**确立 macOS WKWebView 行为，也不解决已提交输入仍可见的独立报告。

修复前，100 行原生剪贴板粘贴让编辑器视口停留在顶部，尽管选择在末尾。Shift+Enter 也不显示下一行。输入一个字符则跳到选择处。在 1280x800 与 720x800 下行为相同。`paste.isTrusted` 为 true；产品处理器阻止了原生编辑。原生 textarea 控件立即跟随选择。这是已确认的延迟光标跟随缺陷，不是原始用户报告的 macOS 反复抖动已被复现的证明。

## 修复

在手工粘贴/换行后，测量光标行并**只调整编辑器自身**的 scrollTop，调整量为其暴露所需的值。不滚动祖先容器、强制文档底部、插入测量标记或更改输入法处理。将粘贴的选择锚定在其文本节点内，使其矩形可测量。对换行，还要识别 `Range.insertNode` 可能产生的空尾随文本节点，保留用于渲染空最后一行的现有零宽填充（序列化时剥离）。

## 验证

- 回归测试在修正前失败：视口下方/上方的粘贴光标与 Shift+Enter/Ctrl+Enter 均不滚动。
- 单独的回归测试对尾随换行后跟空拆分文本节点失败；填充修正后通过。
- 原生 Windows 剪贴板 + Ctrl+V 浏览器检查在两种视口宽度下通过。原始剪贴板格式在内存中备份并恢复。
- 100 行 / 9091 字符时，编辑器高度为 320px。粘贴现在立即滚动到约 1683.33px。五次连续换行操作将其移动到 1703.33、1723.33、1743.33、1763.33 与 1783.33px。后续输入停留在 1783.33px：**无延迟跳变**。
- Shift+Enter 与 Ctrl+Enter、短输入后接换行、以及现有长文本中部的原生粘贴都保持光标可见。
- 中间插入让后续内容留在视口下方，而非强制编辑器到底部。页面 scrollTop 保持零。发送仍清除编辑器及其保存的草稿。
- jsdom 测试覆盖最小向上/向下滚动、已可见光标、实时选择/祖先保留、空几何与输入法守卫。

原生 macOS 桌面与实际系统输入法候选选择仍未测试；不声称 macOS 残余输入/抖动报告已修复。
