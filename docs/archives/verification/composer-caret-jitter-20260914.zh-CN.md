# 长粘贴后 Composer 滚动一致性（2026-09-14）

> 本文是历史快照 [Composer scroll consistency after long paste (2026-09-14)](./composer-caret-jitter-20260914.md)（2026-09-14，commit `f98a2a31`）的忠实逐段中文翻译，保留原文结论、时间与 commit 边界；译文不是新的复核结论。

## 范围与复现

基线：`c65c1f8b`，含来自 #591 的先前的光标显示修复。
在 Windows 上用 Playwright 测试底部对齐 flex 布局（带工具栏）中的实际 `MentionEditor` 与产品 CSS。引擎：WebKit 26.5（build 2336）与 Chromium 151.0.7922.34。未使用 agent、模型调用或生产聊天数据。粘贴是携带纯文本的合成 `ClipboardEvent`；后续输入与 Shift+Enter 使用浏览器键盘自动化。

这是 WebKit 引擎证据，**不是原生 macOS WKWebView 验证**。
macOS 系统剪贴板与真实中文输入法候选 UI 仍未测试。

复现序列：

1. 向空编辑器粘贴 `"long text ".repeat(1000)`。
2. 按 Shift+Enter，然后输入足够字符换行到另一行。
3. 对粘贴文本中一个和两个尾随换行各重复一次。
4. 测量输入后的编辑器 `scrollTop`、高度/顶部与折叠选择范围的矩形，而非从截图推断移动。

在 1000x800 视口（600px 宽宿主）下，基线 WebKit 编辑器被限制在 320px。粘贴 + 换行后，其 scrollTop 为 1943px，光标底部为 747.5px。在第一次软换行时它滚动到 1968px：**20px 的行移动了 25px**，把光标底部移到 742.5px。这暴露了手工字形边缘滚动与原生光标显示之间的不匹配。

带尾随换行的粘贴也有错误几何：WebKit 测量了前一行，而 Chromium 不返回折叠范围矩形并让 scrollTop 保持在零，直到后续编辑。

## 修正

- 使用完整行高（含行距）与编辑器内边距作为光标的可见区域，向外舍入小数修正。
- 对原生输入应用与粘贴/手工换行相同的本地显示。只改手工显示不够：一个中间实验在原生软换行时仍把光标移动 5px。
- 不动活动中的输入法组合；在组合提交后显示。
- 用编辑器现有的零宽空格约定填充粘贴的尾随换行，把光标停在填充之前。序列化移除填充，因此提交文本不变。
- 绝不滚动祖先、强制文档末尾、在测量时更改实时选择，或对范围/编辑器外选择动作。

## 结果

- WebKit 与 Chromium：视口宽度 1000px 与 500px，各配合零/一/两个尾随粘贴换行，随后 Shift+Enter 与 180 个输入字符。全部 12 个用例通过。光标底部相对编辑器保持在 **WebKit 315.5px / Chromium 315px**，包括重复软换行。编辑器高度/顶部保持固定，scrollTop 从不后退，页面 scrollTop 保持零。
- 文档中部粘贴 + 输入在两种引擎的两种宽度下通过；后续内容保持在视口下方而非跳到末尾。
- `MentionEditor.scroll.test.tsx`：14 个测试通过，覆盖内边距/行框几何、小数舍入、原生输入、尾随换行序列化、组合处理、选择所有权与现有显示用例。
- 桌面端检查：`tsc --noEmit`、全部 `src/**/*.{ts,tsx}` 上的 ESLint 与完整 Vitest 套件通过（**110 个文件 / 973 个测试**）。

Mac 验收检查：粘贴长段落与多行文档，继续用中文输入法与拉丁文本输入，交替 Shift+Enter 与软换行，并在中间编辑。在常规与缩放显示设置下检查。文本应跟随光标而无额外垂直抖动；候选选择与发送必须保持不变。
