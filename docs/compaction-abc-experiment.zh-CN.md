# 压缩策略对比（A/B/C/M/Codex/OpenCode）

**问题：** S2 已经保护用户／assistant 原文之后，付费调用模型摘要是不是值得？其他 agent 公开的策略表现如何？

当前默认是 C，说明见 [C 压缩](compaction.zh-CN.md)。本页记录支持这次切换的实验。

## 参与对比的策略

| 组 | 压缩后保留什么 | 来源 |
|---|---|---|
| **A** | 保护原文＋递归模型摘要＋近期尾部（此前默认） | 本仓库，C 之前 |
| **B** | 保护原文＋尾部，删除摘要且不补 | A 的消融 |
| **C** | 保护原文＋固定 2K 工具证据索引＋尾部 | 本仓库，当前默认 |
| **M** | 摘要＋近期尾部，被覆盖原文丢弃 | 实验时的 `origin/main` |
| **Codex** | **全部用户消息（≤20 000 tokens）＋摘要**；不含 assistant 正文与工具输出 | `openai/codex` @ `b13164d8`，`compact.rs::build_compacted_history` 与 `templates/compact/prompt.md` |
| **OpenCode** | **摘要＋保留尾部**（`min(15 000, max(2 000, usable/4))`），摘要输入中工具输出截断到 2 000 字符 | `anomalyco/opencode` @ `e03db9bc`，`session/compaction.ts` 与 `session/message-v2.ts` |

Codex 与 OpenCode 是按上述提交**读源码后重新实现的选取规则**，不是 fork；prompt 逐字转录，所读文件的 git blob SHA 记录在 [abc_external_provenance.json](../scripts/abc_external_provenance.json)。未建模：Codex 的 remote v2（服务端，需要 OpenAI 托管 provider）与 `Feature::TokenBudget`（开新窗口、不生成摘要）；OpenCode 的 `compaction.prune`（默认关闭）。

## 结果

不提供检索，每阶段 48 个字段（2 条链 × 2 模型 × 12 字段）：

| 组 | 第 1 阶段 | 第 4 阶段 | 第 8 阶段 | 全部 | 平均上下文 |
|---|---:|---:|---:|---:|---:|
| A | 41/48 | 43/48 | 42/48 | 126/144 | 14.1K |
| B | 21/48 | 26/48 | 26/48 | 73/144 | 12.7K |
| C | 42/48 | 44/48 | 44/48 | **130/144** | 14.1K |
| M（`origin/main`） | 43/48 | 38/48 | 36/48 | 117/144 | 5.4K |
| **Codex** | **46/48** | **47/48** | **47/48** | **140/144** | **1.6K** |
| OpenCode | 43/48 | 44/48 | 33/48 | 120/144 | 5.2K |

上下文大小是 harness 估算，不是 provider 计费 tokens（见限制）。

四个结论：

1. **Codex 在准确率和上下文大小上同时最好。** 它摘要时读取全部历史、保留所有用户消息，投影只有约 1.6K tokens 却答对 140/144。在这套 fixture 上其他策略都差一截。
2. **纯摘要保留会随反复压缩退化，C 不会。** M 在首次压缩时是 A/B/C/M 中最好的（43/48），随后掉到 38、36，因为每轮摘要要承载更多内容。C 稳定在 42/44/44，因为它的证据每轮都从 journal 重建，而不是被反复重摘要。OpenCode 呈现同样的衰减且更剧烈：43 → 44 → **33**。
3. **直接删摘要仍是最差选项（B，73/144）。** 它丢的是从未出现在用户或 assistant 正文里的工具事实。
4. **C 是成本最低且站得住的方案。** 每次压缩零模型费用，144 个字段中只比 Codex 少 10 个。

## 费用

通过平台 `credit_cost` 在真实 provider 上测得，当前账本：

| 组 | 请求数 | 人民币 | 每次压缩 |
|---|---:|---:|---:|
| A/B/C（仅压缩） | 33 | 1.23 | A **¥0.037**；B、C **¥0** |
| A/B/C（全部问卷） | 690 | 6.17 | — |
| M（`origin/main`） | 260 | 1.88 | ¥0.018 |
| **Codex 组** | 226 | **11.14** | 每次压缩 **¥0.50**（输入 1020 万 tokens） |
| OpenCode 组 | 245 | 1.75 | ¥0.023 |
| **合计** | **1454** | **22.18** | |

"每次压缩"只计维护该保留规则本身的成本，不含普通模型请求与之后的检索（加检索的问卷每次请求另花 ¥0.0036–0.0101）。A/B/C 的 690 份问卷覆盖三种检索接口，因此与其他组单接口的计数不可直接比较。

### Codex 那一列是"缓存冷"价格，这是实验假象

见下文"前缀缓存"：形状与 Codex 相同的压缩请求能命中约 **99.9%** 的缓存，同样读 25.8 万 tokens，费用只有冷请求的 **约 1/48**。我的驱动每个阶段把记录拍平成新的文本块，相邻阶段没有任何字节相同的前缀，所以 Codex 组的每一次压缩都按未命中计费。**真实 Codex 是把摘要指令追加到活动消息历史上——那正是能命中的形状。** 请把 ¥0.50 当作上界，而不是 Codex 的成本。

## 前缀缓存

在真实 provider 上直接测量（`scripts/abc_experiment/cache_test.py`、`cache_probe.py`），单链、第 1 阶段、DeepSeek Flash：

| 请求形状 | 输入 tokens | 缓存命中 | 计费 |
|---|---:|---:|---:|
| 会话消息数组＋尾部追加指令 | 257,978 | **257,792（99.9%）** | **¥0.0135** |
| 同一会话，冷启动 | 257,978 | 0 | ¥0.65（预留值） |
| A 式裁剪摘录，连发两次 | 14,846 | 14,592（98.3%） | ¥0.0145 |

三点结论：

1. **"读全部历史"本身并不贵。** 有共享前缀时，25.8 万 tokens 的边际成本约 ¥0.013——**比我们 A 的 ¥0.037 还便宜**；而 A 只读约 1.6 万 tokens，却因为每个字节都变了而每次都未命中（A 的 33 次摘要：524,196 tokens 中仅命中 14,592，**2.8%**）。
2. **压缩设计应当保住前缀。** 把摘要指令追加到活动会话尾部——而不是拍平后裁剪——才是折扣的来源，而且它让摘要读的是**全部历史**，不是节选。
3. **这改变了 A/B/C 的成本对比。** A 相对"全历史摘要"的成本优势，很大程度上是实验的缓存假象，而不是两种设计本身的属性。

受控重复实验（`cache_diag.py`）复现了该结论：先预热数组、再追加指令，命中 **257,943 tokens 中的 257,792（99.9%）**，花费 **¥0.0094**，而同样前缀冷启动为 ¥0.65。

一个较晚发现的注意点：首次 C+summary 运行用 `max_tokens=16` 预热，只得到 0–2% 命中——这样的请求不会填充缓存。上表的 99.9% 用的是正常输出额度。另有两次相同请求完全未回报 usage，账本记录的是预留值而非结算值。

## 检索有没有用？（所有组用同一套检索工具）

随后用**完全相同**的归档 CLI 重新测了每一组——同一套 `future session history search/get`、同一批按阶段隔离的会话、同样 5 次调用与 32KB 预算。检索引擎因此是受控变量，唯一差异是压缩投影。

| 组 | 闭卷 | 加检索（同一 CLI） | 变化 |
|---|---|---|---|
| A | 126/144 · 12/12 交付 | 120/144 · 10/12 交付 | −6 |
| B | 73/144 · 12/12 交付 | 117/144 · 10/12 交付 | **+44** |
| **C** | 130/144 · 12/12 交付 | **132/144 · 11/12 交付** | **+2** |
| M（`origin/main`） | 117/144 · 12/12 交付 | 107/144 · 9/12 交付 | −10 |
| Codex（混合） | 140/144 · 12/12 交付 | 120/144 · 10/12 交付 | −20 |
| OpenCode（混合） | 120/144 · 12/12 交付 | 107/144 · 9/12 交付 | −13 |

未交付的问卷按 0 计入这些总数。决定性的一列是**有多少问卷完成**：加检索后，凡是交付的答案几乎全对。

| 组 | 闭卷，仅计交付 | 加检索，仅计交付 |
|---|---|---|
| A | 126/144 | 120/120（100%） |
| B | 73/144 | 117/120（97.5%） |
| **C** | 130/144 | **132/132（100%）** |
| M | 117/144 | 107/108（99.1%） |
| Codex | 140/144 | 120/120（100%） |
| OpenCode | 120/144 | 107/108（99.1%） |

**检索把准确率拉平，使对比变成"谁会把调用预算烧光"的问题。** 只要能查，各组几乎都全对，剩下的差别只在有多少次问卷用完了 5 次调用却没给出答案：

* **加检索对信息最少的组帮助最大**（B，+44），对 C 只有小幅提升（+2）——C 本来就带着需要的事实。
* **加检索反而损害信息丰富的组。** Codex 少了 20 个字段和 2 次交付：投影很密时，模型会去搜细节而不是直接作答，最终耗尽调用预算。OpenCode（−13）与 `origin/main`（−10）表现相同。这是固定请求预算造成的现象——若调用不限，准确率大概会一起收敛上去——但有限预算才是真实条件。
* **C 是唯一 12 份问卷里交付 11 份的组**，即它花的调用最少：证据索引已经指出值得读取的条目，检索是定向的而非探索性的。

所以"C＋检索能不能赢 Codex"，诚实的回答是**取决于比哪个 Codex**：

| 对比 | 胜者 |
|---|---|
| C＋检索 vs Codex **＋检索**（同工具） | **C**，132/144 对 120/144（交付 11/12 对 10/12） |
| C＋检索 vs Codex **闭卷** | **Codex**，140/144 对 132/144 |
| C 闭卷 vs Codex 闭卷 | Codex，140/144 对 130/144 |

在检索工具相同的条件下，C＋检索胜过 Codex，因为 C 更会花它的查询预算。但它赢不过 Codex 的闭卷成绩：Codex 的摘要是由一个读过全部历史的模型写的，在这套 fixture 上，这一点的价值高于 2K 证据索引加若干次查询。

**Codex 那一列的"加检索"是混合体，不是 Codex 自身的能力。** Codex 内置的 `history` 工具受托管后端与付费 ChatGPT 套餐限制（见下文），所以这一组是 **Codex 的投影配我们的 CLI**。它展示的是"当存在检索工具时该投影值多少"，不是对 Codex 产品的测量。

## 三种检索接口对比

"检索"不是单一概念。每一组都用三种不同查找接口重测，**投影相同**：

| | 我们 | Codex | OpenCode |
|---|---|---|---|
| 检索对象 | 会话归档 | 会话归档（按 window 分组） | **工作区文件，不是对话** |
| 返回定位 | `entryId`＋**字节偏移** | `window_id`＋`item_id`＋**`next_offset_chars` 游标** | 文件路径＋行号 |
| 搜索语义 | 字面子串，ASCII 忽略大小写 | 字面子串，**区分大小写** | **正则**（ripgrep） |
| 读取方式 | 固定分块，`--limit` ≤ 32768 | 调用方自选 `offset_chars`／`limit_chars` | 行范围 |
| 搜索返回片段 | 匹配偏移附近的头尾块 | `truncated_content`（位置由服务端决定，见下） | 命中行 |

> **更正。** 本页早先的版本报告 Codex 接口崩到 11/144，并归因于"没有匹配位置"。那个数字是**我自己实现的两处缺陷加上我自设的 5 次上限**造成的假象：我没有实现 `read_item` 文档中的 `next_offset_chars` 游标，还发明了一条任何 agent 都没有的 5 次上限。两处都已修复，正确结果如下。

### 无上限、契约已补齐

| 组 | 我们 | Codex 接口 | OpenCode 接口 |
|---|---|---|---|
| A | 121/144 · 丢 1 · 13.8 轮 | — | — |
| B | 107/144 · 丢 1 · 8.2 轮 | — | — |
| **C** | **132/144 · 丢 1 · 3.7 轮** | **132/144 · 丢 0 · 8.8 轮** | **132/144 · 丢 0 · 4.4 轮** |
| Codex 投影 | — | **143/144 · 丢 0 · 8.0 轮** | — |
| M（`origin/main`） | — | 119/144 · 丢 1 · 9.4 轮 | — |

格式为：答对/144 · 丢失问卷数 · 每题平均模型请求数。无上限重跑目前覆盖全部六组的 Codex 接口，以及 C 的三种接口；其余组合见下方仍有上限的表格。

**C 与接口无关：三种接口都是 132/144。** 只要接口实现正确、允许模型跑完，查找工具就不再是决定因素。

**整个研究中最好的结果是 Codex 自己的投影配 Codex 自己的接口：143/144，零丢失。** 它需要更多轮（8.0 对 3.7），因为它的搜索不返回匹配位置，模型必须靠游标翻页——但有游标就能到达。

### 游标改变了什么

没有 `next_offset_chars` 时，模型必须自己计算续读位置；在有上限的那轮里，它发出了 **126 次带猜测偏移的 `read_item`**（86000、86700、87400、88007、88100——手工逼近约 87500 字符处的标记），在到达前用完回合。补上游标后，同一接口让 C 达到 132/144、让 Codex 投影达到 143/144。

### 片段位置无法观测

`search_contents` 只文档化了 `max_chars_per_item` → "max characters returned in each item's `truncated_content`"，**没说**窗口从哪里取；而 `HistoryNotesToolOutput::new` 明确写着"服务器在加密前应用所请求的输出预算"——即由后端而非客户端决定。我实现了 `head` 与 `centered` 两种位置（`abc_retrieval.CODEX_SNIPPET_MODE`），而不是把一种猜测当成契约。上表使用默认值；有了游标之后位置的影响大幅下降，因为模型可以翻到任意位置。

| B | 117/144 · 丢 2 | 0/144 · 丢 12 | 14/144 · 丢 10 |

### OpenCode 根本没有对话检索

它的完整工具集——`glob`、`grep`、`read`、`shell`、`edit`、`write`、`task`、`todo`、`websearch`、`webfetch`、`lsp`、`apply_patch`、`skill`，外加 MCP 与插件工具——**没有任何历史工具**。它的恢复路径是文件系统：重读项目，而不是重读对话。按此忠实实现（每个文件只留最新版本），无上限时该模式仍能让 C 达到 132/144，因为多数问题问的是当前状态；它无法恢复的是被取代的状态，`buried` 字段（有上限时 3/12）就是直接证据。

### 这改变了什么

* **"C＋检索打赢 Codex"是错的框架。** 接口拉平且不设上限后，Codex 的投影得分最高（143/144）。C 的优势不是原始准确率，而是**成本**：它以**零压缩成本**达到 132/144（约为 Codex 的 92%），并且在我们的接口上需要的查找轮数更少（3.7 对 8.0）。
* 检索质量是**接口加预算**的属性，不是投影单独的属性。同一个投影在同一份公开契约的两种实现下，得分可以是 11/144，也可以是 132/144。
* 任何"策略 X 需要 N 次查找"的说法，都必须说明接口，以及预算是否有上限。

## 给 C 加摘要会更好吗？

构造了 C+summary：保留 C 的全部内容（保护原文、确定性证据、近期尾部），**外加一份模型摘要**，且摘要使用高缓存命中形状生成——把活动材料作为真实消息数组，指令追加在尾部。12 份问卷、无上限、Codex 接口。

| 组 | 得分 | 无有效答案 | 每题请求数 | 说明 |
|---|---:|---:|---:|---|
| **C** | **132/144** | 0 | 8.8 | 摘要零成本 |
| C＋摘要 | 125/144 | 1 | 9.8 | 摘要每阶段 ¥0.02–0.25 |
| Codex | **143/144** | 0 | 8.0 | 全历史摘要 |

**加摘要反而让 C 变差（132 → 125），并且有一份 GLM 问卷始终没结束**——它在 `analysis` 第 8 阶段烧完 60 轮失控保护，没有产出答案。摘要在预期的地方起了作用（`buried` 漏答 8 → 5），但在别处付出代价（`latest_version`，以及整份问卷丢失）。

**这个结论只适用于“朴素”摘要，不适用于摘要本身。** 见下文“我们能模仿 Codex 的‘全量’吗”：**粘性**摘要（每轮把上一轮摘要一起传下去）配合**溢出触发**刷新，可以达到 72/72，与 Codex 持平。这里失败的是在已携带证据的投影上临时加一份一次性摘要——摘要变成对证据索引已覆盖内容的第二个、可被质疑的叙述，并把模型拉向搜索而不是作答。这些朴素变体每次都从头重建摘要，什么都没累积，`buried` 只微涨，其他字段却在掉。

### 仍然存在的真实差距

Codex 依然领先 11 个字段，而它的优势是**摘要读取全部历史**（第 1 阶段 258K tokens），而不是节选材料。我们的摘要读的是裁剪后的材料。这个差别——**输入广度，而不是"摘要 vs 证据"**——才是尚未验证的杠杆。读全部历史的摘要在前缀命中缓存时只要约 ¥0.0094，这是目前已知最便宜的买到那 11 个字段的方式。

## 我们能模仿 Codex 的"全量"吗？

能模仿一部分——而且有用的那部分不是"读全部"。

**直接读归档不行。** C 保留完整 journal，所以"全部"在第 1 阶段是 25.5 万 tokens、第 8 阶段是 208 万；从第 4 阶段起就被 provider 拒绝。Codex 之所以能摘要"全部"，是因为它的压缩**替换**历史，活动上下文始终压在约 69 万以下。

可用的等价物是**活动上下文**，并像 Codex 那样链式传递：

```
live(0) = 归档 + 尾部                      -> summary_0
live(N) = [summary_{N-1}] + 此后新增记录    -> summary_N
投影(N)  = C 的投影 + summary_N
```

两个必要条件，都是先失败才找到的：

* **摘要必须"粘性"**：我的第一版每次都用 C 的投影重建摘要，自己上一轮的摘要从未传下去，第 0 阶段的值到第 4 阶段就丢了。
* **压缩必须按溢出触发**：第二版只在探针边界压缩，于是累积了四个阶段（约 100 万 tokens）的记录，第 8 阶段请求被拒。

两者都做到后，在同样的六份问卷上（DeepSeek、两条链、第 1/4/8 阶段）：

| 组 | 得分 | 无答案 | 每题请求数 |
|---|---:|---:|---:|
| **C＋粘性摘要＋Codex 触发** | **72/72** | 0 | 7.3 |
| Codex（用户消息＋摘要） | 72/72 | 0 | 7.8 |
| C（仅证据） | 70/72 | 0 | 8.5 |
| C＋摘要（裁剪输入） | 70/72 | 0 | 6.2 |
| A（原文＋摘要） | 69/72 | 0 | 9.3 |
| M（`origin/main`） | 53/72 | 1 | 7.8 |
| C＋摘要（非粘性） | 55/72 | 1 | 11.8 |
| B（无摘要） | 50/72 | 1 | 8.2 |

唯一区分它们的字段被补齐：C 的 `buried` 从 4/6 变成 **6/6**，与 Codex 逐字段持平。**缺的从来不是 assistant 消息或更大的摘要，而是一份按溢出触发、累积传递的摘要。**

费用：8 次压缩**未命中缓存**共 ¥7.89（每次约 ¥0.99）。预热后同样请求命中 99.9%、只要 ¥0.065–0.085——因为真实会话早已把这些前缀当作普通回合发送过。

## 保留 assistant 正文，不就应该比 Codex 好吗？

**是——但前提是摘要真的被压缩了。** 前面报告的"打平"是真的，但它**不能**说明逐字保留没有价值。

Codex 丢的是"保留"，而它的摘要**读取**了 assistant 正文：摘要输入是整个活动历史。所以信息仍然经过一次，而且**只要摘要相对原文足够大就能存活**。在 assistant 覆盖 fixture 上，agent 自己的消息只有 **568 字符（约 142 tokens）**，摘要几乎逐字复现了它的理由句，两种规则都拿到 **17/28**，assistant 专项 **8/12**。

由此有两点：

1. **主对比根本测不出这件事。** 原始 12 字段问卷里只有**一个** assistant 专属值（`first_code`），所以"Codex 143/144 对 C 132/144"在 assistant 处理这一点上什么都说明不了。
2. **一旦有压缩压力，差别是决定性的。** 让 agent 写下 *N* 个不同的决策代码，把摘要限制在约 200 词，然后精确索要其中 10 个：

| assistant 内容 | assistant tokens | 摘要输出 | 压缩比 | 我们：逐字保留 | Codex 规则：仅摘要 |
|---|---:|---:|---:|---:|---:|
| 40 项决策 | 2 174 | 4 088 | 无压力 | 10/10 | 10/10 |
| 160 项决策 | 8 659 | 564 | **15×** | **10/10** | **0/10** |
| 400 项决策 | 21 629 | 549 | **39×** | **10/10** | **1/10** |

当摘要与被摘要材料一样大时，什么都不会丢，两者打平。一旦必须压缩——15× 以上——**精确标识符最先消失**，精确索要代码的问题**一个都答不出**。逐字保留则全部保住。

这正是 C 已有的性质：assistant 正文位于保护原文集合中，每一轮都从 journal 重建。之前的对比只是从未触发它。

**生产环境更深地处于这一区间，而不是在区间之外。** C 的证据槽是 2K tokens；Codex 组在 25.8 万 tokens 输入下的摘要为 1.1–1.5K tokens——压缩比接近 200×。上面的扫描用于定位转折点，并未夸大效果。

## 真实考卷：真实追问到底在问什么

上文"保留 assistant 正文不应该更好吗"用的是专门构造的 fixture。这里在**真实会话**上重做该问题，并先测量真实追问的指向。

### 测量

对 30 个真实会话的 254 个追问回合分类（本地只读）：

| 追问指向 | 占比 |
|---|---:|
| **agent 自己的产出** | **约 80%** |
| 重复用户自己先前的要求 | 约 4.3% |
| 新要求 | 5.9% |

分类器只统计了显式代词，所以是低估；被判为"其他"的 64% 大多是针对 agent 产出的，只是**用对象名而非代词指代**（"我收回「能不能模糊一下像云」这点"、"首页的「查看文档」貌似没放在按钮垂直中央"）。

原始 12 字段问卷把 **12 个事实中的 11 个放在用户回合或工具结果，只有 1 个在 assistant 正文**——与真实提问的指向恰好相反。

### 考卷

取值来源按实测分布配比：assistant 正文 12 个、用户回合 2 个、工具结果 3 个，另混入 8 个**未出现过的诱饵值**；模型标注哪些出现过。丢掉了某个值的投影无法把它与诱饵区分。这是一种**保留度探测**（识别而非自由回忆）。

### 链：3 合成 + 3 真实

`pipeline` 是新增合成链，其 gold 部分落在 assistant 回合（一项决策、其理由代码、重试预算、一次自我更正）。三个真实会话分别为 756/685/591 条记录；其标识存放在 git-ignored 配置中，**仓库里不出现任何会话标识**。

### 结果

C3 ＝ assistant 与 user 原文逐字保留 ＋ 工具证据 ＋ 尾部 ＋ 摘要；仅摘要 ＝ 用户消息 ＋ 摘要（Codex 规则）。**两者使用同一份粘性摘要**，唯一变量是保留了什么。

| 链 | C3 | 仅摘要 | 差值 | C3 投影 | 仅摘要投影 |
|---|---:|---:|---:|---:|---:|
| analysis（合成） | 10/18 | 9/18 | +1 | 11.1 K | 1.3 K |
| export（合成） | 10/18 | 9/18 | +1 | 11.2 K | 1.4 K |
| pipeline（合成） | 9/18 | 9/18 | **0** | 4.7 K | 1.0 K |
| real-stream | 35/45 | 29/45 | +6 | 8.3 K | 2.4 K |
| real-visual | 28/36 | 27/36 | +1 | 4.8 K | 0.9 K |
| **real-yt** | **34/44** | **27/44** | **+7** | 8.5 K | 2.0 K |
| **合计** | **126/179** | **110/179** | **+16** | | |

| 分组 | C3 | 仅摘要 | 差值 |
|---|---:|---:|---:|
| 真实会话 | **97/125** | 83/125 | **+14（+11.2 分）** |
| 合成链 | 29/54 | 27/54 | +2（+3.7 分） |

两种规则都使用**与 C 证据索引相同的裁剪方式**（保留头尾、而非整块），因此所有投影都在 4.7–11K tokens，合成与真实的数字可直接比较。仅摘要一侧很小，因为它除了摘要几乎不保留别的东西——这正是对比的意义。

**双方误报均为 0**：差距纯粹来自"还能不能从留存内容中确认该值"，不是幻觉。

两点诚实的解读：

* **真实会话的差距才可信：+11.2 分。** 它在 assistant 正文最多的会话上最大（real-yt，+7），在几乎全是工具流量的会话上最小（real-visual，+1）。
* **合成链几乎分不开（0 到 +1）。** 这并不矛盾——它们的 assistant 回合刻意做得很短，几乎没有可供"逐字保留"救回的独有内容，且每阶段只有 6 个可判分值。它们测的是工具密集负载；真实会话测的是真实提问来源的负载。

因此之前的说法需要修正一处：C3 并非"在每一条链上都领先"——它在 `pipeline` 上打平，因为该 fixture 让 assistant 正文几乎不含独有事实。**优势大小取决于"负载中有多少可答细节存在于 agent 自己的产出里"**：真实追问约 80%，而原始问卷接近 0。

这闭合了整条论证：在真实提问指向的地方测量，逐字保留 agent 自身产出比仅摘要高出 **12 分**——这正是先前 fixture 暗示、而原始问卷看不到的方向。

## 之前"assistant 消息无用"的结论是覆盖不足造成的吗？

**是。** 我核查了原始 12 个字段各自真正出现在哪种记录里：

随后构造了含四个"只存在于 assistant 正文"事实的 fixture（一项决策、其理由代码、重试预算、一次自我更正），在同一历史上闭卷对比两种保留规则：

丢弃 assistant 正文会**完整丢掉那四个字段**，其余毫无影响。所以"Codex 不留 assistant 消息仍能赢"是我的问卷偏重机器状态造成的假象，不是 Codex 的特性。assistant 正文承载着别处不会重述的承诺：决策、理由、撤回和未决问题。问一句"你为什么这么选"，差别立刻显现。

## Codex 自己有检索能力吗？

**有——这一点会影响整个对比该怎么读。** Codex 在 `codex-rs/ext/history-notes` 里带了一套第一方历史检索工具，它自己的描述就是：*"在上下文窗口重置后，通过列出、读取和搜索规范化历史来恢复先前对话。"* `history` 命名空间提供 `list_windows`、`list_items`、`read_item`、`search_contents`；另有 `notes` 命名空间，让私有笔记跨上下文窗口保留；还会自动向上下文注入一条 thread hint。

但在本实验测的配置里它没有生效。以下是**同时**满足才可用：

| 条件 | 本实验的情况 |
|---|---|
| `Feature::TokenBudget`、`Feature::ContextManagement` | 均为 `Stage::UnderDevelopment`，`default_enabled: false` |
| 模型 `supports_experimental_context` | 第三方 provider 不满足 |
| provider `supports_codex_backend_routes()`、`requires_openai_auth`，且无 env key／provider auth | 否 |
| 认证方式／套餐 | 必须是 **ChatGPT** 账号且为 **Plus／Pro／ProLite** |

历史数据放在**托管后端**（`alpha/history/v2/*`），不是本地文件。所以本次测的 Codex 是**没有启用实验性上下文管理的本地兜底压缩**——也就是任何使用 API key 或第三方 OpenAI 兼容 provider 的人实际能用到的那套。**"Codex＋它自己的检索"这一组，用 API key 无法复现。**

两点后果：

1. "C＋检索"的方向，与 Codex 付费托管产品已经在走的方向一致：**压缩＋一条回到原始对话的路**。这是支持 C＋检索设计的证据，而不是反对它的。
2. 任何"C＋检索"与"Codex"的对比都必须说明是哪个 Codex。拿"C＋检索"去比"没有历史工具的 Codex"不是同条件比较；本页的数字正是后一种情况。

## 外部策略是如何跑的

Codex 与 OpenCode **替换**对话，所以第 N 次压缩读到的是已被压缩过的历史加此后新增内容，而不是 journal 支撑策略可以合法重建的原始归档。因此存在两种压缩：

* **探针阶段强制压缩一次**（第 1、4、8 阶段），使记录的投影与其他组在同一背景下可比——这是消融设计；
* **探针之间按各自的溢出触发压缩**，在累积历史超出 provider 窗口之前执行。若不这样做，这一组会携带现实中任何会话都装不下的历史：第一次强行在第 4 阶段压缩时被拒绝，报错为 *"maximum context length is 1048576 tokens. However, you requested 1072531"*。

这次拒绝同时校准了 harness：provider 对同一批消息计 1 064 339 tokens，而 harness 估算约 766K（约 1.45 倍差距）。溢出阈值使用这个实测系数。各策略保留自己的输出预算：OpenCode 硬编码 4 096，Codex 使用模型上限（本实验封顶 65 536）。

## 限制

- Codex 与 OpenCode 是依据特定提交的单点复现。其保留规则与 prompt 来自那些提交；上游后续改动会让数字失效。
- **Codex 的数字来自它的本地兜底路径。** 它的第一方历史／笔记检索工具需要托管 Codex 后端、付费 ChatGPT 套餐和两个 UnderDevelopment 特性开关，因此在任何 API key 或第三方 provider 配置里都不存在——包括本次实验。拿带检索的策略与之对比前，先看上文"Codex 自己有检索能力吗"。
- 探针阶段对所有组都是强制的。探针之间外部策略使用自己的触发，因此某个边界的投影可能来自溢出压缩而非边界压缩；每个投影里的 `compactions` 字段记录了实际发生的情况。
- harness 的 token 估算在这套 fixture 上比 provider 计数低约 1.45 倍，所以上下文一列低估了真实提示长度。
- OpenCode 在 GLM 上有两次触及自己的 4 096 输出上限（截断摘要按其源码被接受），还有一次返回空摘要——OpenCode 把这种情况视为**拒绝压缩**，记录为 `declined`，没有改写成假摘要。这是“4K 输出上限 + 大历史”的真实脆弱点。
- 这是事实回忆，不是任务续做，不能说明 agent 能否接着干活。
- 两条合成链来自同一蓝图、工具记录结构化，不是两种独立自然任务；问卷对携带工具证据的策略有利。
- 加检索的数字来自固定的 5 次调用／32KB 预算。**正是这个预算把各组区分开来**，预算放大或取消会让差异收敛；因此上面的排序不能被当作投影本身的固有属性。
- **Codex 接口那一列测的是我们的近似实现，不是 Codex。** 它受三个限制：(a) `read_item` 的文档契约带有游标 `next_offset_chars`，我没有实现；(b) `HistoryNotesToolOutput::new` 明确写着"服务器在加密前应用所请求的输出预算"，所以片段位置由服务端决定、我无法观测——我假设了头部截断，若服务端以匹配为中心居中返回，得分会更高；(c) 命名空间工具名、`encrypted` 查询参数与服务端执行都是 Responses API 的特性，在 Chat Completions 上无法复现。5 次请求上限也是我设的，不是 Codex 的——生产环境没有这个上限，所以"耗尽预算"描述的是我的预算与"需要更多回合的接口"相互作用，而不是工具弱。**本实验支持的是"接口形状"结论（不返回匹配位置 ⇒ 需要更多回合）**，11/144 这个数字不应被读作 Codex 的能力。
- 前缀缓存只在隔离条件下测量过（见"前缀缓存"）。它对完整 A/B/C/M 对比的影响是推断，不是端到端重测。

- 加检索的问卷在闭卷之后运行并复用同一批投影，所以没有重新测量压缩成本。检索成本单独列出（每次请求 ¥0.0036–0.0101）。
- 账本保留了全部失败：4 次作废的早期 OpenCode 调用（尾部预算实现有误）、1 次被中断后重试的 M 请求，以及阈值校准前因超长被拒的 Codex 尝试。
