# 压缩策略对比（A/B/C/M/Codex/OpenCode）

**问题：** S2 已经保护用户／assistant 原文之后，付费调用模型摘要是不是值得？其他 agent 公开的策略又表现如何？

当前默认是 C，说明见 [C 压缩](compaction.zh-CN.md)。本页记录支持这次切换的实验。

## 参与对比的策略

| 组 | 压缩后保留什么 | 来源 |
|---|---|---|
| **A** | 保护原文＋递归模型摘要＋近期尾部（此前默认） | 本仓库，C 之前 |
| **B** | 保护原文＋尾部，删除摘要且不补 | A 的消融 |
| **C** | 保护原文＋固定 2K 工具证据索引＋尾部 | 本仓库，当前默认 |
| **M** | 摘要＋近期尾部，被覆盖原文丢弃 | 本次实验时的 `origin/main` |
| **Codex** | **全部用户消息（≤20 000 tokens）＋摘要**；不含 assistant 正文与任何工具输出 | `openai/codex` @ `b13164d8`，`compact.rs::build_compacted_history` 与 `templates/compact/prompt.md` |
| **OpenCode** | **摘要＋保留尾部**（`min(15 000, max(2 000, usable/4))`），摘要输入中工具输出截断到 2 000 字符 | `anomalyco/opencode` @ `e03db9bc`，`session/compaction.ts` 与 `session/message-v2.ts` |

Codex 与 OpenCode 是按上述提交**读代码后重新实现的选取规则**，不是 fork；prompt 逐字转录，所读文件的 git blob SHA 记录在 [abc_external_provenance.json](../scripts/abc_external_provenance.json)。Codex 另有两条未建模的路径：remote v2（需要 OpenAI 托管 provider）和 `Feature::TokenBudget`（直接开新上下文窗口、不生成摘要）。OpenCode 的可选 `compaction.prune` 未启用，因为默认关闭。

## 实验设置

| 项目 | 内容 |
|---|---|
| 数据 | 两条工具密集合成链（ATLAS、MERIDIAN），第 8 阶段各约 200 万估算 tokens |
| 模型 | DeepSeek Flash、GLM-5.3-Flash |
| 压缩点 | 8 阶段中的第 1、4、8 阶段（A/B/C/M）。Codex 与 OpenCode **仅第 1 阶段**，原因见费用 |
| 问卷 | 12 字段：首问与最新要求、随机码、新旧工具值、只在中段出现的值、验证、阻塞、部署状态、未记录设备 |
| 规模 | 4 条链 × 3 阶段 × 6 组 ≈ 268 次模型请求，**¥5.43** |

## 结果

不提供检索，每阶段 48 个字段（4 条链 × 12）：

| 组 | 第 1 阶段 | 第 4 阶段 | 第 8 阶段 | 全部 | 平均上下文 |
|---|---:|---:|---:|---:|---:|
| A | 41/48 | 43/48 | 42/48 | **126/144** | 约 7.0K |
| B | 21/48 | 26/48 | 26/48 | **73/144** | 约 6.1K |
| C | 42/48 | 44/48 | 44/48 | **130/144** | 约 7.0K |
| M（`origin/main`） | 43/48 | 38/48 | 36/48 | **117/144** | 约 4.9K |
| Codex | **46/48** | 未跑 | 未跑 | — | 约 1.1K |
| OpenCode | 43/48 | 未跑 | 未跑 | — | 约 4.9K |

三个结论：

1. **只靠摘要保留会随重复压缩退化，C 不会。** M 在首次压缩时是 A/B/C/M 中最好的（43/48），随后掉到 38 和 36，因为后续摘要要承载越来越多内容。C 稳定在 42/44/44，A 稳定在 41/43/42——它们被覆盖的原文或证据在每轮都保留下来，而不是被反复重摘要。这正是 Codex 自己界面文案警告的失效模式（"长时间线程与多次压缩会让模型不够准确"）。
2. **直接删摘要是最差选项（B，73/144）。** 它丢的是从未出现在用户或 assistant 正文里的工具事实——这是信息被移除，不是同一种方案的省钱版本。
3. **首次压缩时，喂饱的摘要很强。** Codex 只用约 1.1K 上下文就得到 46/48，是六组里最小的投影，因为它的摘要器读取**全部历史**，替换历史又保留所有用户消息。它的优势来自“读了什么”，而不是“留下了什么”。

## 费用

| 组 | 每次压缩费用 | 原因 |
|---|---:|---|
| C | **¥0** | 不调用模型 |
| OpenCode | 约 ¥0.01 | 只摘要被截断的头部 |
| M | 约 ¥0.02 | 摘要裁剪后的材料 |
| A | 约 ¥0.039 | 摘要裁剪材料＋保护原文 |
| Codex | 约 ¥0.26 | 摘要**全部历史**（第 1 阶段约 25 万 tokens） |

Codex 的费用随归档增长：同样一次调用在第 4 阶段要读约 100 万 tokens，第 8 阶段约 200 万。把 Codex 与 OpenCode 扩展到第 4、8 阶段估计需要 ¥6–17，**在本实验的 ¥10 上限内没有运行**，所以它们只有单点数据。已记录总计 268 次请求、¥5.43。

## 限制

- Codex 与 OpenCode 只有首次压缩点；后续阶段行为未测量，只对照源码核对过它们的保留规则。
- Codex 的摘要读取完整历史，而 A/C/M 摘要的是裁剪材料。因此对比混合了“读什么”和“留什么”，费用那一列就是这种差异的代价。
- 两份数据来自同一合成蓝图、工具记录结构化，对携带工具证据的策略有利。
- 问卷考的是事实回忆，不是任务续做能力，不能说明 agent 能否接着干活。
- 请求在区组内随机，但未严格位置平衡；provider 缓存影响实付价格。
- 账本对失败是诚实的：有一次 M 阶段请求被中断后重试（原次结算未知，重试照常计费）；另有四次早期 OpenCode 调用因为尾部预算错误地按截断文本估算而 **invalidated**，已用 `v2` 重跑，作废的费用仍计入。

原始数据、fixture 与复现脚本：`scripts/abc_experiment/README.md`（harness），以及本地被 git 忽略的 `.future/research/abc-summary-a47313/`（账本、上下文、回答、评分）。
