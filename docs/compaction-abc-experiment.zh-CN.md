# 压缩策略对比（A/B/C/M/Codex/OpenCode）

**问题：** S2 已经保护用户／assistant 原文之后，付费调用模型摘要是不是值得？其他 agent 公开的策略表现如何？

当前默认是 C，说明见 [C 压缩](compaction.zh-CN.md)。本页记录支持这次切换的实验。

## 参与对比的策略

| 组 | 压缩后保留什么 | 来源 |
|---|---|---|
| **A** | 保护原文＋递归模型摘要＋近期尾部（此前默认） | 本仓库，C 之前 |
| **B** | 保护原文＋尾部，删除摘要且不补 | A 的消融 |
| **C** | 保护原文＋固定 2K 工具证据索引＋尾部 | 本仓库，当前默认 |
| **M** | 摘要＋近期尾部，被覆盖原文丢弃 | 实验时的 `origin/main` |
| **Codex** | **全部用户消息（≤20 000 tokens）＋摘要**；不含 assistant 正文与工具输出 | `openai/codex` @ `b13164d8`，`compact.rs::build_compacted_history` 与 `templates/compact/prompt.md` |
| **OpenCode** | **摘要＋保留尾部**（`min(15 000, max(2 000, usable/4))`），摘要输入中工具输出截断到 2 000 字符 | `anomalyco/opencode` @ `e03db9bc`，`session/compaction.ts` 与 `session/message-v2.ts` |

Codex 与 OpenCode 是按上述提交**读源码后重新实现的选取规则**，不是 fork；prompt 逐字转录，所读文件的 git blob SHA 记录在 [abc_external_provenance.json](../scripts/abc_external_provenance.json)。未建模：Codex 的 remote v2（服务端，需要 OpenAI 托管 provider）与 `Feature::TokenBudget`（开新窗口、不生成摘要）；OpenCode 的 `compaction.prune`（默认关闭）。

## 结果

不提供检索，每阶段 48 个字段（2 条链 × 2 模型 × 12 字段）：

| 组 | 第 1 阶段 | 第 4 阶段 | 第 8 阶段 | 全部 | 平均上下文 |
|---|---:|---:|---:|---:|---:|
| A | 41/48 | 43/48 | 42/48 | 126/144 | 14.1K |
| B | 21/48 | 26/48 | 26/48 | 73/144 | 12.7K |
| C | 42/48 | 44/48 | 44/48 | **130/144** | 14.1K |
| M（`origin/main`） | 43/48 | 38/48 | 36/48 | 117/144 | 5.4K |
| **Codex** | **46/48** | **47/48** | **47/48** | **140/144** | **1.6K** |
| OpenCode | 43/48 | 44/48 | 33/48 | 120/144 | 5.2K |

上下文大小是 harness 估算，不是 provider 计费 tokens（见限制）。

四个结论：

1. **Codex 在准确率和上下文大小上同时最好。** 它摘要时读取全部历史、保留所有用户消息，投影只有约 1.6K tokens 却答对 140/144。在这套 fixture 上其他策略都差一截。
2. **纯摘要保留会随反复压缩退化，C 不会。** M 在首次压缩时是 A/B/C/M 中最好的（43/48），随后掉到 38、36，因为每轮摘要要承载更多内容。C 稳定在 42/44/44，因为它的证据每轮都从 journal 重建，而不是被反复重摘要。OpenCode 呈现同样的衰减且更剧烈：43 → 44 → **33**。
3. **直接删摘要仍是最差选项（B，73/144）。** 它丢的是从未出现在用户或 assistant 正文里的工具事实。
4. **C 是成本最低且站得住的方案。** 每次压缩零模型费用，144 个字段中只比 Codex 少 10 个。

## 费用

| 组 | 请求数 | 人民币 | 每次压缩 |
|---|---:|---:|---:|
| A/B/C | 200 | 3.49 | A ¥0.037，B/C ¥0 |
| M | 48 | 0.79 | ¥0.018 |
| Codex | 33 | **10.49** | **¥0.42**（输入 907 万 tokens） |
| OpenCode | 42 | 0.83 | ¥0.030 |
| **合计** | **323** | **15.60** | |

Codex 最准也最贵：摘要器读取整段活动历史，单次压缩约为“只摘要”方案的 23 倍，也约等于整个 A/B/C 组的 3 倍。注意这种不对称：journal 支撑的 A/B/C/M 可以免费从归档重建投影，而破坏性替换历史的策略必须为每一次中间压缩付费，才能把历史压在窗口内。

## 外部策略是如何跑的

Codex 与 OpenCode **替换**对话，所以第 N 次压缩读到的是已被压缩过的历史加此后新增内容，而不是 journal 支撑策略可以合法重建的原始归档。因此存在两种压缩：

* **探针阶段强制压缩一次**（第 1、4、8 阶段），使记录的投影与其他组在同一背景下可比——这是消融设计；
* **探针之间按各自的溢出触发压缩**，在累积历史超出 provider 窗口之前执行。若不这样做，这一组会携带现实中任何会话都装不下的历史：第一次强行在第 4 阶段压缩时被拒绝，报错为 *"maximum context length is 1048576 tokens. However, you requested 1072531"*。

这次拒绝同时校准了 harness：provider 对同一批消息计 1 064 339 tokens，而 harness 估算约 766K（约 1.45 倍差距）。溢出阈值使用这个实测系数。各策略保留自己的输出预算：OpenCode 硬编码 4 096，Codex 使用模型上限（本实验封顶 65 536）。

## 限制

- Codex 与 OpenCode 是依据特定提交的单点复现。其保留规则与 prompt 来自那些提交；上游后续改动会让数字失效。
- 探针阶段对所有组都是强制的。探针之间外部策略使用自己的触发，因此某个边界的投影可能来自溢出压缩而非边界压缩；每个投影里的 `compactions` 字段记录了实际发生的情况。
- harness 的 token 估算在这套 fixture 上比 provider 计数低约 1.45 倍，所以上下文一列低估了真实提示长度。
- OpenCode 在 GLM 上有两次触及自己的 4 096 输出上限（截断摘要按其源码被接受），还有一次返回空摘要——OpenCode 把这种情况视为**拒绝压缩**，记录为 `declined`，没有改写成假摘要。这是“4K 输出上限 + 大历史”的真实脆弱点。
- 这是事实回忆，不是任务续做，不能说明 agent 能否接着干活。
- 两条合成链来自同一蓝图、工具记录结构化，不是两种独立自然任务；问卷对携带工具证据的策略有利。
- 账本保留了全部失败：4 次作废的早期 OpenCode 调用（尾部预算实现有误）、1 次被中断后重试的 M 请求，以及阈值校准前因超长被拒的 Codex 尝试。
