# 压缩策略对比：C、Codex、OpenCode

三种保留策略，六条链，闭卷与开卷两种条件。

| 策略 | 压缩后保留什么 | 来源 |
|---|---|---|
| **C** | 全部受保护的**用户与 assistant 原文** + 2K 确定性工具证据索引 + 近期尾部 + 由会话模型生成的**缓存友好粘性交接摘要** | 本仓库（运行时默认） |
| **Codex** | 全部用户消息（≤20 000 tokens）+ 全历史摘要；不含 assistant 正文、不含工具输出 | `openai/codex` @ `b13164d8`，`compact.rs::build_compacted_history` + `templates/compact/prompt.md` |
| **OpenCode** | 摘要 + 保留尾部（`min(15 000, max(2 000, usable/4))`） | `anomalyco/opencode` @ `e03db9bc`，`session/compaction.ts` |

Codex 与 OpenCode 是依据上述提交读出的选择规则所做的**复现实现**，并非分支。其提示词逐字转写，每个源文件的 git blob SHA 记录在 [abc_external_provenance.json](../scripts/abc_external_provenance.json)。

## C 的摘要如何生成，以及请求形状为什么重要

C 的投影由**生产 Rust 路径**生成（`agent/examples/abc_c3_probe.rs` → `prepare_evidence_with_summary`），因此其内容就是运行时实际提交的内容。摘要是**粘性**的——每一轮都接收上一轮摘要——所以事实在连续压缩中累积，而不是每次重写。

请求被刻意塑造成**可命中 provider 前缀缓存**的形状：

* 活动对话以**真实消息**发送，而非拍平成一个字符串；
* 指令**追加在最后**；
* 复用 agent 自己的 **system prompt 与工具定义**。

provider 按**请求前缀**缓存：复用会话已发送过的回合的请求几乎不计费，而重新拍平或重新包装同样内容的请求没有共享前缀、每次都按全量计费。在隔离 agent 上跑这条生产路径实测：会话增长到 **212 911 tokens** 后压缩，`cache_read = 212 548`——请求的 **99.8%** 由缓存提供，`cache_write = 360`（仅新追加的指令）。该请求冷启动约 ¥0.53，命中缓存后约 ¥0.003。

## 方法

* **链** —— 三条合成链（export、analysis、pipeline）＋三个真实会话，测量前**冻结**为不可变 JSON（`real-yt` 756、`real-visual` 685、`real-stream` 1582 条记录）。冻结是必要的：真实会话从 Agent 数据库实时读取，其中一条在早先几轮测量期间仍在写入，记录数在测量过程中增长。仓库中不出现任何会话标识，冻结副本存放在 git-ignored 的研究目录内。
* **边界** —— 每条链三个（约为历史的 40%、70%、100%），共 **18 份问卷**。
* **考卷** —— 值保留探测：取值来自 assistant 正文、用户回合与工具结果，另混入 8 个**未出现过的诱饵值**。模型标注哪些出现过；丢失了某个值的投影无法把它与诱饵区分。这是识别任务，不是自由回忆。
* **窗口** —— 128K，即 C 的收纳饱和点（见限制）。
* **成本** —— 采用 provider 自己上报的 `credit_cost`，逐次调用计费。

## 闭卷：各策略保住了什么

| 链 | C | Codex | OpenCode |
|---|---:|---:|---:|
| export（合成） | **8/16** | **8/16** | **8/16** |
| analysis（合成） | **8/16** | **8/16** | **8/16** |
| pipeline（合成） | **9/17** | **9/17** | **9/17** |
| real-yt | **35/44** | 31/44 | 24/44 |
| real-visual | **27/36** | **27/36** | 25/36 |
| real-stream | **39/49** | 36/49 | 15/49 |
| **合计** | **126/178（70.8%）** | 119/178（66.9%） | 89/178（50.0%） |

| 分组 | C | Codex | OpenCode |
|---|---:|---:|---:|
| **真实会话** | **101/129（78.3%）** | 94/129（72.9%） | 64/129（49.6%） |
| 合成链 | 25/49（51.0%） | 25/49（51.0%） | 25/49（51.0%） |

**所有策略在所有链上误报均为 0。** 差异来自召回，而非编造。

| 策略 | 投影中位数 |
|---|---:|
| C | 8 495 tokens |
| Codex | 1 223 tokens |
| OpenCode | 3 249 tokens |

解读：

* **C 在真实会话上领先，在合成链上与另两者持平。** 合成链上三者完全相同（25/49）——那些 fixture 把可答细节放在工具记录里，而三种规则都会以某种形式保留工具记录。只有在答案细节位于 agent 正文时各策略才分开，而真实提问正指向那里。
* **Codex 的投影很小、按 token 算高效，但这并不弥补。** 它保留的 token 比 C 少约 7 倍，在真实会话上低 5.4 分；投影小只有在它仍包含答案时才有意义。
* **OpenCode 最弱（真实会话比 C 低 28.7 分）。** 与其设计一致：摘要加一段短尾部，既无逐字原文也无证据索引。它在 `real-stream` 上的崩塌（15/49）是最清楚的例证。

## 开卷：为各策略加上它自己的查找接口

每个策略都用与其设计相符的查找接口重测，投影不变：

| 策略 | 接口 |
|---|---|
| C | 归档 CLI（`future session history search` / `get`） |
| Codex | window/item 接口（`history.search_contents` / `read_item`） |
| OpenCode | 文件系统（对物化工作树做 `glob` / `grep` / `read`） |

| 策略 | 闭卷 | 开卷 | 差值 | 每题平均查找次数 |
|---|---:|---:|---:|---:|
| **C** | 126/178 | **126/178** | **0** | 2.72 |
| **Codex** | 119/178 | **120/178** | **+1** | 3.28 |
| **OpenCode** | 89/178 | 88/178 | **−1** | 1.78 |

检索成本（逐次调用计费）：

| 策略 | 检索调用次数 | 合计 | 每次均价 |
|---|---:|---:|---:|
| C | 58 | ¥0.9232 | **¥0.0159** |
| Codex | 59 | ¥0.3079 | **¥0.0052** |
| OpenCode | 32 | ¥0.3493 | **¥0.0109** |

**检索在这里没有改变分数，两个方向都没有。** 三种策略与各自闭卷结果的差距都在 1 个字段以内。两个原因，都值得说明：

* **保留得多的策略没什么可查。** C 已经携带了保护原文、证据索引与摘要，它的查找多半只是确认已持有的内容。注意它的单次查找成本最高（¥0.0159），因为每次请求都携带最大的投影。
* **OpenCode 的恢复路径看不到被取代的状态。** 它的接口是文件系统，磁盘上只有每个文件的最新版本——因此被后续版本覆盖掉的值无论查多少次都取不回来。它的查找次数最少（1.78），收益为零。

这更正了本页早先的一个版本：那一版报告检索让 C **提升 10 分**、让 Codex **损失 20 分**。那些数字来自我为 C 的证据选择所写的 Python 近似，以及我自己发明的 5 次调用上限；换成真实代码路径且不设上限后，效果是中性的。**查找接口并不等于免费的准确率**——它是找回摘要与证据索引都未保留的具体值的手段，而本次考试中这三种投影丢的东西都还不足以让它发挥作用。

## 每次压缩的成本

在 driver 上测量，请求是**冷启动**的（driver 不会先把对话当作普通回合发送，因此没有热前缀）：

| 策略 | 摘要次数 | 平均成本 | 平均输入 tokens |
|---|---:|---:|---:|
| C | 15 | ¥0.1014 | 67 491 |
| Codex | 18 | ¥0.0286 | 7 079 |
| OpenCode | 19 | ¥0.0256 | 7 352 |

冷启动数字**低估了 C 的真实优势**：C 读取**整个活动对话**（平均 6.7 万 tokens，最高 12.8 万），而 Codex 与 OpenCode 只摘要一个有界切片（约 7 千）。冷启动时读全历史很贵；**热启动时它是三者中最便宜的**——产出这些 token 的回合早已为前缀付过费。上文 99.8% 的缓存命中把一次 21.3 万 tokens 的读取变成 ¥0.003，而一次 7 千 tokens 的**冷**摘要要 ¥0.0286。

真实会话的摘要总是热启动的，因为它所摘要的对话刚刚才被发送过。**因此 C 压缩的生产成本是缓存后的数字，而不是上表中的 ¥0.1014**——后者是 driver 造成的假象。

## 限制

* **Codex 与 OpenCode 是单点复现实现。** 其保留规则与提示词读自特定提交，上游后续改动会使数字失效。两者都按其**使用 API key 或第三方 OpenAI 兼容 provider 时可得**的配置建模。Codex 的第一方 `history`/`notes` 检索工具需要托管后端、付费 ChatGPT 套餐以及两个未开发阶段的功能开关，因此"Codex 配自有检索"这一臂**无法复现**；表里的 Codex 是它的本地兜底压缩路径。
* **考卷是识别任务，不是任务续做。** 它不衡量 agent 能否接着把活干完。
* **合成 fixture 偏重工具。** 它们奖励携带工具证据；策略之间真正分开是在真实会话上。
* **窗口敏感。** C 的保护原文预算随上下文窗口缩放，收纳率在 128K 饱和（实测：32K 时 65%、128K 时 79%、256K 与 1M 不变）。生产窗口来自模型注册表——`models/future.rs` 里的 `128000` 只是模型未声明时的兜底。
* **开卷数字使用有界预算**（每次探测最多返回 32KB、60 轮上限）。换预算会改变查找次数，但不会改变"本考卷上检索是中性的"这一结论。
* **检索取不回任何接口都未存储的东西。** OpenCode 的文件系统路径只能看到每个文件的最新版本，这是该接口的性质，而非调参问题。
