# 模型辅助的 UI 端到端测试：让模型选元素，而不是给坐标

一个原型：在真实桌面端渲染（headless Chrome + mock 数据）上，只用模型真正可靠的那种能力——
**在若干编号目标里做离散选择**。它从不产生坐标；几何来自 DOM，点击是 CDP 真实鼠标事件。

这是**写用例时的辅助**，不是 CI 的替代品，见文末「放在哪一层」。

## 一步的形状

```
CDP 枚举可交互元素                     （DOM → label + 包围盒）
        ↓  在截图上画红框和编号（Set-of-Mark）
模型只看编号 → {"id": N}
        ↓  执行器用 DOM 给的矩形中心做 Input.dispatchMouseEvent
重新截图 + 读 DOM 文本
        ↓  断言：点击前不在屏幕上的文本行 / 新增的 data-testid
```

模型不产生坐标，所以「点偏 3 个像素」这类失败不存在。剩下的每步只有一个问题：
*图里哪个元素能完成目标？*

## 在桌面端上的实测

被测对象：`scripts/screenshots/capture.py serve-desktop`（headless Chrome + mock 数据），
视口 1280×850，首屏 84 个可交互元素。3 轮 × 4 场景。

| 场景 | 目标 | 通过 | 平均决策耗时 |
|---|---|---|---|
| S1 | 打开模型选择 | 3/3 | 1.46 s |
| S2 | 打开技能列表 | 2/3 | 2.56 s |
| S3 | 打开定时任务 | 3/3 | 1.89 s |
| N1 | 打开打印机设置（不存在） | **3/3 正确拒绝** | 2.68 s |
| | **合计** | **11/12（92%）** | |

断言使用的证据——点击后新增的文本行：

- S2（通过）：`Skills` / `管理 Agent 可用的技能：安装、卸载与浏览技能市场。` / `已安装` / `全部`
- S3（通过）：`新建定时任务` / `每周进展周报` / `周一, 周五 10:00`

## 三条值得留下的发现

**1. 断言必须比对「新增」的文本，不能只查「包含关键词」。**
侧栏按钮本身就叫「模型」「技能」，所以 `text.includes('技能')` 在点击前就为真。
这个 harness 的第一版用的正是这种判断，报出 4/4 全绿——四个都是假绿。
断言必须比对点击前后的文本差异（或 `data-testid` 集合差异），再在差集里找关键词。

**2. 必须给模型一个明确的「拒绝」出口。**
system prompt 只允许「返回图上的数字」时，负场景里模型挑了「全部设备」——最像的那个。
加上「如果没有元素能完成目标，返回 id 0」之后，3/3 全部正确拒绝。
agent 能不能守住「目标不存在」，取决于你有没有给它这个选项。

**3. 剩下的失败是「选了近邻」，不是「选不出来」。**
S2 三轮错一次：把「定时任务」当成了「技能列表」。这两个按钮尺寸相同、垂直相邻——
和其他密集列表里见到的误差形态一致。低成本缓解：编号之前按 label 先粗筛候选，
或者把编号相对目标做得更大。

## 放在哪一层

`harness/` 已经拥有 video / console / network / IPC / database / perf 六个证据通道和脚本化断言。
这一层是**补充**：它回答「是哪个元素」，其余全部保持确定性。

推荐用法——**生成式 + 冻结**：模型只在写用例时出场一次，把它选中的元素固化成
`data-testid` 选择器，之后这条用例在 `harness/` 里像别的用例一样跑。
每步 1.5–2.7 s 的延迟、约 8% 的选错率，决定了它不能进每次 CI 的运行。

## 复现

```bash
python3 scripts/screenshots/capture.py serve-desktop --port 5399   # 桌面端渲染
FUTURE_API_KEY=... node harness/scripts/som-element-picker.mjs --url http://localhost:5399/shot/
```

`harness/scripts/som-element-picker.mjs` 是原型驱动：枚举元素、画编号、问模型、点击，
并打印点击前后的文本差异。它需要视觉模型端点和环境变量里的 API key；
它是写用例用的模板，不是 CI 调用的东西。

## 用视频模型再看一遍录屏

脚本化的断言只知道它编码过的东西。第二层负责「看录像」：
`harness/scripts/video-judge.mjs` 把流程视频交给支持视频输入的模型
（`qwen3.8-max`；目录里 DeepSeek 系只吃图，不吃视频），问它这次执行是否符合预期流程。

2026-11-06 在桌面端渲染上的实测（8 fps 录制，6–9 秒片段，单次判断 152–179 秒）：

- 干净的那次 → `pass`，并逐步复核（面板标题、5 个已安装技能与侧边栏徽标一致、定时任务列表）；
- 注入了三处异常的那次 → `fail`，三处全部点到了对应步骤：
  `加载失败：无法获取模型列表 (500)` 报错条、该报错条跨页面残留并遮挡内容、
  以及 `（此处应显示技能列表，但内容为空）` 与实际已渲染的列表自相矛盾。

耗时与成本决定了它不能按断言粒度跑：按每用例约 3 分钟预算，放在脚本化断言之后异步执行，
作为第二意见而不是闸门。
