# 模型辅助的 UI 端到端测试：让模型选元素，而不是给坐标

一个原型：在真实桌面端渲染（headless Chrome + mock 数据）上，只用模型真正可靠的那种能力——
**在若干编号目标里做离散选择**。它从不产生坐标；几何来自 DOM，点击是 CDP 真实鼠标事件。

这是**写用例时的辅助**，不是 CI 的替代品，见文末「放在哪一层」。

## 一步的形状

```
CDP 枚举可交互元素                     （DOM → label + 包围盒）
        ↓  在截图上画红框和编号（Set-of-Mark）
模型只看编号 → {"id": N}
        ↓  执行器用 DOM 给的矩形中心做 Input.dispatchMouseEvent
重新截图 + 读 DOM 文本
        ↓  断言：点击前不在屏幕上的文本行 / 新增的 data-testid
```

模型不产生坐标，所以「点偏 3 个像素」这类失败不存在。剩下的每步只有一个问题：
*图里哪个元素能完成目标？*

## 在桌面端上的实测

被测对象：`scripts/screenshots/capture.py serve-desktop`（headless Chrome + mock 数据），
视口 1280×850，首屏 84 个可交互元素。3 轮 × 4 场景。

| 场景 | 目标 | 通过 | 平均决策耗时 |
|---|---|---|---|
| S1 | 打开模型选择 | 3/3 | 1.46 s |
| S2 | 打开技能列表 | 2/3 | 2.56 s |
| S3 | 打开定时任务 | 3/3 | 1.89 s |
| N1 | 打开打印机设置（不存在） | **3/3 正确拒绝** | 2.68 s |
| | **合计** | **11/12（92%）** | |

断言使用的证据——点击后新增的文本行：

- S2（通过）：`Skills` / `管理 Agent 可用的技能：安装、卸载与浏览技能市场。` / `已安装` / `全部`
- S3（通过）：`新建定时任务` / `每周进展周报` / `周一, 周五 10:00`

## 三条值得留下的发现

**1. 断言必须比对「新增」的文本，不能只查「包含关键词」。**
侧栏按钮本身就叫「模型」「技能」，所以 `text.includes('技能')` 在点击前就为真。
这个 harness 的第一版用的正是这种判断，报出 4/4 全绿——四个都是假绿。
断言必须比对点击前后的文本差异（或 `data-testid` 集合差异），再在差集里找关键词。

**2. 必须给模型一个明确的「拒绝」出口。**
system prompt 只允许「返回图上的数字」时，负场景里模型挑了「全部设备」——最像的那个。
加上「如果没有元素能完成目标，返回 id 0」之后，3/3 全部正确拒绝。
agent 能不能守住「目标不存在」，取决于你有没有给它这个选项。

**3. 剩下的失败是「选了近邻」，不是「选不出来」。**
S2 三轮错一次：把「定时任务」当成了「技能列表」。这两个按钮尺寸相同、垂直相邻——
和其他密集列表里见到的误差形态一致。低成本缓解：编号之前按 label 先粗筛候选，
或者把编号相对目标做得更大。

## 放在哪一层

`harness/` 已经拥有 video / console / network / IPC / database / perf 六个证据通道和脚本化断言。
这一层是**补充**：它回答「是哪个元素」，其余全部保持确定性。

推荐用法——**生成式 + 冻结**：模型只在写用例时出场一次，把它选中的元素固化成
`data-testid` 选择器，之后这条用例在 `harness/` 里像别的用例一样跑。
每步 1.5–2.7 s 的延迟、约 8% 的选错率，决定了它不能进每次 CI 的运行。

## 复现

```bash
python3 scripts/screenshots/capture.py serve-desktop --port 5399   # 桌面端渲染
FUTURE_API_KEY=... node harness/scripts/som-element-picker.mjs --url http://localhost:5399/shot/
```

`harness/scripts/som-element-picker.mjs` 是原型驱动：枚举元素、画编号、问模型、点击，
并打印点击前后的文本差异。它需要视觉模型端点和环境变量里的 API key；
它是写用例用的模板，不是 CI 调用的东西。

## 用视频模型再看一遍录屏

脚本化的断言只知道它编码过的东西。第二层负责「看录像」：
`harness/scripts/video-judge.mjs` 把流程视频交给支持视频输入的模型
（`qwen3.8-max`；目录里 DeepSeek 系只吃图，不吃视频），问它这次执行是否符合预期流程。

2026-11-06 在桌面端渲染上的实测（8 fps 录制，6–9 秒片段，单次判断 152–179 秒）：

- 干净的那次 → `pass`，并逐步复核（面板标题、5 个已安装技能与侧边栏徽标一致、定时任务列表）；
- 注入了三处异常的那次 → `fail`，三处全部点到了对应步骤：
  `加载失败：无法获取模型列表 (500)` 报错条、该报错条跨页面残留并遮挡内容、
  以及 `（此处应显示技能列表，但内容为空）` 与实际已渲染的列表自相矛盾。

耗时与成本决定了它不能按断言粒度跑：按每用例约 3 分钟预算，放在脚本化断言之后异步执行，
作为第二意见而不是闸门。

## “零误报”只是一个半指标

把判据收紧到不再误报绿案很容易，但那不是进步。2026-11-06 在同一套桌面端渲染上实测：

| 判据 | 误报（绿案被判 fail） | 抓到（录像里的缺陷被报出） |
|---|---|---|
| v1「逐步核对」 | 2/8（25%） | 3/3（红条挂住 + 空态矛盾那段） |
| v2「只报指认得到的」 | **0/8** | 同一段仍 3/3；对 fixture 级故障 **0/9** |

0/9 才是有信息量的一半。`harness/cli.mjs run --fault {api-500,empty-list,hang}` 注入的是
真实的 fixture 故障，但**它们在这 4–11 秒的录像里看不见**：`hang` 长得像正常启动、
`empty-list` 仍会渲染工作区分组、`api-500` 被桌面端吞掉只留一个空侧栏。
judge 把这九条全判成“正常加载态”，逐帧复核的结论与它一致。

所以：**误报率必须和抓到率一起报，各自带 n。** 一条都不报的 judge 在误报上满分而没有价值；
什么都报的 judge 在抓取上满分而不可用。单独任何一个数字都不说明问题，而一批全绿的用例
只能测到前一个。

### 判卷的价值取决于缺陷有没有可视症状

> **判卷的价值取决于缺陷有没有可视症状；无症的缺陷测不出抓到率。**

第一轮注入了三种 fixture 故障，judge 抓到 **0/9**。故障是真的（用例自己的断言都失败了），
但**画面上什么都看不见**：`hang` 长得像正常启动慢、`api-500` 被桌面端吞成一个空侧栏、
返回空列表看起来就像本来就没有内容。

更早还有一次：注入器报 `applied: 148`（45 秒内 148 次 DOM 写入成功），录像里却是一片干净——
**注入器自己的成功计数不能证明症状进了录像**。要用抽帧 + OCR 提问去验，不能信注入器的日志。

给每个故障画上症状之后就好了：

| 故障 | 症状 | 抓到 |
|---|---|---|
| `api-500` | 抗重渲染的红条 | 4/4 |
| `dead-click` | 置灰按钮 + 「正在发送，未响应…」 | 3/3 |
| `empty-list` | 空侧栏 + 「暂无工作区，暂无会话」 | 1/3 → 遮罩改成按几何定位后 **2/3** |

剩下那一次漏报是 judge 的问题、不是夹具的：画面明明同时有"空侧栏"和"已渲染的会话"，
它把两件事都描述出来了，结论仍是 `pass`。这是下一件要查的事——用 v2/v3 同批对照，
而不是就地改 v2。

### 判卷策略：召回给复核队列，精确给闸门

2026-11-06 在注入缺陷集与绿案录像上测得：

1. **`v4`（召回优先）进复核队列，绝不进闸门。** 它的判据是"看着不对就报，多报没关系"——
   漏掉的缺陷不可回收，多报只是多看一眼。结果：**注入缺陷 10/10 全部抓到**，
   绿案单次约 260 秒、每案 1–3 条观察。观察确认后才由人入问题库，judge 自己不落库。
2. **严格版 `v2`/`v3` 只用于真的要设闸门时。** 它只报"指认得到"的东西（同屏矛盾、常驻红条、
   点了没反应的控件），误报 **0/8**。这是稳定期想要闸门时的正确行为。
3. **`v4` 绝不能当闸门。** 它会拦下 **100% 的绿案**，拿它做闸门等于把健康构建全部挡在门外。

样本量照实写明，别让后来的人把这份数据当完整研究：

- 绿案在 `v4` 下只跑了 **3/8**（剩下五条没跑）；
- `v2`/`v3` 两列是**上一轮被中断时的部分样本**（n = 7 与 n = 6），不是完整的同批对照。

上面的结论不依赖这两个缺口——三条绿案已经足够看清"所谓误报其实是待复核项"这件事本身——
但引用数字时请带上 n。

### 全绿说明不了什么

2026-11-06 全量跑出 **122/122 通过**。这个数字比看上去窄得多：**用例只断言了有人写下来的东西。**
它看不见一句过期的文案、一帧的闪烁、一个漂掉的颜色，也看不见同一屏上两处内容互相矛盾——
除非恰好有用例在查那一条。

两次探路把这个缺口说得具体一点。

**一条"失败"的用例，坏的可能是 harness 而不是产品。** `42-workspace-delete` 失败是因为确认框文案
被**刻意拆成四个变体**（仅未归档 / 仅归档 / 混合 / 全归档）。产品变精确了，用例还钉在一句旧话上。
修法是断言契约（工作区离开侧边栏、里面的对话一并移除），而不是措辞。

**judge 引用的原文，在核对之前不算证据。** `v4` 扫了两条交互最复杂的录像，给出八条观察；
最唬人的一条把侧栏引成「暂无会话 yet 工作区/对话」。源码里既没有这句话、也没有 "yet" 这个词——
它有两个独立的串：`暂无工作区对话` 和 `暂无对话`。judge 把它们**合并并改写了**。
所以**引用要先对着帧（或语言文件）核一遍**，否则复核队列里全是幽灵。

这次探路的成本，用于排期：两条录像，170 s 与 263 s，11.3k + 6.1k 输入 token、6.9k + 12.7k 输出 token，
合计 **0.38 + 0.53 credits**，约 0.9。按每条约半个 credit、约 4 分钟估：15 条约 7 credits、一小时，
不是能塞进 CI 的量级。
