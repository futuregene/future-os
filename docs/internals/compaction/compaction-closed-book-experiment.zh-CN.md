# 压缩策略：闭卷对比

六条冻结链上的五个保留策略，仅闭卷。

**命名。** 各臂按代码命名：`summarized` 是运行时默认（`summarized-evidence-v1`），`deterministic`
是同一投影但不调用摘要模型（`deterministic-evidence-v1`），`main` 是已发布分支实际部署的算法。

| 臂 | 保留什么 | 来源 |
|---|---|---|
| `summarized` | 全部受保护的**用户与 assistant 原文** + 2K 确定性工具证据索引 + 近期尾部 + 由会话模型生成的**缓存友好交接摘要** | 本仓库（运行时默认） |
| `deterministic` | 同一投影，不调用摘要模型 | 本仓库 |
| `main` | 递归模型摘要 + 受保护原文 + 近期尾部 | 本仓库，`origin/main` @ **`7e268efe`** |
| `codex` | 全部用户消息（≤20 000 tokens）+ 全历史摘要；不含 assistant 正文、不含工具输出 | `openai/codex` @ `b13164d8`，`compact.rs::build_compacted_history` + `templates/compact/prompt.md` |
| `opencode` | 摘要 + 保留尾部（`min(15 000, max(2 000, usable/4))`） | `anomalyco/opencode` @ `e03db9bc`，`session/compaction.ts` |

`main` 不是复现实现：[`released_probe.rs`](../../../scripts/compaction_experiment/released_probe.rs) 在
`origin/main` 的 detached worktree 中于上述 commit 构建，调用该 checkout 自己的入口与预算规则，因此这一列
是已发布的算法本身，不是它的移植。引用这些数字前请先跑 `git log -1 origin/main`；上游再有任何提交都会使
它们失效。

Codex 与 OpenCode 是依据上述提交读出的选择规则所做的**复现实现**，并非分支；提示词逐字转写，每个源文件的
git blob SHA 记录在 [provenance.json](../../../scripts/compaction_experiment/provenance.json)。

## 调用形状

每个 Rust 臂都按运行时的真实形状驱动，而不是模拟形状：

| | 取值 |
|---|---|
| 窗口 | 注册表声明的窗口，1 000 000 |
| 输出预留 | `effective_max_tokens`，384 000 |
| 请求预算 | `set_request_budget`，传入捕获的会话提示词与真实工具定义 |
| system prompt | 由 [`capture_shape.py`](../../../scripts/compaction_experiment/capture_shape.py) 捕获的真实生产提示词 |
| 触发 / 阶段 | Automatic + PreTurn，即生产的回合前压缩 |
| 节奏 | 累积到经济触发线 613 952 tokens |

该触发线是窗口的 80%，再被 `窗口 − 输出预留 − 余量` 夹住。它高于夹具里每一条真实会话边界，也高于三条
合成链中的两条，因此在生产触发条件下 Rust 臂经常根本不压缩——见[线上行为](#线上行为生产触发条件)。

## 压缩与压缩的可比

各臂并不共享触发条件。Codex 与 OpenCode 在每个评分边界无条件压缩，因此若把它们与经常跳过压缩的 Rust 臂
放在一起，测到的是触发条件而不是保留策略。下表因此强制每一臂在每个边界都压缩：Rust 臂使用 Manual，设计上
即绕过经济触发线。24 个边界全部满足，178 道题在同一条件下评分。

| 策略 | 召回 | 投影中位数 | 压缩率 | 压缩（未命中） | 压缩（计缓存） | 每轮 | 回本 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `summarized` | **147/178（83%）** | 12 113 tok | 5.7% | 7.98 | **0.53** | 0.000480 | 61 轮 |
| `deterministic` | 127/178（71%） | 9 945 tok | 4.7% | **0** | **0** | 0.000394 | 立即 |
| `opencode` | 83/178（47%） | 5 152 tok | 2.1% | 0.99 | 0.99 | 0.000204 | 110 轮 |
| `main` | 68/178（38%） | 3 418 tok | 1.3% | 0.83 | 0.83 | 0.000135 | 91 轮 |
| `codex` | 68/178（38%） | 1 706 tok | 0.6% | 7.64 | 0.42 | 0.000068 | 46 轮 |
| *（不压缩）* | — | 232 777 tok | — | — | — | 0.009219 | — |

成本列均为每次压缩的 CNY，`每轮` 是把这份投影在后续每一轮重发所花的钱，两者都在
[成本](#计入缓存后的成本)一节说明。`回本` 指持续节省需要多少轮才能抵回一次性压缩。

| 分组 | `summarized` | `deterministic` | `opencode` | `main` | `codex` |
|---|---:|---:|---:|---:|---:|
| 真实会话 | 98/129（76%） | **99/129（77%）** | 50/129（39%） | 39/129（30%） | 40/129（31%） |
| 合成链 | **49/49（100%）** | 28/49（57%） | 33/49（67%） | 29/49（59%） | 28/49（57%） |

| 链 | `summarized` | `deterministic` | `opencode` | `main` | `codex` |
|---|---:|---:|---:|---:|---:|
| export | 16/16 | 9/16 | 12/16 | 10/16 | 12/16 |
| analysis | 16/16 | 9/16 | 10/16 | 8/16 | 13/16 |
| pipeline | 17/17 | 10/17 | 11/17 | 11/17 | 3/17 |
| real-yt | 33/44 | 35/44 | 16/44 | 20/44 | 10/44 |
| real-visual | 27/36 | 27/36 | 24/36 | 14/36 | 21/36 |
| real-stream | 38/49 | 37/49 | 10/49 | 5/49 | 9/49 |

**没有任何策略在任何链上产生假阳性**：上表差异全部是召回，不是虚构。

解读：

* **线上算法的保留量约为运行时默认的三分之一。** 总体 38% 对 83%；真实会话上 30% 对 76%。这不是尺寸问题：
  Codex 只保留 0.6% 的历史、得分同样是 38%，而 `main` 的 1.3% 没有换来任何可测收益——两者都丢掉了问题真正
  指向的 assistant 正文。
* **压缩率不是目标。** 按投影大小排序，质量顺序正好倒过来：Codex 比 `summarized` 多压约 10 倍，答案差约
  45 个百分点。
* **两个当前策略的差别按工作负载而非总体得分。** 合成链上交接摘要起决定作用——49/49 对 57%；真实会话上
  两者持平（76% 对 77%）。合成链结构化且值密集；真实会话的细节分散在正文里，逐字保护本身已经带上了。

### 交接摘要的贡献

用不调用模型的包含性测量：统计每道题的应含值在哪个臂的投影文本中出现。

| | 出现的应含值 |
|---|---:|
| `deterministic` 投影 | 130/178 |
| `summarized` 投影 | **151/178** |

也就是说摘要带来了确定性投影没有携带的值，得分随之变化：127 对 147。这里要谨慎表述：这不是摘要本身的固有
属性，而是取决于投影必须丢弃多少——已经逐字保住全部材料的投影，从它的有损副本里得不到任何东西；而必须丢弃
一份 249K token 历史中大部分的投影，则能拿到摘要带过来的一切。

## 线上行为（生产触发条件）

同样六条链，但用生产触发线而非强制压缩。Rust 臂**只在 24 个边界中的 6 个**发生压缩；Codex 与 OpenCode
在这里没有自己的经济触发线，24 个边界全部压缩。

| 策略 | 召回 | 实际压缩 | 投影中位数 |
|---|---:|---:|---:|
| `summarized` | 149/178（84%） | 6/24 | 34 498 tok |
| `main` | 144/178（81%） | 6/24 | 4 911 tok |
| `deterministic` | 137/178（77%） | 6/24 | 32 419 tok |
| `codex` | 85/178（48%） | 24/24 | 1 644 tok |
| `opencode` | 81/178（46%） | 24/24 | 5 360 tok |

**这些质量数字不是保留策略的度量。** 24 个边界里有 18 个 Rust 臂发的是未压缩历史，所以这张表有一部分测的
是"没有压缩"而不是"压缩得更好"。列在这里只为记录线上行为：

* Rust 臂在全部 6 个真实会话边界都完全跳过压缩，因为触发线落在 1 000 000 token 窗口的 80%，而那些历史达不到；
* 因此线上每一轮都支付完整历史。同样 90 道题的评分开销是 2.67 CNY，而强制压缩那轮是 0.72 CNY。

## 计入缓存后的成本

这里有两种成本，混为一谈是最容易犯的错。**压缩成本**是产出这份投影的一次性花费；**每轮成本**是此后每一轮
重发它的花费。上表两者都给了，`deterministic` 也说明了为什么必须分开：它压缩时**不调用模型**，压缩成本恰好
是 0，而每轮成本不是 0——它的投影比原始历史小，但不是不存在。

费率取自模型注册表，按每 1M tokens 计：输入 **1.0**、输出 **4.0**、缓存读取 **0.02**、缓存写入 0。缓存读取
因此比新输入便宜 50 倍，这直接决定了哪个策略付得起。

一个请求**能否**用上缓存，取决于第 0 个 token 即 system prompt，因为前缀从头比对：

| 策略 | 共享会话前缀？ | 原因 |
|---|---|---|
| `summarized` | **是** | 传会话自己的 system prompt 与工具定义，活动对话以真实消息发送。生产路径实测缓存读取 **99.8%**（212 911 中命中 212 548） |
| Codex | 是 | 复用自己的基础指令，并把指令追加在最后 |
| `main` | **否** | 换成自己的 `SUMMARY_SYSTEM_PROMPT` 常量，第 0 个 token 与会话发过的任何请求都不同 |
| OpenCode | 否 | 发送专用的压缩 system prompt |

表中对能共享前缀的臂按**假设 98% 命中**计价（生产实测 99.8%，98% 为保守取值），不能的按全价。

解读：

* **缓存把成本排序翻了过来。** 未命中时 `summarized` 是这里最贵的，7.98 CNY 对线上算法的 0.83；计入缓存后
  它更便宜——0.53 对 0.83——而答案多 45 个百分点。
* **按每分召回的成本**（1 次压缩 + 100 轮）：`summarized` 0.0070 CNY、Codex 0.0112、线上算法 0.0220——线上
  算法**每单位召回贵约 3 倍**，正好与它未命中时的数字优势相反。`deterministic` 以 0.00055 低一个数量级，
  因为它根本不花钱。
* **压缩只有在几十轮之后才回本。** 每一臂的每轮成本比"不压缩"基准低 19–136 倍，但一次性成本仍需要
  46–110 轮才能收回（`summarized` 61 轮、线上 91 轮）。对短会话而言压缩是净支出；它买到的是召回与上下文
  余量，不是钱。
* **线上算法的节省是真的，但很小，而且来自另一个机制。** 它的摘要请求输入 token 少 11 倍
  （695 775 对 7 762 538），因为它**不重读原文**：第一个 checkpoint 之后它的 `covered_from` 是**上一个
  checkpoint 的 entry id**，每次只是把"上一份摘要 + 新增区间"向前折叠。这既解释了请求为何小，也解释了召回
  为何只有 38%——原文此后再不被查阅，而摘要在被递归地摘要。
* **私有 system prompt 在压缩上约损失 5 倍。** 同样按 98% 命中计价，`main` 自己的请求会是 0.16 CNY 而不是
  0.83。放弃缓存的是"自选一份摘要专用提示词"这个决定，而不是发送的文本量。

这些缓存数字是**建模值而非实测**：各轮自身的缓存计数被臂与运行顺序污染——各臂互相预热，且后一轮会复用前一轮
残留在 provider 缓存里的前缀——所以 98% 锚定在那一次生产实测上，不是本 harness。

## 方法

* **链** —— 三条合成链（`export`、`analysis`、`pipeline`）＋三个真实会话，测量前冻结为不可变 JSON
  （`real-yt` 756、`real-visual` 685、`real-stream` 1582 条记录）。冻结是必要的：真实会话从 Agent 数据库
  实时读取，其中一条在早先一轮测量期间仍在写入。
* **边界** —— 每条链三个评分点（约 40%、70%、100%），共 **18 份问卷**；另有节奏产生的压缩边界（强制那轮
  为 24 个）。
* **考卷** —— 精确值识别：取值来自 assistant 正文、用户回合与工具结果，另混入 8 个未出现过的诱饵值。丢失了
  某个值的投影无法把它与诱饵区分。
* **模型** —— 所有臂统一使用 `future/deepseek-flash`，生成参数一致。
* **评分** —— 每臂每边界一抽，不做显著性声明，无重复。
* **成本** —— 实际扣费来自 provider 上报的用量；缓存数字按上文说明、用注册表费率建模。

## 限制

* **考卷是识别而非任务续做。** 它不衡量智能体能否接着干活，而且它问的是精确值——这恰是逐字保留最擅长、
  摘要最不擅长的。
* **Codex 与 OpenCode 是单点复现实现。** 规则与提示词读自特定 commit，上游此后任何改动都会使数字失效。
  Codex 自带的 `history`/`notes` 检索工具需要其托管后端与特性开关，因此"带自有检索的 Codex"这一臂在此
  无法复现；这一列是它的本地兜底压缩。
* **合成夹具偏重工具**，因此有利于携带工具证据；真正区分各策略的是真实会话。
* **每格仅一抽。** 几个百分点的差异在这个样本量下无法分辨。
* **摘要的收益是有条件的。** 投影必须丢弃历史时它带来值，投影已逐字保住时它一个也带不来；本轮并未刻意变动
  这两个因素中的任何一个。

## 复现

本轮所需的一切都在 [scripts/compaction_experiment/](../../../scripts/compaction_experiment/)，命令见其
[README.md](../../../scripts/compaction_experiment/README.md)；设计取舍见
[CLOSED_BOOK_PROTOCOL.md](../../../scripts/compaction_experiment/CLOSED_BOOK_PROTOCOL.md)。

大致流程：

```sh
# 构建驱动（本 checkout，以及被测量的那个 checkout）
cargo build -p future-agent --example compaction_probe --example model_bridge
cp scripts/compaction_experiment/released_probe.rs <released-checkout>/agent/examples/
(cd <released-checkout> && cargo build -p future-agent --example released_probe)

# 从真实回合抓取调用形状（隔离 HOME、新端口、本地桩）
python3 scripts/compaction_experiment/capture_shape.py --binary target/debug/future \
    --out ~/compact-exp/shape

MAIN=$(git -C <released-checkout> rev-parse HEAD)
python3 scripts/compaction_experiment/run_closed_book.py \
    --output ~/compact-exp/v4-forced --force-compaction --budget 300 \
    --driver target/debug/examples/compaction_probe \
    --main-driver <released-checkout>/target/debug/examples/released_probe \
    --main-commit "$MAIN" \
    --bridge target/debug/examples/model_bridge --shape ~/compact-exp/shape
```

上面的 `--force-compaction` 是公平模式；去掉它即得线上行为表，但那次要另给一个 `--output`。
`--report-only` 可从已有运行重新生成 `report.json` 而不调用模型，因此表格可以零成本重建。

输入、账本与结果存放在任何仓库之外，因为它们包含真实会话数据：合成链可由 `freeze_sessions.py` 的种子化
生成器逐字节重建，真实会话链则完全无法公开。脚本在缺少必需输入时会直接报错而不是跳过，因此不会有部分运行被
误当成完整运行。第三方若要复现真实会话那一半，需要换用自己的会话；绝对值会不同，比较结论应当成立。

引用任何数字之前，先跑 `verify_request_shape.py`：它不需要模型，检查考试是否仍在发送生产的提示词与工具。
