# 压缩策略：开卷实验

检索对摘要压缩策略有帮助吗？单臂 `summarized`，跑闭卷那套链：压缩之后，如果模型能搜索原始历史，
它能否找回投影丢掉的东西？

**答案：靠它自己不行。** 三个"检索可选"的提示词变体，没有一次发生过检索；唯一产生提升的配置要求模型必须核对——而生产环境并不存在这种要求。因此**召回指引已从运行时删除，检索 CLI 保留**。

本页记录几轮实验，包括失败的那些。

## 测量装置

请求形状取自 Rust 代码而不是转写（`production_shape.RequestShape` → `compaction_probe --print-request-shape`）：

| | 取值 |
|---|---|
| system prompt | 会话自己的，逐字节相同 |
| 工具 | `coding_tools()`——`read`、`write`、`edit`、`shell` |
| 检索入口 | 普通 shell 工具背后的 `future session history search` / `get` |
| 被测归档 | 与闭卷臂评分所用的同一批记录，放在隔离的 Agent 数据库里 |
| 工具执行 | 生产 handler，经 `production_tool_executor` |
| 模型 | `future/deepseek-flash`，生成参数与闭卷一致 |
| 评分 | `realistic_exam.score`，与闭卷完全相同 |

每次工具调用都经过生产代码。harness 只额外加了一件事：`allowed_roots` 边界——因为生产的文件工具对绝对路径原样接受，否则会伸到案例之外（见[隔离](#隔离)）。

## 各轮实验

每次 18 个案例。"工具调用"指真正到达 handler 的执行次数。

| # | 改了什么 | 设计 | 召回 | 工具调用 |
|---|---|---|---:|---:|
| — | *（闭卷基线，冻结）* | 无工具 | 147/178 (82.6%) | 0 |
| 1 | 生产 prompt + 生产工具，别无其他 | 自主 | 148/178 (83.1%) | **0** |
| 2 | + 加强生产自己的召回指引 | 自主 | 149/178 (83.7%) | **0** |
| 3 | + 考卷措辞不再把投影称作"the record" | 自主 | 145/178 (81.5%) | **0** |
| 4 | 用第 3 轮措辞重测闭卷 | 无工具 | 147/178 (82.6%) | 0 |
| 5 | + 明确要求核对，并强制首次调用 | 要求核对 | **166/178 (93.3%)** | **100** |

解读：

* **第 1–3 轮是同一个结果重复三次。** 工具调用都是零，召回在 145–149 之间的浮动是 178 个值上的单次翻转发声：这些运行与闭卷基线的差别只在于**模型碰巧报了哪些投影里已有的值**。三轮都没有发生检索，因此没有新增任何东西。
* **第 4 轮是第 3 轮的对照。** 如果改措辞真的影响了结果，闭卷臂应当同步变化；它没有（两版都是 147），所以第 3 轮的 −2 是噪声，而不是模型变差。
* **第 5 轮是上界，不是结果。** 它是同一模型在被要求核对、并被强制调用一次时的表现。生产环境没有这种指令，因此这个分数不可达。

### 这些漏报是怎么发生的

对全部 178 个受检值分类：是否在投影里、模型是否报告、检索 query 是否包含过它。

| | 闭卷 | 第 1–3 轮 | 第 5 轮 |
|---|---:|---:|---:|
| 报告了，且就在投影里 | 147 | 148–149 | 146 |
| 报告了，投影里没有（**靠检索**） | 0 | 0 | **20** |
| 在投影里，但没报告 | 4 | 2–5 | 5 |
| 不在投影里，搜过，仍漏 | 0 | 0 | 3 |
| 不在投影里，**从没搜过** | **27** | **27** | 4 |

那个 **27 是恒定的**。这些值就在归档里，而模型从未去看：要求核对那一轮通过检索把 28 个中的 20 个找了回来。所以缺口是**行为上的，不是能力上的**——没有丢什么，只是从没去找。

这也就解释了为什么 prompt 侧的改动不可能奏效。第 1–3 轮各自用不同方式说"你可以去看"；模型每次都直接依据投影作答，代价是漏掉本可确认的值。第 5 轮的区别不在于**怎么描述**检索，而在于它是**必须做的**。

### 具体改了什么

第 2 轮改写了生产自己的指引（`history_recall.rs`），以"可见上下文中没有，并不等于事情没发生过"开头，并把定向检索变成预期的默认行为，同时保留全部范围与安全规则。第 3 轮不动提示词，改考卷问题——原措辞一边告诉模型"上文**就是**那次会话的记录"，一边指引里写着"partial projection, not the complete record"，并且只问"**在那次对话中**出现过的值"。两者都已回退；见[结论](#结论)。

## 成本

按 harness 记录，单位 CNY：

| 运行 | 调用数 | 计费 |
|---|---:|---:|
| 第 1 轮 | 18 | 0.3265 |
| 第 2 轮 | 18 | 0.3278 |
| 第 5 轮 | 98 | 0.1780 |
| 第 4 轮（闭卷重测） | 18 | 0.0177 |

**这些数字彼此不自洽，不应作定量使用。** 第 5 轮的调用数是第 1 轮的 5 倍，计费却不到其一半，隐含单价低约 11 倍。provider 报的是每次调用的 credit cost，而各轮自己的缓存计数始终读为零，所以差异无法用本 harness 测到的任何东西解释——最可能的原因是 provider 侧对共享前缀做了跨轮缓存，而不是各臂本身的什么属性。把这些数字理解为"每个 18 案例的臂不到零点几元"即可，仅此而已。

## 隔离

生产的 shell 工具由 OS 沙箱约束，但**并未被约束在案例之内**：模型对工作区之外的路径执行了 `ls`/`grep`。

| 观察 | 次数 |
|---|---:|
| 指向案例之外路径的 shell 调用 | 18 |
| ……其中从操作者文件系统返回了非平凡输出的 | 15 |
| 被 harness `allowed_roots` 边界拒绝的调用（一次 `read`） | 1 |
| 触发 120 秒 shell 超时的调用 | 1 |

这些都没有进入答案——每个被找回的值都归因于 `future session history` 查询，而不是宿主文件——但有两点结论。**能读宿主机的重放会被宿主污染**；而一个要求真实会话数据保持私密的实验，不能只依赖工具层。协议里原有的"不构成全局读取隔离保证"这句提醒，现在是一个实测事实。

## 限制

* **只有单臂。** 只跑了 `summarized`，其他策略未覆盖。
* **每案例仅一抽。** 18 个案例、178 个值；几个百分点就是一次翻转，低于这个量级的差异无法分辨。
* **考卷是识别任务。** 它问的是精确值，而这恰是逐字保留最擅长的。换成任务形态的考卷，行为可能不同。
* **要求核对那一轮是上界。** 它衡量的是"能检索到什么"，不是"会话会做什么"。
* **证明了可检索，未做优化。** 第 5 轮发了 100 次调用并触及输出预算；没有尝试寻找更好的查询策略。

## 结论

召回指引已从运行时删除（`agent/src/agent/history_recall.rs` 删除、调用点简化）。理由属于这个特性本身而非本次实验：那段指引描述的是一项模型**已经具备**的能力，而把能力描述得更强硬，并不会让模型去用它。三个变体、54 个案例、零行为变化。

检索 CLI 保留——`future session history search` / `get`、两个 RPC 命令，以及 journal 的 entry 引用。被移除的只是运行时的**宣传**。

有一个值得记下、且算是改进的后果：会话的 system prompt 不再因 checkpoint 提交而变化。它原先会追加那段指引，导致请求预算必须预先预留这部分增长，摘要请求必须逐字复现它，否则就丢掉 provider 的前缀。两个问题现在都消失了，并且有测试断言"提示词跨 checkpoint 恒定"，而不是靠人工保持两处调用点同步。

这些数字指向的下一步，是任何**实际去做**而不是**描述**的做法：对最新用户回合做确定性预检索、在 checkpoint 之后强制首次调用，或者扩大投影自身的保留范围。两轮提示词重写已足以说明，措辞不是杠杆。

## 复现

全部内容在 [scripts/compaction_experiment/](../../../scripts/compaction_experiment/)：命令见其
[README.md](../../../scripts/compaction_experiment/README.md)，设计（含哪些 flag 会改变问题本身）见
[OPEN_BOOK_PROTOCOL.md](../../../scripts/compaction_experiment/OPEN_BOOK_PROTOCOL.md)。

```sh
cargo build -p future-agent --example compaction_probe --example production_tool_executor \
                          --example model_bridge
cargo build -p future-cli --bin future

# 先用零模型调用验证整条链路，再正式跑
python3 scripts/compaction_experiment/run_open_book.py \
    --closed ~/compact-exp/v4-forced --arm summarized --output ~/compact-exp/open-summarized \
    --future target/debug/future \
    --executor   target/debug/examples/production_tool_executor \
    --driver     target/debug/examples/compaction_probe \
    --shape-probe target/debug/examples/compaction_probe \
    --base-prompt ~/compact-exp/shape/system-prompt.txt \
    --bridge target/debug/examples/model_bridge \
    --smoke --only export
```

正式跑时去掉 `--smoke`。各轮只差 flag，因此是同一个命令：

| 轮次 | flag |
|---|---|
| 1 | *（无）* |
| 2 | *（无）*——当时把 `agent/src/agent/history_recall.rs` 里的指引加强，后已回退 |
| 3 | `--exam-wording v2` |
| 4 | `--exam-wording v2 --closed-reprobe` |
| 5 | `--require-retrieval` |

中断是安全的：已完成的案例会保留并在重启时跳过。若某次调用在中断时正处于进行中，
`--retry-unsettled` 是显式的逃生口。

引用任何数字之前：先跑 `verify_request_shape.py`（不需要模型），它检查提示词就是会话自己的、未被修改，
工具定义与检索 CLI 完整；再用 `--smoke` 对一条链做端到端验证。

冻结输入与逐案例结果留在 `~/compact-exp`（任何仓库之外），因为真实会话链是私有的。第三方若要复现那一半，
需要换用自己的会话。
