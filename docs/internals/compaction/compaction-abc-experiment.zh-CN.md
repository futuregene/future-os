# 压缩策略对比

六条冻结链上的五个保留策略，闭卷。四个按生产调用形状实测；下文各表是较早的一次等尺寸对比。

**命名。** 各臂按代码命名：`summarized` 是运行时默认（`summarized-evidence-v1`），`deterministic` 是同一投影但不调用摘要模型（`deterministic-evidence-v1`）。本文较早的章节把它们写作 **C3** 与 **C**，是同一个策略的两个称呼。

| 策略 | 压缩后保留什么 | 来源 |
|---|---|---|
| **`summarized`** | 全部受保护的**用户与 assistant 原文** + 2K 确定性工具证据索引 + 近期尾部 + 由会话模型生成的**缓存友好交接摘要** | 本仓库（运行时默认） |
| **`deterministic`** | 同一投影，不调用摘要模型 | 本仓库 |
| **`main`** | `origin/main` 线上部署的算法：递归模型摘要 + 受保护原文 + 近期尾部 | 本仓库已发布分支 |
| **Codex** | 全部用户消息（≤20 000 tokens）+ 全历史摘要；不含 assistant 正文、不含工具输出 | `openai/codex` @ `b13164d8`，`compact.rs::build_compacted_history` + `templates/compact/prompt.md` |
| **OpenCode** | 摘要 + 保留尾部（`min(15 000, max(2 000, usable/4))`） | `anomalyco/opencode` @ `e03db9bc`，`session/compaction.ts` |

Codex 与 OpenCode 是依据上述提交读出的选择规则所做的**复现实现**，并非分支。其提示词逐字转写，每个源文件的 git blob SHA 记录在 [abc_external_provenance.json](../../../scripts/abc_external_provenance.json)。

**本文报告两种形状，它们回答不同的问题。** 后面的生产形状实测让每个 Rust 臂走运行时的真实调用形状（注册表窗口、模型输出预留、真实请求预算、生产触发条件与阶段），因此它的数字就是生产计算的数字。较早各表用**模拟 128K 窗口、无预算**测得，是等尺寸的保留规则对比。两种形状对缓存、对线上策略、对摘要价值的结论都不同，下文每一节都会说明自己用的是哪种形状。

## 生产形状的实测，以及线上策略本身

下文各表是用**模拟的 128K 窗口、无输出预留、无请求预算**测得的——那是一次等尺寸的保留策略对比，不是生产实际计算的数字。后续一轮用运行时真正的调用形状驱动同样的策略（注册表窗口、`effective_max_tokens`、带捕获的会话提示词与真实工具定义的 `set_request_budget`、生产触发条件与阶段），并把**线上算法**作为第五臂加入。其协议见 [PRODUCTION_SHAPE_PROTOCOL.md](../../../scripts/abc_experiment/PRODUCTION_SHAPE_PROTOCOL.md)，以下是它的结果。

本机模型（声明窗口 1 000 000、输出预留 384 000）下经济触发线为 **613 952** tokens：窗口的 80%，再被 `窗口 − 输出预留 − 余量` 夹住。这高于夹具里**每一个**真实会话边界，所以在生产触发条件下，Rust 两策略经常根本不压缩。把它们与无条件压缩的臂放在同一张表里，测到的是触发条件而不是保留策略。因此两种视图都给，且只有第一种是同等条件对比。

**压缩之后 vs 压缩之后**（强制每一臂在每个边界都压缩，24 个边界，178 道题）：

| 策略 | 召回 | 投影中位数 | 压缩率 | 压缩成本 |
|---|---:|---:|---:|---:|
| `summarized`（运行时默认） | **147/178（83%）** | 12 113 tok | 5.7% | 7.14 CNY |
| `deterministic` | 127/178（71%） | 9 945 tok | 4.7% | **0** |
| OpenCode | 83/178（47%） | 5 152 tok | 2.1% | 0.25 CNY |
| **线上（`main`）** | 68/178（38%） | 3 418 tok | 1.3% | 0.81 CNY |
| Codex | 68/178（38%） | 1 706 tok | 0.6% | 6.29 CNY |

| 分组 | `summarized` | `deterministic` | 线上 | Codex | OpenCode |
|---|---:|---:|---:|---:|---:|
| 真实会话 | 98/129（76%） | 99/129（77%） | 39/129（30%） | 40/129（31%） | 50/129（39%） |
| 合成链 | **49/49（100%）** | 28/49（57%） | 29/49（59%） | 28/49（57%） | 33/49（67%） |

解读：

* **线上算法丢掉了四分之三的真实会话答案。** 真实会话仅 30%，而替换它的两个策略是 76–77%。差距不在尺寸：Codex 只保留 0.6% 的历史、拿到同样的 38%；而 `main` 的 1.3% 没有换来任何可测量的收益——两者都丢掉了问题真正指向的 assistant 正文。
* **交接摘要在本考卷上值它的成本，但只在这里值。** 合成链满分 49/49，而不调用模型的投影是 57%；真实会话上两者持平（76% vs 77%）。摘要靠结构化链回本，其 7.14 CNY 与 Codex 的 6.29 CNY 接近而效果远好；不调用模型的策略则以零成本拿到 71%。
* **压缩率不是目标。** 按投影大小排序，质量顺序正好倒过来：Codex 比 `summarized` 多压约 10 倍，答案差约 45 个百分点。比值只有在剩下内容仍含答案时才有意义。
* **成本取决于输入大小，不是输出大小。** `summarized` 与 Codex 的压缩花费几乎相同（7.14 vs 6.29 CNY），尽管投影相差约 7 倍——因为两者都要摘要同一份完整历史。更小的投影买到的是**后续每一轮**的成本。

**线上行为**（生产触发条件；Rust 两臂只在 24 个边界中的 6 个发生了压缩，Codex/OpenCode 则是 24/24）。这些质量数字**不是**保留策略的度量——24 个边界里有 18 个发的是未压缩历史——列在这里只为记录线上行为：

| 策略 | 召回 | 实际压缩 | 压缩时的投影中位数 | 压缩成本 |
|---|---:|---:|---:|---:|
| `summarized` | 149/178（84%） | 6/24 | 34 498 tok | 0.13 CNY |
| `main` | 144/178（81%） | 6/24 | 4 911 tok | 0.03 CNY |
| `deterministic` | 137/178（77%） | 6/24 | 32 418 tok | 0 |
| Codex | 85/178（48%） | 24/24 | 1 644 tok | 6.50 CNY |
| OpenCode | 81/178（46%） | 24/24 | 5 360 tok | 0.44 CNY |

线上在全部 6 个真实会话边界都跳过了压缩，直接原因就是触发线落在 1 000 000 窗口的 80%。它的评分成本也相应更高（同样 90 道题 2.67 CNY vs 0.72 CNY），因为每次探测都带上完整历史——上面的投影大小是**每轮重复发生**的成本，不是一次性成本。

### 计入缓存后的成本

上面的压缩成本列是**未命中缓存**的价格：账本上实际扣除的金额。生产不会付这个价，因为复用了会话自己的 system prompt、工具定义与消息的摘要请求会由 provider 的前缀缓存提供。本机模型一次缓存读取是 **0.02 CNY / 1M tokens，而新输入是 1.0**——便宜 50 倍——所以缓存直接决定了哪个策略付得起。

策略**能否**共享该前缀，是它构造出的请求的性质；前缀从第 0 个 token 开始比对，所以只由 system prompt 决定：

| 策略 | 共享会话前缀？ | 原因 |
|---|---|---|
| `summarized` | **是** | 传会话自己的 system prompt 与工具定义，活动对话以真实消息发送。生产实测缓存读取 **99.8%**（212 911 个 token 中 212 548 命中） |
| Codex | 是 | 复用它自己的基础指令并把指令追加在最后；在它自己的部署里那就是会话的 system prompt |
| `main` | **否** | 换成自己的 `SUMMARY_SYSTEM_PROMPT` 常量，第 0 个 token 与会话发过的任何请求都不同 |
| OpenCode | 否 | 发送专用的压缩 system prompt |

下表把每一臂的实际调用按注册表费率重算：能共享前缀的策略按**假设 98% 命中**（生产实测是 99.8%，98% 为保守取值），不能的按全价。每轮成本指压缩后的投影在后续每一轮重发所花的钱（同样按缓存计价），这才是更小投影真正买到的东西。

这里有两种不同的成本，混在一起是最容易犯的错。**压缩成本**是“产出这份投影”的一次性花费；**每轮成本**是此后每一轮重发该投影的花费。不调用模型的策略第一项**恰好为零**，第二项仍然非零——它的投影比原始历史小，但不是不存在：

* 这些边界上的历史中位数是 **249 142 tokens**，按缓存计价每轮 0.009866 CNY。上表每一臂的每轮数字都是相对这个基准的，这个差额就是“压缩本身”持续产生的价值。
* `deterministic` 压缩时**不调用模型**，所以它的压缩成本是 **0**——不是“很小”，也不是“未测量”。它的 0.04 CNY 全部是 100 轮 × 重发那份 10 233-token 投影的 0.000406 CNY。

| 策略 | 召回 | 投影 | 压缩（未命中） | 共享前缀 | 压缩（计缓存） | 每轮 | 100 轮 | 回本所需轮数 |
|---|---:|---:|---:|:--:|---:|---:|---:|---:|
| `summarized` | **83%** | 12 503 tok | 7.98 | 是 | **0.53** | 0.000496 | 0.0496 | 56 轮 |
| `deterministic` | 71% | 10 233 tok | **0** | — | **0** | 0.000406 | 0.0406 | 立即 |
| Codex | 38% | 1 821 tok | 7.64 | 是 | 0.42 | 0.000073 | 0.0073 | 43 轮 |
| OpenCode | 47% | 5 372 tok | 0.99 | 否 | 0.99 | 0.000213 | 0.0213 | 103 轮 |
| **线上（`main`）** | 38% | 4 027 tok | 0.83 | 否 | 0.83 | 0.000160 | 0.0160 | 85 轮 |
| *（不压缩）* | — | 249 142 tok | — | — | — | 0.009866 | 0.9866 | — |

解读：

* **缓存把成本排序翻了过来。** 未命中时 `summarized` 是全场最贵的（7.98 CNY）；计入缓存后它比线上算法更便宜（0.53 vs 0.83）——而答案多出 45 个百分点。这不是夹具的巧合：98% 的输入享受 50 倍价差，结果就应该是这个。
* **压缩会回本，但需要几十轮。** 每一臂的每轮成本都比“不压缩”基准低 20–135 倍，但一次性压缩成本足够大，需要 **43–103 轮**才能把它省回来（`summarized` 56 轮、线上 85 轮、Codex 43 轮）。对短会话而言，压缩是净**支出**——它买到的是召回和上下文占用，不是钱。不要把这个列读成“从第二轮起就更便宜”。
* **按“每分召回的成本”算**（1 次压缩 + 100 轮）：`summarized` 0.0070 CNY、Codex 0.0112、线上算法 0.0221——**线上算法每单位召回贵 3 倍**，正好与它未命中时的数字优势相反。
* **线上算法的节省是真的，但很小，而且来自另一个机制。** 它的摘要请求输入 token 少 11 倍（695 775 vs 7 762 538），因为它**不重读原文**：第一个 checkpoint 之后它的 `covered_from` 是**上一个 checkpoint 的 entry id**，每次只是把“上一份摘要 + 新增区间”向前折叠。这既解释了它的请求为何小，也解释了它的召回为何只有 38%——原文此后再不被查阅，而摘要在被递归地摘要。`summarized` 每次都从 journal 重新覆盖整个区间，所以请求大；缓存是让它付得起的原因。
* **私有 system prompt 在压缩上约损失 5 倍。** 同样按 98% 命中计价，`main` 自己的请求会是 0.16 CNY 而不是 0.83——差额全在于它的第一个 token 与会话发过的任何东西都不匹配。放弃缓存的是“自选一份摘要专用提示词”这个决定，而不是发送的文本量。
* **`deterministic` 每分成本低一个数量级**（0.0006 vs 0.0070），因为它根本不花钱，而且仍能拿到 71%。交接摘要每分召回的成本约为不摘要的 12 倍（0.0070 vs 0.00057）——它是质量采购，不是效率优化。

这些是**建模**出来的缓存数字，不是实测：各轮自身的缓存计数被臂与运行顺序污染（见 PRODUCTION_SHAPE_PROTOCOL.md），而 98% 锚定在那一次生产实测上，不是本 harness。

## 摘要如何生成

`summarized` 的投影由**生产 Rust 路径**生成，它跑的**选择逻辑**就是生产的那一个。投影内容只是该函数在冻结记录上的输出，**不等于生产 checkpoint 的字节**：driver 从简化导出重建消息。机制见[策略说明](compaction.zh-CN.md)。

**下文 128K 窗口的各表不复现生产前缀。** 它们通过 `--system-prompt-file` 供应 Codex 的基础指令、传空工具列表，使 `summarized` 与 Codex 两臂共用同一前缀、只在保留内容上不同。由此产生两个后果，都不得当作生产路径的性质：

* 那些运行记录的 stage-0 高命中率（99%+）是 **Codex 臂替 `summarized` 垫好了前缀**，不是它自己挣来的——两臂在同一 block 内先后运行；后续 stage 只有约 10%，来自相邻压缩共享的头部；
* 替换 prompt、去掉工具定义、或在 system prompt 里多一行，在已预热前缀上实测都是 **0%**，所以那轮实验无论正反都不能给生产成本定界。

本文顶部的生产形状实测确实传入了会话的提示词与工具定义，因此其摘要请求具备生产前缀；但冻结会话自己的提示词是按回合从其工作目录重建的、不在 journal 里，所以那是一份真实捕获的生产提示词在代位。它的缓存计数同样不可比：各臂在同一 block 内互相预热。**这就是上方的成本表用建模值而非实测值的原因。**

## 方法（下文 128K 各节）

* **链** —— 三条合成链（export、analysis、pipeline）＋三个真实会话，测量前**冻结**为不可变 JSON（`real-yt` 756、`real-visual` 685、`real-stream` 1582 条记录）。冻结是必要的：真实会话从 Agent 数据库实时读取，其中一条在早先几轮测量期间仍在写入，记录数在测量过程中增长。仓库中不出现任何会话标识，冻结副本存放在 git-ignored 的研究目录内。
* **边界** —— 每条链三个（约为历史的 40%、70%、100%），共 **18 份问卷**。
* **考卷** —— 值保留探测：取值来自 assistant 正文、用户回合与工具结果，另混入 8 个**未出现过的诱饵值**。模型标注哪些出现过；丢失了某个值的投影无法把它与诱饵区分。这是识别任务，不是自由回忆。
* **窗口** —— 128K，即 `summarized` 的收纳饱和点（见限制）。生产形状实测改用注册表声明的 1 000 000。
* **成本** —— 采用 provider 自己上报的 `credit_cost`，逐次调用计费。这些是**未命中缓存**的数字；生产形状实测另行对缓存计价。

## 开卷：为各策略加上它自己的查找接口

每个策略都用与其设计相符的查找接口重测，投影不变：

| 策略 | 接口 | 读的是什么 |
|---|---|---|
| C3 | 归档 CLI（`future session history search` / `get`） | 会话归档 |
| Codex | window/item 接口（`history.search_contents` / `read_item`） | 会话归档，按窗口分组 |
| OpenCode | 文件系统（`glob` / `grep` / `read`） | 物化出的工作树 |

| 策略 | 闭卷 | 开卷 | 差值 | 平均查找次数 | 读取数据量 |
|---|---:|---:|---:|---:|---:|
| **C3** | 129/178 | **168/178（94.4%）** | **+39** | 2.67 | 0.20 MB |
| **Codex** | 119/178 | **170/178（95.5%）** | **+51** | 6.28 | 2.66 MB |
| **OpenCode** | 89/178 | **117/178（65.7%）** | **+28** | 4.33 | 0.54 MB |

按负载拆分：

| 负载 | C 闭卷 → 开卷 | Codex 闭卷 → 开卷 | OpenCode 闭卷 → 开卷 |
|---|---|---|---|
| 真实会话 | 101/129 → **119/129** | 94/129 → **126/129** | 64/129 → **85/129** |
| 合成链 | 28/49 → **49/49** | 25/49 → **44/49** | 25/49 → **32/49** |

检索成本（逐次调用计费）：

| 策略 | 检索调用次数 | 合计 | 每次均价 |
|---|---:|---:|---:|
| C3 | 48 | ¥0.7113 | **¥0.0148** |
| Codex | 114 | ¥3.3083 | **¥0.0290** |
| OpenCode | 78 | ¥1.2088 | **¥0.0155** |

**检索完全改变了结果，也改变了排序。** 闭卷时 C 领先 10 个字段；开卷时两者相差不到 2 个（168 对 170），因为两者都能取回归档中的大部分内容。三点发现：

1. **增益与投影保留了多少成反比。** C 起点最高、增益最少（+39）；Codex 起点较低、增益最多（+51）；OpenCode 增益 +28，但最终仍明显落后。换言之，**闭卷测的是策略保住了什么，开卷测的是它能找到什么——而只有前者能区分这几种设计。**
2. **C3 用一小部分代价达成结果。** 它花 2.67 次查找、读 0.20 MB，而 Codex 花 6.28 次、读 2.66 MB——**用少 13 倍的数据达到相当的水平**。C3 的证据索引直接指向值得读的记录，因此它的查找是有的放矢而非广撒网。在合成链上，C3 是唯一达到满分的臂（49/49）。
3. **天花板由归档决定，而非投影。** 凡能读取归档的策略都会向其收敛；剩下的差异在于各自抵达的效率。唯一的例外是 OpenCode（65.7%）：它的接口是文件系统，而文件当前状态不包含被后续版本覆盖掉的值——因此归档的一部分通过该接口**结构上不可达**，无论查多少次。

> **更正。** 本页早先的版本报告检索只值 +1 到 +10 个字段，并据此得出"检索是中性的"结论。那次测量有三处缺陷：CLI 回落到一个早于该历史命令的 agent 构建，导致每次查找都返回 `unknown command` 与 0 字节；Codex 臂被传入空的窗口列表、OpenCode 臂根本没有被分派；合成链传入的是空会话 ID。三处修好后，效果显著且对每个策略方向一致。

## C3 的检索需要调整吗，Codex 的检索更好吗

开卷结果引出的两个问题，都能从已存的运行数据回答。

### Codex 的检索并不更好——只是用得更频繁

| 策略 | 追回字段 | 查找次数 | 读取量 | 每字段 KB | 每次查找字段 |
|---|---:|---:|---:|---:|---:|
| **C3** | 39 | 48 | 0.20 MB | **4.9** | **0.81** |
| Codex | 51 | 113 | 2.66 MB | 50.9 | 0.45 |

C3 每读 4.9 KB 就追回一个字段；Codex 需要 50.9 KB，且每字段的查找次数是两倍。按此衡量，**C3 的接口在字节效率上约高出十倍**——这正是指向"值得读的记录"的证据索引应有的效果。

Codex 那 2 分的领先来自一个**行为差异**，而非更好的工具。有 3 个探针 C **完全没有发起工具调用**——直接凭投影作答——并恰好丢掉了它投影里缺失的那些值：

| 探针 | C 闭卷 | C 开卷 | C 查找 | Codex 开卷 | Codex 查找 |
|---|---:|---:|---:|---:|---:|
| real-visual s2 | 9/12 | 9/12 | **1（未调用）** | 11/12 | 3 |
| real-stream s1 | 12/15 | 12/15 | **1（未调用）** | 15/15 | 4 |
| real-stream s2 | 14/17 | 14/17 | **1（未调用）** | 17/17 | 5 |

这 3 个探针就是全部差距。**因此值得从 Codex 借鉴的不是它的接口，而是它"愿意去查"这一点**——而这份意愿源于它别无选择：1.2K tokens 的投影不查就答不出来，而 C3 的 8.5K 投影往往可以。

在 C 确实检索的场合，它精确地补上了缺口：18 个探针中有 13 个，其增益等于投影缺失值的数量（缺口 3 就补回 3，等等）。

### 只检索工具记录：节省比预期小

投影包含**全部 assistant 与用户文本块**——跨 18 个投影实测，100% 的文本块逐字存在。因此 assistant 正文从不需要检索。问题在于忽略它能省多少。

按记录类型统计的检索命中（跨冻结会话采样，108 次命中、9 个查询）：

| 类型 | 命中 | 片段字节 | 字节占比 |
|---|---:|---:|---:|
| 工具结果 | 64 | 26 180 | **61.9%** |
| 工具调用（参数） | 34 | 13 781 | **32.6%** |
| assistant 正文 | 10 | 2 350 | **5.6%** |

由此得出两点，而它们指向相反方向：

* **assistant 正文只占返回字节的 5.6%**，排除它几乎省不下什么。为此专门做一种检索模式不值得。
* **排除工具调用则是错的。** 投影**并不包含**它们：assistant 文本块 100% 存在，但真实会话里只有 **16–19%** 的工具调用路径存活（27/169、42/216、29/250），合成链为 40–100%。这些调用携带文件路径与命令，占返回字节的 **32.6%**——为省 5.6% 而丢掉它们是不划算的交易。

所以答案比问题本身更窄：**"只检索工具记录"对 assistant 正文而言是安全的，但对工具调用参数不安全，而节省只有 5.6%。** 投影的分工其实已经接近正确——正文逐字携带、工具证据建立索引、检索作为两者都未覆盖时的兜底。

## 每次压缩的成本

在 driver 上测量，请求是**冷启动**的（driver 不会先把对话当作普通回合发送，因此没有热前缀）：

| 策略 | 摘要次数 | 平均成本 | 平均输入 tokens |
|---|---:|---:|---:|
| C3 | 15 | ¥0.1173 | 73 539 |
| Codex | 18 | ¥0.0286 | 7 079 |
| OpenCode | 19 | ¥0.0256 | 7 352 |

冷启动数字**低估了 C3 的真实优势**：C3 读取**整个活动对话**（平均 6.7 万 tokens，最高 12.8 万），而 Codex 与 OpenCode 只摘要一个有界切片（约 7 千）。冷启动时读全历史很贵；**热启动时它是三者中最便宜的**——产出这些 token 的回合早已为前缀付过费。上文 99.8% 的缓存命中把一次 21.3 万 tokens 的读取变成 ¥0.003，而一次 7 千 tokens 的**冷**摘要要 ¥0.0286。

真实会话的摘要在它所复用的那回合刚发送后发出，所以它的成本是缓存后的数字，而不是上表中的 ¥0.1173——后者是 driver 造成的假象。这只是说这个形状**理应是热的**，不是保证：命中要求请求的 system prompt 与工具定义与那一回合完全一致；上文隔离 agent 的实测就是一致时的代价。实验自己的两个臂并没有测到这种情况（见“C3 的摘要如何生成，以及请求形状为什么重要”）。

## C3 的投影里有什么

约 1.1 万 tokens 的投影并非一整块。跨全部 18 个边界测量，通过从已提交的 checkpoint 精确还原各部分（无模型调用）：

| 部分 | 平均 tokens | 占比 |
|---|---:|---:|
| 受保护原文（用户＋assistant，逐字） | 5 155 | **45.8%** |
| 确定性工具证据索引 | 2 415 | **21.5%** |
| 粘性模型摘要 | 1 592 | **14.1%** |
| 保留的近期尾部 | 2 095 | **18.6%** |
| **合计** | **11 259** | |

各部分的配比随负载不同，读分数时值得注意：

| 负载 | 合计 | 原文 | 证据 | 摘要 | 尾部 |
|---|---:|---:|---:|---:|---:|
| 合成（n=9） | 9 067 | 63.1% | 26.4% | 10.5% | 0% |
| 真实会话（n=9） | 13 451 | 34.1% | 18.1% | 16.6% | **31.2%** |

由此有两点。证据索引稳定在约 2.4K tokens（它有固定的 2K 预算并会填满），因此在小历史和大历史上开销相同。而真实会话携带大得多的近期尾部，因为其记录更细：单个会话 1582 条记录，意味着更大比例落在保留窗口内。

## 128K 消融：当投影几乎保住了全部材料

这次消融去掉了模型摘要（只留确定性投影，不传 provider），窗口与上下文各表相同（128K）。**它的结论是那个形状的性质，而不是策略的性质**，而且生产形状实测与它结论相反——两者应当放在一起读（见下文“消融确立了什麼”）。

| 臂 | 闭卷 | 开卷 | 开卷平均查找 | 摘要成本 |
|---|---:|---:|---:|---:|
| **C3**（运行时默认） | 129/178 | **168/178** | 2.67 | 冷启动 ¥0.1173/次压缩 |
| **C**（纯确定性） | **129/178** | 162/178 | 2.22 | **¥0** |

**闭卷完全相同——18 个探针里每一个的得分都一样。** 开卷时摘要值 **+6**。

### 为什么在这个窗口下摘要毫无贡献

考卷问的是精确值，而在 128K 下确定性投影本就保住了几乎全部，有损副本无处发挥。跨 18 个投影测量包含性（无模型调用）：

| | 存在的值 |
|---|---:|
| 确定性投影（原文＋证据＋尾部） | **130/178（73.0%）** |
| 模型摘要 | 74/178（41.6%） |
| **两者并集** | **130/178** |
| **摘要带回了、而其余部分没有的值** | **0** |

摘要中的每一个值都同时存在于确定性投影中。**摘要是严格子集**，因此它无法提升一个已由投影其余部分决定的分数——它只能丢失信息。这正是两臂完全打平的原因。

这与前面压缩扫描得到的结论是同一效应、只是方向相反：逐字保留之所以胜过摘要，正是因为有损副本的缘故。此处的有损副本是**叠加**在逐字材料之上而非替换它，而**有损副本与精确副本并存时贡献为零**。

### 为什么开卷能拿到 +6：它改变了检索行为

这 6 分不是信息增益。在全部六个有差异的探针中，**查找次数更多的一方恰好高出 3 个字段**：

| 探针 | C3 | C（无摘要） | Δ | C3 查找 | C 查找 |
|---|---:|---:|---:|---:|---:|
| pipeline s3 | 6/6 | 3/6 | **+3** | **2** | 1 |
| real-stream s1 | 16/17 | 13/17 | **+3** | **4** | 1 |
| real-visual s1 | 15/15 | 12/15 | **+3** | **2** | 1 |
| real-yt s0 | 14/14 | 11/14 | **+3** | **2** | 1 |
| real-stream s0 | 12/15 | 15/15 | −3 | 1 | **2** |
| real-visual s0 | 9/12 | 12/12 | −3 | 1 | **3** |

相关性 **6/6**，两个方向都成立。摘要并没有提供那些缺失的值——它提供了足够的上下文，**让模型决定去查**。这正是开卷对比中把 C 与 Codex 区分开的同一行为，也意味着**摘要的实测价值是提示效应，而不是保留效应。**

### 这对设计意味着什么

* **在这份考卷上，摘要没有为自己的成本买单。** 它每次压缩花掉一次模型调用，却没有贡献任何投影中尚不存在的内容。它唯一被测出的收益是间接的。
* **诚实的限制是：本考卷是值回忆探测。** 它问"这个确切字符串是否出现过"，而这是逐字保留最擅长、摘要最不擅长的任务。摘要应当有助于本考卷没有问的那类问题：目标是什么、某个决定为何做出、还有什么未决。那正是真实追问所问的内容（前面实测约 80% 指向 agent 自身产出），但它们在这里没有被计分。
* **不要据此移除摘要。** 本次测量界定的是它在**回忆型考卷**上的价值；它并不能证明其在生产环境中无用。它确实确立的是：摘要的**保留**贡献为零，而其**行为**贡献是真实的——这是一个更窄、也更有用的结论。

### 当原文被挤掉时，摘要能证明自己的成本吗？

上面所有考卷都在"C 完整保留了每一个 assistant 块"的条件下运行，这使摘要在结构上就是冗余的。本测试**制造**摘要可能起作用的条件：压得足够狠，迫使原文被丢弃，然后看摘要是否保住了它们。

**压缩压力。** 扫窗口，统计"其特征短语在投影中任何位置幸存"的 assistant 文本块：

| 窗口 | assistant 块 | 逐字保留 | 由摘要承载 | 丢失 |
|---:|---:|---:|---:|---:|
| 128 000 | 446 | **446** | 0 | **0** |
| 32 000 | 446 | 333 | **1** | 112 |
| 8 000 | 277 | 184 | **0** | 93 |
| 4 000 | 277 | 123 | **0** | 154 |

在与生产相关的窗口下**一个都没丢**。在真实压力下（32K 及以下）有 93–154 个 assistant 块被丢弃，而摘要逐字承载其中**至多 1 个**。

**生成测试。** 包含性检验的是精确字符串，而摘要会改写，所以上表低估了它。本测试要求模型**生成**：从它的投影中列出能找出的每一个确切标识符、路径、版本、大小与计数。题目**不点名任何一个值**，因此丢失了某个值的投影无法靠匹配把它找回来。按精确包含评分——不经裁判——覆盖三个真实会话、两个窗口：

| 臂 | 被丢弃值 | 恢复 | 恢复率 |
|---|---:|---:|---:|
| C3（运行时默认） | 257 | **1** | **0.4%** |
| C（纯确定性） | 252 | **1** | **0.4%** |

**完全相同，且实际上都是零。** 两臂丢弃的值数量也几乎一致（257 对 252）——这正是子集结论从另一个方向再次显现：加入摘要使保留内容变化约 2%。

**关于对照的一个诚实提醒。** 同一次运行也测了模型列出了多少**存在**的值，以确认任务可做。该对照噪声过大，不足以支撑任何论断：32K 时含摘要臂列出 20%、另一臂 51.5%；16K 时顺序反转（72.1% 对 25.6%）。模型"列举"的行为在轮次之间的波动远大于任何摘要效应，因此这里只把它作为"任务可做"的证据报告，**不据此得出摘要是否帮助或损害精确生成的任何结论。**

### 消融确立了什麼

上表三项测量在此窗口下一致：值回忆增加 0、压缩压力保住 93–154 个被丢弃块中的 1 个、被丢弃值的生成恢复 0.4% 且有无摘要相同。

**生产形状实测与第一项相反。** 在那里 `deterministic` 的投影包含 130/178 个被测值、得分 127，而 `summarized` 包含 **151**、得分 147；摘要文本自身携带了约 47% 的被测值，而这里是 41.6%——但这里它们全部已在确定性投影里，那里不是。

所以诚实的表述是有条件的，而不是绝对的：**摘要能加多少，取决于投影本身已经逐字保住了多少被测材料。** 128K 下确定性投影单独就覆盖 130/178（73%），摘要是它的子集，因此增加 0；生产形状下同样覆盖 130，而摘要在其上又补了值。两次测量是同一个变量的两个端点，不是矛盾；而两轮都没有刻意变动这个变量——这正是本文仍缺的实验。

本文**不能**确立的是摘要在生产中无用（也无从确立它不可或缺）。这里每份考卷问的都是精确值——而这恰恰是摘要最差、逐字保留最擅长的。摘要应当有助于本考卷从未问过的问题：目标是什么、某个决定为何做出、还有什么未决——那正是真实追问所问的。

### 延续考卷：真实用户实际会问的问题

上面每一份考卷问的都是精确值，而这恰恰是摘要做不到的事。这一份测试的才是它的本职——**支撑延续**——并且它的三个输入全部取自真实会话，没有任何合成：

| 要素 | 来源 |
|---|---|
| 边界 | 某个真实用户回合之前的记录 |
| 问题 | 那句用户回合，逐字 |
| 参考答案 | 紧随其后的 assistant 回合，逐字 |

真实 follow-up 几乎全部在问 agent 自己此前的产出——*"为什么 prime agent 这么快？"*、*"手调提示词做了什么？"*、*"为什么 loop 花了这么久？"*——这正是摘要本应承载、而值回忆考卷够不到的材料。

两臂对同一边界走同一代码路径，只在是否生成摘要上不同，且作答时不使用工具。评分采用**盲配对评判**，臂标签随机打乱。

**结果随样本量移动，最终变得没有意义。**

| 样本 | C（含摘要） | C（去摘要） | 配对 |
|---|---:|---:|---|
| 18 题 | **1.61** | 1.39 | 摘要 9、去摘要 6、平 3 |
| 27 题（全部合格） | 1.19 | **1.37** | 摘要 10、去摘要 11、平 6 |

前 18 题上摘要看起来值 +0.22；补上 9 题后变成 −0.18。在完整样本上两臂无法区分：已判定配对中 48% 偏向摘要——等于抛硬币。

**判官无法分辨这么小的效应，而这一点本身是可测的。** 在**完全相同的答案对**上重新生成判定（答案有缓存），即可直接得到仪器的噪声底：

| | |
|---|---:|
| 相同输入下平均绝对分数差（0–3 量表） | **0.97** |
| 重复判定中完全一致的比例 | **11/36（31%）** |
| 相差达最大 2 分的重复比例 | 10/36 |
| 待测的臂间差异 | **0.18** |
| 含摘要 95% 置信区间 | [0.79, 1.58] |
| 去摘要 95% 置信区间 | [1.05, 1.69] |

**仪器的自相矛盾度是要测效应的五倍**，而两个置信区间几乎在整个范围上重叠。判官连配对结论本身都会翻转——同一道题在相同输入上先判"B 更好"、后判"A 更好"。

### 这确立了什麼

现在有三份考卷都没能找到摘要的保留价值，原因各不相同，而这个区别很重要：

| 考卷 | 结果 | 原因 |
|---|---|---|
| 值回忆（闭卷） | 摘要增加 **0** 个值 | 它是投影的严格子集 |
| 压缩压力下的生成 | 恢复 **0.4%**，两臂相同 | 它保不住原文被丢弃的内容 |
| 延续，真实提问 | **无可测差异** | 判官噪声过大，无法判定 |

前两项是关于摘要的**否定性发现**：它确实不增加内容，也确实在压力下保不住东西。第三项则是**测量的局限**，而非关于摘要的证据——在"摘要可能有效"的唯一条件下，它既不支持也不反驳其收益。

**什么才能定论。** 用**确定性评分表**取代自由形式的判官：从留出的延续内容中机械地导出条目（后续回合实际引用了哪些文件、哪些标识符、哪些已陈述的阻塞），按包含性评分。这等于用"是否抓住大意"的覆盖面，换取接近零的噪声底——而按本次证据，**一个没有方差的评分器，比一个它无法可靠回答的更丰富的问题更有价值。**

**评分表随后已构建并运行。** 它对照会话当时给出的参考答案，对两个确定性量打分：**内容召回**（候选答案包含的参考内容词比例——ASCII 单词加中文 bigram，即 ROUGE 式覆盖）与**指称召回**（其具体的路径、标识符、版本、大小与计数中被候选答案产出的比例）。两者方差**恰好为零**：对相同输入重新评分，结果逐位一致。

本轮重新生成了答案，并在提示中禁止工具调用——因为自由判官那轮的提示让模型输出了无人执行的 `<tool_calls>` 标记，那些答案被截断成标记、会被当成空答案计分。现在 38 个问题的答案全部非空，且无任何工具标记。

| 臂 | 内容召回 | 内容 F1 | 指称召回 | 字符数 |
|---|---:|---:|---:|---:|
| C3 | **0.199** | 0.146 | **0.242** | 2 208 |
| C | 0.182 | 0.142 | 0.216 | 2 270 |

| | |
|---|---:|
| 配对的平均差（内容召回） | **+0.0172** |
| 配对差的标准差 | 0.0672 |
| **n=38 时 80% 功效可检出的最小差异** | **0.0305** |
| 配对胜出 | 摘要 18、去摘要 20 |
| 符号检验 | p = 0.871 |

**测得的差异小于该设计可分辨的下限。** 在零方差评分器之下，制约因素不再来自仪器，而是**效应量相对样本量**：要在 80% 功效下检出 0.017，约需 120 个问题而非 38 个。因此评分表消除了判官的噪声，从而暴露出真实处境——**摘要在延续问题上的收益即使存在，也小到本次考卷在任何已运行的样本量下都无法看见。**

这条研究线到此诚实地停下。三份考卷都没能找到摘要的保留价值，其中一份还是专门为移除掩盖答案的仪器而重建的；剩下的问题是**效应量低于该测量的分辨率**，而不是"证明该效应不存在"。要确认或否证一个约两个百分点的收益，需要比这三个真实会话所能提供的大得多的题库。

一个顺带的发现，与生产有关而非与两臂有关：在 2048 tokens 的输出上限下，若干探针的答案返回为**空**，因为推理在任何文本产出之前就耗尽了全部额度。同一失效模式此前在粘性摘要路径上也出现过。**对任何未考虑推理开销而设定输出预算的调用，这都是一个真实隐患。**

## C 保留的 assistant 内容多得多，为什么只领先一点

这是对结论的一个合理质疑，而考卷自身的构成回答了它。

### 考卷的值到底来自哪里

| 来源 | 项数 | 占比 | C3 保住 | Codex 保住 | OpenCode 保住 |
|---|---:|---:|---:|---:|---:|
| 工具结果 | **120** | **67.4%** | **72/120** | 62/120 | 43/120 |
| assistant 正文 | 44 | 24.7% | **44/44** | 43/44 | 32/44 |
| 用户文本 | 14 | 7.9% | 14/14 | 14/14 | 13/14 |
| **合计** | 178 | | **130** | 119 | 88 |

三点结论，其中一点更正了前提：

1. **在 assistant 来源的项上，C 与 Codex 实际打平：44/44 对 43/44。** C 对 assistant 正文的逐字保留是满分的，但 **Codex 的全历史摘要也把这 44 个值几乎全部找回来了**。所以本考卷无法奖励 C 在这方面的优势——不是因为优势不存在，而是因为 Codex 根本没在这类事实上丢分。
2. **C 真正的领先来自工具结果：72 对 62。** 这是确定性证据索引在起作用，也是 +10 的来源。
3. **考卷有 67% 来自工具结果。** 只有四分之一的题项能在 assistant 内容上区分两者，而在这部分它们打平。

### 你的直觉是对的，但它需要一个压缩比

"如果问题大量命中 assistant 内容，C 应该好很多"——这个判断在原则上是正确的，并且在**本考卷未能制造的条件下**已被实测证实：

| assistant 内容 | 压缩比 | 逐字保留 | 仅摘要 |
|---|---:|---:|---:|
| 160 个精确决策代码 | 15× | **10/10** | 0/10 |
| 400 个精确决策代码 | 39× | **10/10** | 1/10 |

**一旦摘要被迫大幅压缩，逐字保留就决定性胜出。** 而在这些真实会话上摘要并未承受那种压力：模型对 7.3 万 tokens 的输入只写出约 1.6 千 tokens 的摘要，在这个比例下它足以留住所需的 assistant 事实。因此两者的差别主要落在工具结果上——C 有索引，Codex 什么都没有。

**能真正把它们分开的**，是一个 assistant 回合里包含大量**精确且形似**的标识符的会话（即上表 fixture 所建模的情形），或者一个更紧的摘要预算。本考卷两者都不具备，而其 67% 的工具权重是所测这两个真实负载的性质，并非普遍规律。

## 限制

* **Codex 与 OpenCode 是单点复现实现。** 其保留规则与提示词读自特定提交，上游后续改动会使数字失效。两者都按其**使用 API key 或第三方 OpenAI 兼容 provider 时可得**的配置建模。Codex 的第一方 `history`/`notes` 检索工具需要托管后端、付费 ChatGPT 套餐以及两个未开发阶段的功能开关，因此"Codex 配自有检索"这一臂**无法复现**；表里的 Codex 是它的本地兜底压缩路径。
* **考卷是识别任务，不是任务续做。** 它不衡量 agent 能否接着把活干完。
* **合成 fixture 偏重工具。** 它们奖励携带工具证据；策略之间真正分开是在真实会话上。
* **窗口敏感。** C3 的保护原文预算随上下文窗口缩放，收纳率在 128K 饱和（实测：32K 时 65%、128K 时 79%、256K 与 1M 不变）。生产窗口来自模型注册表——`models/future.rs` 里的 `128000` 只是模型未声明时的兜底。
* **开卷数字使用有界预算**（每次探测最多返回 32KB、60 轮上限）。换预算会改变查找次数。
* **开卷那轮必须先为合成会话造出真实会话。** 归档 CLI 读取的是 Agent 的会话数据库，其中只有真实会话，因此合成 fixture 被写入该数据库的隔离副本（含注册表行、entries 与 message blocks），该臂才能读到它们。生产数据库从不被写入；副本由 SQLite 的 backup API 生成。
* **检索取不回任何接口都未存储的东西。** OpenCode 的文件系统路径只能看到每个文件的最新版本，这是该接口的性质，而非调参问题。

## 复现

harness 与操作说明见 [scripts/abc_experiment/README.md](../../../scripts/abc_experiment/README.md)。输入、账本与结果位于 `~/compact-exp`（可用 `ABC_ROOT` 覆盖），之所以放在任何仓库之外，是因为其中包含真实会话数据。

因此复现是**部分的，且恰好沿本文的结构分界**：

| 由什么推导 | 能否仅凭检出复现 |
|---|---|
| 三条合成链（`export`、`analysis`、`pipeline`） | **可以**——固定种子的生成器，重新生成逐字节一致 |
| 一切涉及 `real-yt`、`real-visual`、`real-stream` 的结果 | **不能**——这些是私有对话，从操作者的 Agent 数据库读取并由 `freeze_sessions.py` 快照；其 ID 与快照均不公开 |

具体而言：本文每张表的**合成部分**都能仅凭仓库重建，而**真实会话部分不能**——那是 178 个考题项中的 **129 项（72%）**：闭卷表中的全部真实会话行、整张开卷表（合成链没有可读归档）、消融、延续考卷与构成分析。

缺少必需输入时脚本会**报错停止而非跳过**，因此部分运行不会被误认为完整运行。第三方要复现真实会话结果，需按 README 的步骤**替换为你自己的会话**；绝对数值会不同，但对比结论应当成立。
