# Vibe 面板

状态：**P0 已实现**（网格、成员=置顶、顺序、三层、输入层）；P1（远程会话、设备筛选、
添加对话框、两栏阅读层）与 P2 尚未开始。本文是产品与交互契约，它用到的按键在
[`KEYBINDINGS.md`](KEYBINDINGS.md) —— 那份文件负责键盘表，本文负责面板，两者不重复。

面板是一个**全屏、没有左边栏的置顶会话网格**：每格一个会话，可以放大到单会话全屏；
整个面板按"坐在沙发上用"来设计 —— 一只手拿遥控器，麦克风是主输入。

## 1. 成员：置顶的会话，仅此而已

一格 = **一个置顶会话** —— 本机的（`threads.pinned`），或某台主机自己报告为置顶的
（`pinRemoteConversation`）。没有第二份成员清单，这就是设计本身：

* **加入面板 = 置顶。** 用户先选设备、再选工作区、再选一条**尚未置顶**的会话；它被置顶，
  于是出现在面板里。从面板移除 = 取消置顶。两个入口，一个状态，所以"置顶了但不在面板里"
  不可能发生。对话框在页脚说一次这件事（不是每行都提醒）。在远程主机上，加入就是该主机
  自己的 `set_session_pinned`，用它的 thread id 寻址（用 session id 去置顶会写到错误的记录上，
  所以报不出 thread id 的老主机是被拒绝，而不是被猜）。
* **工作区置顶不把它的会话带进面板。** 工作区置顶只影响左栏排序；带进来会一次塞进十几条
  会话，正好毁掉面板存在的理由（一眼总览）。
* 在别处产生的置顶（左栏行菜单、主机自己的界面）下一次读取就会出现在这里。面板是置顶的
  视图，不是它的缓存。

远程置顶需要那台主机可达：离线时**明确拒绝并说明原因**，绝不排队。置顶是对另一台机器
数据库的写入，给它加发件箱等于造第二个更弱的事实源。

**哪些算数由那台主机自己报告。** 已配对主机的目录里每个会话带 `pinned`，面板读它 —— 我们
不维护"我想放哪些远程会话"的本地清单。所以一格的出现与消失都跟着那台主机的下一次读取走。

**远程的一格能说什么，取决于那台主机报了什么**，面板不编造其余部分：它的目录有标题、工作区、
`streaming` 与置顶，但没有创建时间（所以那一格没有日期，见 §2），也没有运行失败与未读标记，
于是一台主机的会话可以**在网格里、却不在待处理队列里**（§9.5）。它自己的审批会以事件到达
那一格，并在格子里被回应。

**这是已知限制，不是待办**：主机的会话既进不了待处理队列，也进不了发送队列，因为这两件事在
线路上都不存在 —— 目录是那台机器自己的摘要，不携带单次运行的结果、也不携带未读状态，而给它
发一句话是另一条命令、另一套前置条件。要让面板显示出其中任何一个，都是**主机侧目录协议的
改动** —— 值得做，但它是一件有自己兼容性说明的独立任务，不是这个面板再聪明一点就能补上的。

## 2. 顺序：按创建时间，加上用户挪过的位置

默认顺序是 **`createdAt` 升序** —— 最早置顶的在第 1 格，新置顶的追加到末尾。这与左栏
"最近活跃优先"刻意相反：

> 左栏是时间流，面板是空间记忆。

某格不能因为里面有人回了话就跳位置。用户可以重排，且用户的顺序优先：

```
resolved = []
for key in userOrder:            # 用户放过的位置，按他的相对次序
    if key in members: resolved.push(key)
for key in members sorted by createdAt:
    if key not in resolved:      # 新置顶的
        insert at the first position whose createdAt is later
```

* key 是 `local:<threadId>` / `remote:<desktopId>:<sessionId>`，所以改名、重连都不会让
  一格挪位置。
* 用户定下的相对次序**永远不被算法改写**；新成员按时间落到该在的位置。
* 取消置顶或删除只是从 members 消失，不动别人的位置。

同时看两台机器时，两个 `createdAt` 来自两个时钟；这只影响**新格子插入的位置**，不影响
已有格子，所以最坏是把一个新来的放错一格。

## 3. 设备筛选

默认显示**全部设备**，也可以只看一台。切换筛选**不重排**：切回来每格回到原位置。每格带
设备徽标，添加对话框以当前筛选为起点。

这个选择是一个**和列数同类的视图偏好**，按机器记住（它是随窗口大小做的决定，不是随账号的）。
入口只有菜单那一行，因为遥控器驱动不了对话框；而那一行是**值行**（`←`/`→`），这正是不打开
任何东西就能回答"我在看哪台机器"的原因。

筛选列出的是**已配对**的机器，而不是碰巧有置顶内容的机器：如果面板空了筛选就消失，那恰好
是读者最想按机器看一眼的时候。

## 4. 网格

布局是"格数 + 窗口尺寸"的纯函数（不依赖浏览器即可测试）：1 → 1×1，2 → 2×1（窄窗口
1×2），3–4 → 2×2，5–6 → 3×2，7–9 → 3×3，10–12 → 4×3 —— 也就是 `ceil(sqrt(n))` 列，
上限四列。

一格"喜欢"大约 520×420，而这个数字是**偏好，不是下限**：1280px 的窗口里五格无论怎么排
都给不出每格 520px，为此拒绝画网格比画出 416px 的格子更糟。这个偏好只决定一件事 ——
窗口窄到某个程度时**堆叠优于挤压**，所以两格会变成 1×2 而不是两条竖条，而五格仍然是
3×2（堆成五条会变成 180px 的横条）。

* **不满一行留空，不拉伸。** 第 2 格永远是第 2 个位置。按键可以覆盖列数（`⌘=` / `⌘-`，
  `⌘0` 回自动）。
* **不滚动，改成分页。** 12 格是一页，第 13 个置顶会话去第二页，而不是变得够不着 —— 顶栏
  显示 `1/2`，`⌥←`/`⌥→` 翻页。拒绝滚动是刻意的（需要滚动才能看全的网格不是总览），而无限制
  缩小格子更糟：13 格时 4×4 的 320px 格子根本读不了。
* 每格顶部 24px 的格头 —— 序号、标题、设备、运行状态、待批准数、未读点 —— 在正文之外，
  鼠标点击和 `↩` 都作用在这里。
* **空出来的那一格就是「加号」。** 形状本身留出空格时（三格是 2×2，空一格），那里放一个 `+`：
  选中环像走格子一样能走到它，`↩` 打开选择器，选择器头几行是读者最近待过的五个会话 —— 这张
  列表回答"哪一个"比一个完整的浏览树好得多。最后两行是「浏览全部会话…」（设备 → 工作区 → 会话
  的对话框）和「新开一个会话…」：后者离开面板去新建界面，并**把建好的会话置顶**。两条路都遵守
  §1 的「加入即置顶」。页满时没有空格，走菜单里的加入行。
* **一格的方块是写出来的，不是猜出来的。** 网格的每个子元素 —— 格子与加号都一样 —— 都从
  `gridAreaOf`（§13）拿到显式的 `gridRow` **和** `gridColumn`。只给列、把行留给自动布局时，CSS 会
  按自动布局光标摆它们：先画的加号占了第一行，每格都往下推一行，最后几格落进**隐式**行，而
  声明的行被压成 0 —— 实测读数是 `rows: 346px 346px 70px`、第三格只有 70px 高，用户报的就是
  「第一行的两个屏幕高度没了」。现在模板只决定尺寸，序号只决定方块，没有一件事留给自动布局算法。
* **hover 永远不是唯一入口。** 每格提供的操作都能用按键到达，因为遥控器没有指针。

## 5. 三层作用域，一个可编辑元素

面板有三层。同一时刻只有一层拥有键盘，而让它安全的那条规则是一条不变式：

> **面板打开期间，应用最多只有一个可编辑元素** —— 输入层的那一个编辑器。其余格子的输入框
> 一律 `disabled`（`contentEditable=false`），拿不到焦点，因此也接不到语音。

这条是"十几个会话 + 麦克风"能成立的原因：语音引擎把文字打给"当前有光标的那个元素"，所以
候选元素必须唯一。它由测试保证，不靠自觉：

`document.querySelectorAll('[contenteditable="true"]').length === 1`。

| 层 | 作用域 | 谁持有键盘 | 方向键 |
| --- | --- | --- | --- |
| 网格 | `vibeGrid` | 面板（选中环） | 移动选中环 |
| 阅读 | `vibeZoom` | 面板 | `↑`/`↓` 滚动正文，`←`/`→` 换会话 |
| 输入 | `vibeInput` | **输入法**，经由那一个编辑器 | 归输入框（候选、光标） |

`Esc` / 返回永远退一层，在网格层则退出面板。栈里不存在"返回关不掉"的弹层。

### 5.1 进面板就进输入层

网格里在某一格按 `↩`，直接打开**该会话的输入层** —— 光标就在编辑器末尾，准备好接一句话。
说话是这个面板最便宜的动作，所以它拿最短的路径：

```
网格 ──↩──► 输入（光标在编辑器）
 ▲             │ ⏎ = 发送；空 ⏎ = 收起
 │             ▼
 └──Esc──► 阅读（看着回答流式输出）
               │ ⏎ → 回到输入
```

发送后落到**阅读层**并滚到正在发生的地方，编辑器不会挡住刚问出来的回答。只想看不想说：
`菜单 → 查看`，或 `↩` 再按 `Esc`。

### 5.2 一个键只有一种含义

发送键的含义不随草稿状态改变：

* 空草稿 → **收起**输入层，不发送；
* 非空草稿 → **发送**，并进入阅读层。

没有开关，没有长按，没有组合键。一个"有时候发送、有时候什么也不做"的键，用户会不再相信它。

**这个键是输入框自己的，不是一条命令。** `⏎` 本来就是编辑器在发送（`MentionEditor.onSubmit`，
`FIXED_KEYS` 里的一条），而且它在输入法组合期间本来就让路。面板只补了编辑器原本没有答案的那
件事 —— 空草稿收起输入层 —— 而且补在发送路径里、不是命令表里。做成命令就是一次按键两个拥有
者：分发器在捕获阶段监听，会先于编辑器的提交执行，这套组合离"发两次"只差一次糟糕的重构。

又因为格子的阅读层**根本不挂载**输入框，"收起输入层不会被自动聚焦抢回去"也就成了结构性质，
而不是一个开关：编辑器已被卸载，没有东西可以获得焦点。

### 5.3 输入层关掉什么，以及那项能力去了哪

面板的编辑器就是应用原有的输入框（contentEditable，由同一批 IME 测试保护），输入层打开
期间关掉三件事：

1. **`@` / `/` / `#` 触发器。** 语音是一次性大段插入，一句里出现"斜杠"或一条路径就会在正文
   上弹出菜单 —— 更糟的是下一句话的按键被菜单吃掉。保持关闭。
2. **技能推荐。** 推荐会先问一次再发送，于是第一次 `⏎` **不会**发出。在沙发上这读起来就是
   按键坏了。
3. **输入层之外的自动聚焦。** 实际上不需要关掉任何东西：输入框**只由输入层挂载**，所以格子的
   阅读层既没有编辑器，也没有会运行的聚焦 effect。层的边界就是组件的边界。

**"用语音点名文件"去哪了**：不是消失，兜底是 `菜单 → 查看 → @`：先说完发送，在阅读层用
键盘补一个引用（或从另一台设备的左栏"加入上下文"）。特意记在这里：这项能力曾经是一个键、
现在是两个键，下次有人问"它去哪了"，应该能找到答案，而不是把功能半恢复回来。

### 5.4 会话正在运行：发送队列

会话正在跑时按 `⏎`，**把那句话留下来**，而不是丢掉：输入框把草稿交出去并清空自己的框，
格子上显示 `已排队`；等这一轮结束，文字**回到那个会话的输入框**，格子显示 `已放回输入框`，
读者如果还想发就再按一次 `⏎`。

**任何时候都不自动发送**，这是设计而不是偷懒。两种队列里——"跑完自动发"和"跑完交还给人看
一眼"——这是更安全的那种：沙发上说出来的一句话多一次确认，不存在"后悔了但已经发出去了"的
窗口，也没有需要调的定时器。

五条规则（`vibeQueue.ts`）：

| 规则 | 怎么成立 |
| --- | --- |
| **可见** | 存着一句话的格子显示 `已排队`；刚交还的格子显示 `已放回输入框`，直到读者打开那个会话 |
| **可撤，且撤回不等于丢弃** | 菜单的撤回行，或输入层里的 `⌘⇧X`，把文字放回输入框。如果框里已经有读者后来输入的内容，撤回**被拒绝**、句子继续排队 —— 覆盖一段正在写的话是比等待更糟的事 |
| **一格最多一条** | 再按一次 `⏎` 是**拒绝**（输入框把文字留在自己框里），而不是替换。替换最容易把一句话吞掉 |
| **发出前的那一瞬属于读者** | 队列里根本没有发送路径：它只写 `composerDraft` |
| **失败也留着** | 失败或中断的运行会走到同一个"没在跑"的判断，所以句子照样交还 —— 绝不会因此被当成第二条自动重发 |

输入层里的 `Esc` 仍然是"退出输入层"，**不**撤回队列：退出输入层是读者不说话了，撤回一句是
他改主意了。一个键兼两职，等于让 `Esc` 的含义取决于读者从键上看不出来的状态。

### 5.5 与会话视图之间的契约

面板把它的规则带进主窗口的那两个组件，所以它们的 prop 是**契约**，不是实现细节：
**默认值才是让普通会话保持普通的东西**，改默认值等于改整个应用。

| Prop | 所在组件 | 默认值 | 谁可以传 | 作用 |
| --- | --- | --- | --- | --- |
| `chrome` | `AgentThread` | `"full"` | 只有面板 | `full` 画标题栏、查找栏与浮动的输入框；`read` 只画正文与审批卡片，**不挂载输入框**；`input` 画会话尾部，输入框在流里 |
| `ownsCommands` | `AgentThread` | `true` | 只有面板 | 这个实例能否认领 `chat.stop` —— 除聚焦格之外都为 false，因为一条命令只有一个处理者，否则"最后挂载的赢" |
| `triggers` | `Composer` → `MentionEditor` | `true` | 只有面板 | 输入时 `@` / `/` / `#` 是否弹出菜单 |
| `onEmptySubmit` | `Composer` | 无 | 只有面板 | 空草稿下发送键的含义（收起输入层）；其他地方不传，那里空提交就是不发送 |
| `controls` | `Composer` | `"full"` | 只有面板 | `full` 是那一行可操作控件（模型、思考级别、审批档位、附件）；`none` 隐藏它 —— 输入层把这些收进菜单，屏幕上只留一行只读值 |
| `onQueue` | `Composer` | 无 | 只有面板 | 会话还在跑时"发送"意味着什么：草稿交给面板的队列，而不是被丢掉。其他地方不传，那里运行中的发送就是不发送 |
| `chrome` | `RemoteConversationView` | `"full"` | 只有面板 | `read` 去掉会话自己的顶栏（格子自己有格头），并把审批卡片从正文之上挪到底部的一条里 |
| `selectiveEvents` | `RemoteConversationView` | `true` | 只有面板 | 挂载这个视图时，是否把该主机的事件通道收窄到这一个会话。面板会同时显示同一台主机的多个会话，所以它**不能**收窄：通道是给"一个会话"的带宽买卖，网格不是一个会话 |

两条不变式挂在这些默认值上，而且都是结构性的、不是监督性的：

* **`read` 不挂载输入框**，所以"面板打开期间应用最多一个可编辑元素"成立，是因为树里只有
  一个编辑器，而不是因为有人盯着焦点。
* **`chrome` 默认 `full`、`triggers` 默认 `true`**，所以一个完全不知道面板存在的调用方
  拿到的行为与面板出现之前一模一样。新增 prop 遵守同一条规则：先进这张表，再进代码。

### 5.6 值一直可见，只有"改"进了菜单

输入框那一行控件（模型、思考级别、审批档位、附件）在主窗口里是对的，插在一句语音中间是错的。
但它不是被删掉 —— 因为"这一格在用什么模型、被允许做多少事"恰恰是同时看五个会话的人会问的问题。

所以面板把这一行拆成两半：

* **值永远在屏幕上，只读**，一行 —— `DeepSeek V4 Pro · 中 · 完全放开` —— 在**阅读层与输入层
  的同一个位置**。一个会在两层之间挪动或消失的值，是读者会不再相信的值。
* **"改"在菜单里**（§9），三条值行，用 `←`/`→` 调整：模型（在目录里循环）、思考级别（在该模型
  有的级别里循环）、审批档位。

三条归属规则：

* **一格的模型与思考级别属于那个会话**，通过它自己的 thread id 写（`vibeCellSettings.ts`）。
  主窗口的 `changeModel` 写到**外壳当前选中的会话**——在面板里那是主窗口碰巧打开的那一个，
  用它会把另一格悄悄改掉。
* **审批档位属于整个应用，不属于某一格。** 菜单那一行明说（"对整个应用生效"）；每格一个档位
  并不存在，面板也不暗示它存在。
* **远程格没有设置行，也没有那三行。** 它的模型与沙箱属于那台主机，面板只改自己拥有的。

这个值读的是该会话在 agent 缓存里的状态（这个会话**实际**在跑的），只在那份状态还没读过一次时
才回落到外壳的选择。

### 5.7 顶栏，以及它必须做对的三件事

面板是 `fixed inset-0`：它是应用里唯一内容从 x = 0 开始的界面，而窗口是 macOS 的
**overlay 标题栏**（`titleBarStyle: "Overlay"`、`trafficLightPosition: { x: 14, y: 26 }`），
红黄绿三个按钮是**画在页面之上**的，大约占 x 14–72。由此三件事，每一件都曾经错、现在有测试钉住：

* **顶栏的内容从按钮右边开始。** macOS 且在非全屏时留 80px（`pl-20`，与左边栏同一个预留值），
  其他情况（别的平台、以及全屏时系统会隐藏按钮）就是普通的 12px。规则在 `barChrome.ts` 里，
  数字来自配置，不是手感。
* **顶栏和别的顶栏一样高。** `h-12` —— 左边栏顶栏、会话标题栏、上下文面板、新建会话页顶栏
  用的都是这个高度，也是三个按钮所在的那条线。它曾经是 `h-9`：文字中线在 18px，而那些界面在 24px，
  6px 的抬升看起来正是用户报的「三个点后面的文字没对齐」。高度现在是常量（`BAR_HEIGHT`），
  `barChrome.test.ts` 会去读那几处顶栏的源码确认它们仍然一致，所以两边不会再各自漂移。
* **顶栏就是拖窗口的地方。** 面板打开时屏幕上看不到别的可拖区域，所以顶栏按下即开始拖窗口
  （`startWindowDrag`，它会跳过按钮，所以栏里那三个控件照常可点）。

还有一件和几何无关的全屏事实：**`set_fullscreen` 是要显式授权的能力**。`isFullscreen` 来自
`core:default`，`setFullscreen` 不在里面 —— 这个按钮曾经就这样发出去过一次：能力层拒绝了调用，
代码里的 `.catch(() => {})` 把拒绝吞了，按钮什么也不做。所以现在切换只有一个函数
（`fullscreen.ts`），失败会**到达读者**（错误提示 + 控制台），并且
`fullscreenCapability.test.ts` 就在用到它的代码旁边断言这条授权。

## 6. 阅读层：块光标，与一栏/两栏的放大

**滚动，按实现说**：阅读层里 `↑`/`↓` 把正文滚一屏（`PageUp`/`PageDown` 同样）；在**网格**里
`PageUp`/`PageDown` 滚动选中那一格的正文，而选中环不动 —— 读一格和走到下一格不是同一件事。
滚轮与触控板照常。

本文更早的版本描述过的**块光标**（整行高亮一块消息、`⏎` 展开工具调用）**没有实现**。它是另一种
交互（一个选中态，而不是一个滚动位置），对没有翻页键的遥控器仍然是更好的答案 —— 但它记在 §14 的
剩余项里，而不是写成已经有。

从网格打开时，默认**一栏**：正文维持主窗口的排版尺度。**第二栏**就是现有的上下文面板
（本机会话用 `ContextPanel`，远程会话用 `RemoteFilesPanel`）。复用这两个面板是刻意的：
右栏显示什么，不该取决于它是从哪个界面打开的。

它有三态，**按会话记住**（用面板自己的 key，`readingPanel.ts`）：

| 状态 | 什么时候出现 |
| --- | --- |
| `auto`（默认） | 窗口宽度 ≥ 1100px：够正文的排版尺度再加一条 400px 的栏 |
| `hidden` | 永不出现 —— 而且**会延续**：最近一次 `hidden`/`auto` 的选择会成为没有独立记录的会话的默认值，所以在一个格子里关掉，切到下一格仍然是关的 |
| `pinned` | 一直在，窗口怎么变都在 —— 固定的意义就是这个 |

`⌘\` 在 `hidden` 与 `auto` 之间切换（是切换、不是三态循环：一次按键有时会把读者正在藏的栏
**显示**出来，那种键读者会不再相信）；`⌘⇧\` 固定/取消固定。`pinned` **不**延续 —— 固定是对
一个会话的决定，继承它会给下一格打开一条没人要求的栏。菜单里同一个选择是一条值行，所以
"这个会话现在是哪一态"不按任何键就能答。栏宽固定 400px、没有拖拽手柄：阅读层是一个会话的
视图，不是有三个可拖列宽的窗口。

## 7. 输入层的屏幕

mac 输入法的候选窗、语音输入法自己的浮层，都跟着光标出现在屏幕下方。所以输入层**不是**
底部条：

* 顶部是**目标条**：发给哪个会话、哪台机器（屏幕上最高优先级，因为"我在跟谁说"必须一眼
  可答；发送后会闪一次，确认"落到这里了"）；
* 会话最后两条消息，灰掉、不可交互，只作上下文；
* 编辑器居中偏上，比主窗口大一号，4 行之后滚动；
* 屏幕其余部分留空 —— 候选窗就落在那里，不挡任何字；
* 提示行由命令表生成（只列出"有处理者且有绑定"的命令，所以它不可能声称一个不存在的键）。

网格在层后面可见、压暗：谁在跑、谁在等批准，正是同时看多个会话的人必须一直看见的东西。

## 8. 语音输入：六条硬约束

应用不实现语音识别，系统或第三方输入法做。应用欠它的是：

1. **绝不发送正在组合的按键。** `isComposing`、`keyCode 229`、WebKitGTK 的
   `"Unidentified"` 都属于输入法（这条规则在 dispatcher 和输入框里已有）。提交候选的那个
   `⏎` 不是发送的 `⏎`。
2. **关掉触发器。** 见 5.3。
3. **不换编辑器的类型。** contentEditable 编辑器背着 IME 的修补（`revealCaret`、
   `optimizeSpeed`、行尾零宽空格）；另做一个"对语音友好"的 textarea 等于把同一批 bug 重犯一遍。
4. **在按键处理的同步路径里给焦点，光标停在末尾。** `MentionEditor.focus()` 就在按键处理的
   同一拍里调用；用动画帧延迟的聚焦可能晚于输入法打开，那句话就丢了。
5. **一大段一次性插入是常态。** 编辑器会滚到光标；输入层把高度限制在 4 行。
6. **撤销可达。** 语音必然听错：`菜单 → 撤销这次输入` 把草稿恢复到输入层打开时的快照，一句
   错话一个键就丢掉，不必逐字删。**不做**"静音后自动发送" —— 沙发上必然误发，明确不在此列。

## 9. 按键

### 9.1 键盘

见 `KEYBINDINGS.md` → "Modes"。面板不维护第二张表。

有两个键值得在这里重复一次，因为它们是面板自己的语法、而不是快捷方式：方向键移动选中，
**`h`/`j`/`k`/`l` 用同样的方式移动** —— 同一条命令、第二个绑定。它们永远不会在编辑器上
触发（无修饰键的按键属于有光标的输入框），所以说话时打一个就是打一个字。

### 9.2 遥控器

小米一类的蓝牙遥控器约十二个物理键，其中只有七个能稳定到达 webview。映射**按层**给出，
因为七个键要覆盖二十多个动作：

| 遥控器键 | 网格 | 阅读 | 输入 |
| --- | --- | --- | --- |
| `↑` `↓` `←` `→`（按住时系统自己连发） | 移动选中环 | `↑↓` 消息块、`←→` 换会话 | 归输入法 |
| `确定` / 中键 | 打开该格 → **输入层** | 打开输入层 | **发送**（空则收起） |
| `返回` | 退出面板 | 回到网格 | 回到阅读 |
| `菜单` | 当前层的菜单 | 当前层的菜单 | 当前层的菜单 |
| `主页` | 第 1 格 | 跳到正在发生的地方 | 跳到正在发生的地方 |

**以上没有一条经过真机验证。** 下表的键位是设计，不是测量：某台遥控器的某个键实际发什么，记在
[`VIBE-REMOTE-KEYS.md`](VIBE-REMOTE-KEYS.zh-CN.md) 里，而那张矩阵是空的。面板自带一个**只读的按键
读数**用来填它（连按三次 `⌥⇧K`，见同一份文件）——它不是命令，也不拦任何按键。

**目前应答哪些键。** 方向键、`确定`、`返回`、数字键与 `菜单` 可用（菜单在 P1-1 落地）；
`主页`、注意力队列、添加对话框与设备筛选仍属 P1，在它们有处理者之前**不会**出现在提示行里。
下表的 `主页` 一行是计划，不是已发布行为 —— 而某台遥控器究竟会不会发出这些键，目前仍未验证
（§11 的真机矩阵是空的）。

两个刻意的取舍：

* **审批卡片上按确定只是打开卡片，不是批准。** 批准要走 `确定 → ←/→ 选"允许" → 确定`。
  遥控器误触率高，而批准不可撤销，所以不可逆动作多付一次按键。
* **不做长按、不做双击。** 两者都需要阈值，都无法在提示行里表达，而遥控器的连发会让双击
  不可靠。设计里唯一的"按住"是系统的方向键连发 —— 它不花我们的成本，也不需要解释。

### 9.3 降级：遥控器键不够时

实测口径（§11 的矩阵），并且诚实说明什么会失效：

| 情况 | 行为 | 还剩下什么 |
| --- | --- | --- |
| 没有 `菜单` 键（按下什么也不发） | 菜单**从遥控器上**到不了 —— P1-1 落地之后这是真实损失，也正是 §9.4 的 `aliases` 要有存在感的原因 | 键盘 `⌘⇧K`，或面板顶栏指针可点的 `⋯`。菜单能配的东西（列数、顺序、移除、在主窗口打开）在那里都能做，所以没有这个键的遥控器仍可用，只是永远停在自动布局 |
| 没有 `主页` 键 | 没有"跳到正在发生的地方" | 正文自己的回到底部控件；发送本身也会滚到那里 |
| 没有 `返回` 键（或 `Esc` 被吞） | **面板仍能退出**：面板顶栏的退出按钮始终存在、可点，`⌘⇧V` 也能开关。退出永远不能依赖某台遥控器可能没有的键 | 鼠标或键盘 |
| 只有 `←` / `→` + 一个功能键（翻页笔） | 面板能打开，`←`/`→` 可换会话 | 不足以使用；写在这里，免得有人再试 |
| 音量 `+` / `-` | 通常被系统消费，根本到不了我们 | 不绑定；个别型号能送达，是 P2 字号控制的候选 |
| 语音 / 电源 | 属于系统（助手、睡眠） | 永不绑定 |

我们绑定的每个键都在真机上量过，不靠假设：下面的矩阵就是记录，而"某型号菜单键什么也不发"
正是 9.3 第一行存在的原因。

### 9.4 设备的键 vs 用户的键

遥控器的按键是**设备**的属性，所以在命令表里是 `aliases`：用户改绑键盘组合键之后、甚至清空
绑定之后，它们照样生效。设置页把它们显示在录制框旁边，只读。但它们仍然会拒绝对同一作用域内
另一条命令的录制 —— 两条命令共用一个按钮与共用一个组合键一样含糊。

### 9.5 待处理队列

同时看几个会话的人最常问的是"哪一个在等我"。答案刻意很窄 —— 忙不等于需要你：

| 状态 | 进队列？ | 为什么 |
| --- | --- | --- |
| 有待批准（`approvals > 0`，或运行自报 `waiting_approval`） | **是**，`待批准` | 唯一会卡住 agent 的状态；也正因为它卡住运行，它排在失败之前 |
| 运行失败 | **是**，`失败` | 等下去它也不会自己继续 |
| 你没在看的时候跑完了（左栏的未读标记） | **是**，`已完成` | 值得看一眼，但没有东西被卡住 |
| 排队中、运行中、已取消 | **否** | 把"运行中"放进来，队列就是整个面板 —— 那只是慢一点的左右键 |
| 跑完了而且已经看过 | **否** | 它只是一个跑完的会话 |

两个地方从两个距离回答它：面板顶栏给数量（"1 个待处理"），格子的格头说明**为什么**在等
（`失败`、`已完成`；待批准本来就有计数徽标）。按键跳到**从读者当前位置顺时针的下一个**
需要处理的格子，并直接落在它的**阅读层** —— "它想让我做什么"是靠打开来回答的，再让读者按
一次就让队列失去意义。

没有待处理时这个键**不被认领**（根本不注册），这是面板对所有命令的规则：无事可做的键必须
留给应用自己。菜单仍然回答这个问题，用一行**禁用的**"没有需要你处理的会话"，而不是干脆
不显示 —— 当"没有"正是被问的问题时，空答案也是一个答案。

## 10. 面板不做什么

* 不做自由分屏树，不做拖动改格子大小（那是窗口管理器，不是总览）。
* 不做滚动网格：一页 12 格，再多就分页（§4）。
* 不在面板里做一套新建会话的**流程**：加号菜单里的「新开一个会话」去的是那个本来就要第一句话的
  界面，并把建好的会话置顶。
* 不做跨机器同步顺序或布局；顺序按机器，与其他视图偏好一致。
* 不做停顿自动发送，也不做自动批准。

| 遥控器的按键在改绑、清空绑定之后仍然生效 | `shortcuts.test.ts`、`catalog.test.ts`、`keybinding.test.ts` |

其中两条在落地前被手工证伪过（去掉断言 → 测试变红 → 断言放回）：空草稿收起、以及"只含置顶"。

仍然没有覆盖、并如实记在这里：

* **运行中会话的拒绝**：P0 不排队（P1），可见原因挂在输入框自身的状态上，而不是对面板的测试。
  P1 之前是人工核对项。
* **触发器抑制**：输入层不传技能推荐，触发器本身在编辑器里，但还没有测试断言"说出来的 `@`
  不弹出菜单"—— 触发器是文本驱动的，需要在编辑器层面补一条。
* **每会话的右栏偏好**（阅读层的第二栏）属于 P2，尚未实现。
* **队列自己的状态是组件测试覆盖的，不是截图。** 截图 harness 能把"运行中"报给**左栏**
  （`?streaming=`），但本机输入框的"我这一轮在跑"来自该会话消息流里的一条流式助手气泡，
  夹具不伪造 agent 就造不出来。所以那次截断断言的是相邻的性质 —— 队列**不会**抢走一次
  普通的发送 —— 而标记、交还、撤回行由 `VibeStage.test.tsx` 与
  `Composer.inputLayer.test.tsx` 覆盖。


**真机：未测。** 矩阵在 [`VIBE-REMOTE-KEYS.md` 第三节](VIBE-REMOTE-KEYS.zh-CN.md)，是空表，每一格写
「未测」。它的第一节就是可打印的逐键清单，面板里的只读按键读数负责填它 —— 连按三次 `⌥⇧K`，然后按
遥控器。在那一节有实测行之前，本文与 `KEYBINDINGS.md` 都不得声称某个键可用；每条实测记录都要写明
由谁、何时、哪台机器、哪个型号。

## 12. 存储

| 数据 | P0 | 之后 |
| --- | --- | --- |
| 成员 | 不存 —— 它就是置顶 | — |
| 顺序、每会话的右栏偏好、列数覆盖 | `localStorage`（`future.vibe.order`、`future.vibe.prefs`） | 就留在那里 —— 见下 |
| 键位 | 现有快捷键存储（`KEYBINDINGS.md` §Storage） | 同左 |

面板的视图偏好与主题、字号、面板宽度同一条规则：按机器、在读渲染路径上读、存在
`localStorage`。

**为什么顺序不进 `app.db` —— 已评估，结论是不做。** 问题是面板的顺序、每会话的右栏选择与列数
覆盖该不该从 `localStorage` 搬进应用数据库。不该：

* **没有第二个客户端要对齐。** 面板只存在于桌面端；手机上没有对应界面，跨设备的网格布局同步
  也不是需求。一张数据库表能换来的只有 webview 存储本来就已经具备的持久性，别的没有。
* **它会白走一次这个功能的边界。** 桌面端的数据库与迁移链在 `host/src/store/`（桌面端
  `src-tauri/src/store.rs` 只是 `future_host::store` 的再导出），设置文档的 schema 在
  `packages/app-settings/` —— **两者都在 `desktop/` 之外**。搬迁是一次带版本化迁移、全新安装
  夹具和双语 `ER.md` 同步的 schema 改动。
* **这些是视图偏好，不是数据。** 按机器、在读渲染路径上读 —— 和主题、字号、面板宽度同一条规则。
  `vibePreferences.ts` 是唯一碰这些键的文件，所以将来真要搬，改的是两个函数，不是一整张调用图。

记为**已关闭**而不是"待办"：原来挂在 P2 表里的那一条已经删掉，读到这段的人就是答案所在。

## 13. 代码落在哪

```
desktop/src/features/vibe/
  VibeStage.tsx          网格与放大格；面板的渲染根
  VibeCell.tsx           一格的格头、内容与降级渲染
  VibeCellContent.tsx    本机 / 远程（复用 AgentThread 的内容层 / RemoteConversationView）
  VibeInputLayer.tsx     输入层：目标条、编辑器、提示行
  VibeBar.tsx            顶部细条：设备、布局、退出
  VibeMenu.tsx           当前层的菜单（一个组件，三种变体）
  AddToVibeDialog.tsx    设备 → 工作区 → 会话
  layout.ts              gridOf(count, width, height) —— 纯函数
  order.ts               resolveOrder / insertOrder —— 纯函数
  useVibeOrder.ts        存下来的顺序与两处写入
desktop/src/features/keyboard/   catalog、scopes、dispatch（键位已经落地）
desktop/src/components/layout/AppShell.tsx   面板进渲染树，而不是并列
desktop/src/features/agent/AgentThread.tsx   抽出内容层供复用
```

面板画在 `AppShell` **内部**（切换 `viewMode`），不是第二个窗口，也不卸载外壳。让运行状态、
未读、审批、远程轮询活着的 hooks 都在那里；自带一份副本的面板会与左栏显示两个事实。

`AgentThread` 没有抽出第二个渲染器，而是长了一个 `chrome` 参数（`full` | `read` | `input`）：
第二个消息渲染器会把已经修好的滚动、分页、审批 bug 重新挣一遍。三种 chrome 是同一个组件按层挑
外围部件，而 `read` 干脆不挂载输入框 —— 这正是不变式成为**组件树的性质**、而不是靠人看管一条
规则的原因（§5）。

P0 实际落地的东西，对照上面的计划：`layout.ts` 与 `order.ts` 是纯模块，表在测试里逐条断言；
`vibePreferences.ts` 是唯一读写面板存储键的文件；`VibeStage.tsx` 持有层、成员与几何；
`VibeHintBar.tsx` 生成提示行；`VibeStage` 通过 `vibeOpen` 接进 `AppShell`，**替换**外壳的三栏
而不是盖在它上面，所以输入框不可能留在下面继续挂着。
