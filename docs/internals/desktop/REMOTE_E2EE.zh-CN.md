# Remote v2 端到端通道

> （[English](REMOTE_E2EE.md)）

## 安全边界

移动端与桌面端互相认证，并在发布到 NATS 之前加密应用记录。恶意 broker 可以丢弃、
延迟、乱序、重放、路由和伪造消息，但必须**无法**获知应用明文，也**无法**制造一条
被接受的命令、回复、文件分块或 presence/catalog 事件。

这不防护：被攻陷的端点、被窃取/未锁定的凭据存储、泄露的**未使用**邀请、流量
时序/大小、NATS subject 元数据或可用性。当攻击者能压制投递时，云端吊销不是即时
的端点吊销信号。本地禁用/解除配对立即作废访问并清除流量密钥/candidate。NATS JWT
ACL 仍是纵深防御，不是消息来源证明。生产桌面端要求经校验的 TLS；移动端要求 WSS。
进程内 Rust 测试 broker 刻意使用明文。

## 配对与迁移

桌面端在本地生成 X25519 身份与一个独立的随机 32 字节邀请 PSK。私钥与 PSK 都不发送
给平台 API。现有平台的 claim nonce **不是**这个 PSK：claim nonce 仍然发给平台。

同一份完整的 `futureos://remote/pair` 邀请同时用于扫码与复制粘贴。它包含 `v=2`、
现有平台 `code`、`desktopId`、现有 NATS `desktopKey`、X25519 `secureKey` 与本地
`secret`。把整份邀请当作短时效的 bearer 凭据对待。不新增 6 位数字码模式。不得记录
邀请、不得发送给 analytics、不得用远程 API 渲染二维码。

移动端生成自己的 X25519 身份，并把 bundle 存入 Expo SecureStore
（`WHEN_UNLOCKED_THIS_DEVICE_ONLY`），沿用现有的双槽凭据提交。桌面端用其现有的
owner-restricted、原子化配对凭据文件存储配对身份；这不是硬件 keystore 保证。

首次配对使用 `Noise_XXpsk0_25519_ChaChaPoly_BLAKE2b`。移动端在发送最后一条握手消息
之前，先核对远端静态密钥与扫码/粘贴的密钥。桌面端验证邀请 PSK 的持有、绑定远端
静态密钥、持久化绑定，并把 PSK 从活动凭据中移除。之后即使有人复制了该邀请也会被
拒绝。这是"持有可信邀请"的认证，不是对人或法律身份的核验。

后续握手使用 `Noise_IK_25519_ChaChaPoly_BLAKE2b`；双方都要求已绑定的远端身份。丢失
首次配对确认时，可用同一手机身份以 IK 恢复，而不接受服务端提供的替代密钥。每次
握手都用全新临时密钥。流量密钥/计数器从不落盘。

旧桌面端配对由新邀请替换。旧移动端凭据 bundle 无法进入 v1 业务通道。现有用户升级
两端后必须重新配对。没有生产明文回退。旧的 `desktop/web` 验证客户端不是 v2 客户端，
不能控制此桥接。遗留 Rust 协议/业务夹具仅用于测试，不是兼容模式。

## 握手所有权与就绪

原始请求/回复交换只使用现有 pair 命令 subject 上的 `secure_open` 与
`secure_finish`。原始输入上限 16 KiB；Noise 消息上限 8 KiB。待定握手/candidate
有界且 30 秒过期。只有经认证的 Noise 输出才能产生 candidate 流量通道。

桌面端返回加密的 `handshake-confirm` 记录，含 presence、桥接身份与能力。仅凭它
不能取代正在服务的通道。移动端安装订阅并 flush 后，发送加密的 `secure_ready` 命令。
桌面端把该 candidate 提交为当前通道并返回加密确认。失败的 candidate 不会停用上一
通道，已停止的 access epoch 也无法安装迟到的 candidate。未提交的 candidate 不能
运行普通命令或上传分块。

JWT 续期与 NATS socket 替换复用钉住的身份，绝不重置流量密钥计数器。后台/重启恢复
创建新握手。过期的 heartbeat 回执触发经认证的探测/重连；恢复重启后的桌面端不信任
任何未签名的发现信标。

## 二进制应用记录

记录层使用 Noise Split 出的两个方向密钥做 ChaCha20-Poly1305。Rust 侧用 `snow` 与
`chacha20poly1305`；移动端用 `noise-handshake`（纯 JS sodium 后端）与记录层的
`@noble/ciphers`。独立记录层支持超过 Noise 65,535 字节传输消息上限的 NATS 消息。
不要用 JS 握手库的传输 cipher 处理这些记录。

| 偏移 | 字节数 | 字段 |
| --- | ---: | --- |
| 0 | 4 | ASCII `FRE2` |
| 4 | 16 | Noise 握手哈希的前 16 字节 |
| 20 | 8 | 小端序列号 |
| 28 | 可变 | 密文 + 16 字节 AEAD tag |

Nonce = 四个零字节 + 8 字节小端序列号。每个发送方向有独立的密钥与单调计数器。
序列号达到 `2^32-1` 之前必须发起新握手。线上上限 1 MiB，明文可用 1 MiB - 44 字节。
请求与所有主动记录把精确的 NATS subject 作为固定头之后的附加数据参与认证。

回复上下文是 `reply:<请求 subject>:<请求头字节 4..28 的十六进制>`。它把回复绑定到
已认证的请求通道与序列号，而不是 broker 提供的 inbox。替换回复 inbox 不得替换响应。
缓存的业务回复在**端点内部**保持明文，并在每次经认证重试的回复上下文中重新加密。
业务操作 ID 跨重试保持稳定；记录序列号不保持。

接收方按通道/方向维护 4096 条的有界重放窗口。认证成功后才变更窗口。反射的、
subject 不符的、连接不符的、被篡改的、重复的与窗口外的记录一律拒绝。接收方认证
先于解压、JSON 解码与业务去重。压缩在现有策略启用时发生在加密之前。

所有命令/回复、文件上传/下载、presence、catalog、事件与断开路径都走这条边界。
配对控制是唯一的原始例外。NATS subject 仍然可见，所以协议不声称元数据机密性。

## 验证与上限

`packages/remote-crypto/tests/vectors.json` 同时被 Rust/snow 与移动端用确定性的公开
测试密钥检查，覆盖 XXpsk0、IK、握手哈希、记录字节、AAD 与回复关联。
`generate-vectors.cjs` 打印 JS 向量；生产环境不暴露任何固定临时密钥的选项（我们的
wrapper 不提供）。

测试还覆盖逐字节篡改、错误 PSK/prologue/密钥、重放/反射、大记录、丢失确认、
钉住密钥重连、过期凭据刷新、持久化失败、邀请复用/过期、就绪交接、本地作废，以及
穿过真实桌面端 NATS 命令循环的加密请求。现有业务/生命周期夹具显式 mock 其认证
传输；仅凭那些夹具不能作为 E2EE 的证据。

固定记录开销为 44 字节，业务/文件流量不做 Base64 膨胀。握手字段是小的 Base64url
字符串。性能与兼容性必须在真实 Android/iOS 设备上测量后，才能对手机延迟、耗电或
硬件密钥背书作声明。Metro/Hermes 导出与桌面 Node 测试是有用的检查，但不是真机
运行时测试或渗透测试。
