# 用技能推荐这套评测换一个决策模型打分：先校验装置

[评测](evaluation.zh-CN.md)只给一个模型（Jev）打了分。要把另一个决策模型（例如 Perplexity 的
`pplx-decider-v1.2`）放到同一道题上比，第一件要确认的不是"它多强"，而是**这套装置现在跑出来的
数还是不是报告里那些数**。本页记这次校验、校验必须冻结的技能目录、换模型时用的那条命令，以及
——从 2026-11-09 起——第二个模型到底测出了什么。

**一句话结论**：在测试环境上，`pplx-decider-v1.2` 与 Jev 都是 100 题答对 93 题，而它们答错的题
几乎不重叠——decider 在"选哪个技能"上好 3 题，在"该不该推荐"上差 4 题。这个差别不足以让这批题
替你做决定。真正能定的是延迟：decider 每题有 3.48 秒的下限，而服务路径的死线是 2.5 秒（§6），
照现在的配置每张推荐卡都会超时。**这不是一次换模型，除非先把延迟解决**；本页没有任何准确率数字
支持换。

## 1. 装置校验（2026-11-02）

把 Jev 整个重跑一遍——同一批 100 题、同一份 `dataset/gold-v1.json`、同一条服务路径（一个 Choice
+ `none_of_these` 门控，即 `Suggester.rank`）、同一份 141 个技能的目录（§2）——与
`dataset/score.json` 里记录的数逐项对照：

| 指标 | `dataset/score.json` | 重跑 | 差 |
|---|---|---|---|
| 决策一致（n=100） | 93.0%（93） | 93.0%（93） | 0 |
| 首答正确（n=65） | 90.8%（59） | 90.8%（59） | 0 |
| 首答∈参照集（n=65） | 93.8%（61） | **95.4%（62）** | **+1.6 个百分点** |
| 正确拒答（n=35） | 97.1%（34） | 97.1%（34） | 0 |
| 误拒（n=65） | 1.5%（1） | 1.5%（1） | 0 |
| 首答 = 出题所用技能（n=65） | 93.8% | 93.8% | 0 |
| 输入 token，每题中位 | 8,765 | 8,749 | −16 |
| 延迟，中位 / p90 | 488 / 1224 ms | 685 / 787 ms | 见下 |

决策、首答、拒答、成本四项与报告逐字对上。两处需要各补一句。

**唯一动了的那项指标（首答∈参照集）可以逐题解释，不是装置有偏。** 把重跑结果与
`dataset/score.json` 的 `per_question.jev` 逐题比：**首答相同 95/100，推荐/拒答判定相同 98/100**。
翻转的只有 5 道，而且除了这一项之外互相抵消：

| 题目 | 报告那次 | 重跑 | 参照 | 影响 |
|---|---|---|---|---|
| p015 | `future-web` | `future-paper` | `[future-web, future-paper]` | 首答错，但仍在参照集内 |
| p028 | `future-explore` | 拒答（`none` 0.18 ≥ 0.15） | `[future-explore]` | 首答错；本次唯一的误拒 |
| p035 | `dnanexus-integration` | `latchbio-integration` | `[latchbio-integration]` | 改对 |
| p043 | `pyzotero` | `paperzilla` | `[paperzilla]` | 改对 |
| n032 | 拒答 | `future-deep-research` | `[future-web]` | 两边都错；这次它的误拒位置挪到了 p028 |

净值：首答 +2 −2 = 0；首答∈参照集 +2 −1 = +1（61 → 62）；正确拒答与误拒都还是 1/35 与 1/65，
因为本次唯一那处误拒换了身份（n032 → p028）。这正是评测 §5.6 量到的运行间采样波动——同一个请求
两次独立运行，首答相同 91/100、判定相同 97–99/100——本次的 95/100 与 98/100 落在这个范围内，
所以那 1.6 个百分点是噪音，不是偏差。引用这组数时仍要这样读：**一次运行只能分辨约 ±2 道题的差异，
再细的差别它看不出来。**

顺带值得记一笔：p035 与 p043 恰好是 §2.2.5 归给**被移除的第二次调用**的那两道（胜利依赖 SKILL.md
正文措辞）。这次服务路径只有一次调用，两道都自己答对了。这进一步说明那"3 道题 / 4.6 个百分点"
的差距在采样噪音之内，不是稳定的能力差。

**延迟不能跨天比。** 重跑中位更高（685 vs 488 ms）、p90 更低（787 vs 1224 ms），同一个 endpoint、
不同网络、不同时间；token 数一致说明载荷没变。延迟只在同一时段、同一网关下测的两次运行之间可比
——§4 里的两个模型就是这样比的。

## 2. 目录冻结在 gold 答案所依据的 141 个技能

`dataset/roster.json` 就是那次评测用的 141 个技能。新模型必须用它而不是当前的 `skills/` 子模块，
有两条理由：

- gold 答案是照着这批技能出的；目录一旦增删或改名，题目和参照答案都变了，分数就与任何东西都不可比；
- 选项表就是模型看到的全部世界。141 个选项约 8.7k 输入 token，每多一个技能就是每个请求都多一行
  （评测 §4.1）。

子模块现在已经长到 **242 个技能**（17 内置 + 225 第三方，同样由 `loadRoster` 读出）。242 仍在 254
个选项的上限内，所以在当前目录上跑仍是"一个 Choice"——但那是**另一道题**：它需要先重出 gold
（`ground-truth.mjs`）才谈得上打分，而且两个模型必须在同一批里跑，因为新 gold 的分类与旧分数不可比。

所以 `scripts/skill_reco/bench/decider-run.mjs` 把 `dataset/roster.json` 铺成一份临时技能树，
交给仓库里那个 `loadRoster` 读——选项文本、顺序、220 字符截断都走发布路径，而不是另写一份等价实现。

## 3. 换一个模型怎么跑

```bash
cd scripts/skill_reco
# 先 5 题：这个 endpoint 到底会不会答一个合法的 Choice
node bench/decider-run.mjs run decider-smoke --model pplx-decider-v1.2 --limit 5
# 再全量，再对比
node bench/decider-run.mjs run decider-test --model pplx-decider-v1.2
node bench/decider-run.mjs compare jev-test decider-test
```

一次运行由这些输入定义，写清楚是为了让数字能被重新跑出来，而不是只能被相信：

| 输入 | 值 |
|---|---|
| endpoint | `~/.future/agent/auth.json` 里 `future` 项的 `base_url`——当前是 `https://test.future-os.cn/api`；指向别处时用 `--base` |
| 模型 id | `--model pplx-decider-v1.2`——测试环境也接受 `decider` 作它的别名（§5）；基线用 `--model jev` |
| 题目 | `dataset/questions.json` —— 100 道（65 有答案 / 35 应拒答） |
| gold | `dataset/gold-v1.json` |
| 目录 | `dataset/roster.json` —— 141 个技能，铺成桩树 |
| 提示词 | 发布路径那一份：`stage1-one-choice-none-v3`，chunk 254，`none_of_these` 门控 0.15 |
| 解码 | 不传——载荷只有 `{state, model, questions}`，走 endpoint 的默认 temperature（它表现成什么样见 §4.1） |
| 并发 | 1（默认）；并发跑量到的是网关排队，不是模型 |
| 轮次 | 一次运行算一轮；§4 报的是同一时段的 decider 两轮 + Jev 一轮 |

- 凭据用 `~/.future/agent/auth.json` 里的 `future` 项（和 agent 自己用的是同一份）；
  `FUTURE_API_KEY` 可覆盖，用于自带 key 的 endpoint。
- `--limit 5` 不是客套。换模型最常见的失败不是答错，而是**格式不合**——返回自由文本、一次给多个
  选项、或者没有 `none_of_these`——而 `Suggester.rank` 会把缺失的概率读成空分布，于是每道题都变成
  "很自信地拒答"。这次冒烟把一个格式错误变成报错，而不是等 100 题跑完才发现全废；它还会断言自己
  发的请求与服务路径发出的请求逐字节相同，因此这项检查不会与它要覆盖的提示词走散。
- 成本与时间：Jev 每题约 8.7k 输入 token、decider 自报约 7.2k，整批分别约 87.5 万与 71.9 万。
  按各自公示价，100 题约 $0.037（Jev）与 $0.014（decider）。顺序运行的时长由延迟决定：Jev 约
  1 分钟，decider 约 6 分钟。
- 记录落在 `runs/<name>/`（gitignore），每条带自己的配置（endpoint、模型、目录、门控阈值、
  stage-1 版本）。换配置重跑会重录，不会把旧答案当成新结果续上。

## 4. `pplx-decider-v1.2` 在测试环境上的结果（2026-11-09）

先在同一 endpoint、同一时段把 Jev 重跑一遍，与 §1 逐项吻合（93.0 / 90.8 / 97.1，零误拒）；然后
`pplx-decider-v1.2` 跑了两轮。

| 指标 | Jev（`jev-1.13`） | `pplx-decider-v1.2` |
|---|---|---|
| 决策一致（n=100） | 93.0% | 93.0% |
| 首答正确（n=65） | 90.8%（59） | **95.4%（62）** |
| 首答∈参照集（n=65） | 95.4%（62） | **96.9%（63）** |
| 正确拒答（n=35） | **97.1%（34）** | 88.6%（31） |
| 误拒（n=65） | 0% | 0% |
| 首答 = 出题所用技能（n=65） | 93.8%（61） | **98.5%（64）** |
| 输入 token，每题中位 | 8,749 | 7,188 |
| 延迟，中位 / p90 | **676 / 774 ms** | 3581 / 3650 ms |

两个系统都是 100 题答对 93 题——总数相同，但来自相反的方向。**逐题只有 6 道不同**：decider 改对
3 道（p015 → `future-web`、p019 → `benchling-integration`、p043 → `paperzilla`，都是 gold 的首选），
改错 3 道（n026、n029、n030，都是应拒答的题被它给了技能）。p037 是两个模型都错的那一道
（`matlab`，gold 是拒答）。

按主口径读，这是一次平手：decider 在"选哪个技能"上好 3 题（在独立的 `source_skill` 标签上好 3 个
百分点），在"该不该推荐"上差 4 题——35 道应拒答的题里它给了 4 道技能（n026、n029、n030、p037），
Jev 只给 1 道（p037，两边都错这道）。对 65 道正例来说，3 道题正好是这批题的分辨极限（§1）。

token 数在同一份逐字节相同的载荷上差了 18%（8,749 对 7,188）：每个 endpoint 用各自的 tokenizer
报用量，所以每题成本必须用各模型自己的计数乘自己的价目，不能共用一个 tokenizer。按各自公示价，
decider 每题便宜约 2.6 倍（$0.00014 对 $0.00037）——放到 §6 面前没有意义。

### 4.1 两轮零差异：这个模型在这条链路上是确定性的

`decider-test` 与 `decider-test2` 是连着跑的。100 道题**逐题差异 0 道**，输入 token 总量两轮完全
相同（都是 718,603），中位延迟相差 20 ms 以内（3581 与 3562 ms）。作为对照，Jev 对同一个请求两次
运行之间会移动 ±2 道题（§1，评测 §5.6）。

这就是上面那个 +3 / −3 能被当作"差异"来引用的原因：它不是采样。如果是一次 Jev 对一次 decider，
"3 道题"与噪音分不开；decider 稳定之后，诚实的说法是**两个模型犯的错不同，而且这两句都能复现**。
保留的警告只针对样本量（65 道正例分辨不到 ±2 以内），不针对模型。

### 4.2 拒答那 4 道是门槛假设，不是能力差

服务路径在 `none_of_these` 概率达到 `NONE_GATE_THRESHOLD` 时拒答（0.15，
`scripts/skill_reco/suggest.mjs:94`）。这个常数不是模型无关的：它的注释记着，交叉验证在 Jev 上
逐折选出 0.11–0.17，因为那是 Jev 两组之间那条空带的边。

decider 的分布比 Jev 极化得多：

| | Jev | decider |
|---|---|---|
| 有答案题里 `none` ≥ 0.01 的 | 13/65 | **0/65**（最大 0.004） |
| 应拒答题里 `none` < 0.15 的 | 1/35 | 4/35（中位 0.864） |
| 首答概率 > 0.5 的题 | 62/65 | 64/65 |

所以同一个 0.15 在两个模型身上问的是两件不同的事：对 Jev 它落在空带里；对 decider 它是一条几乎
没有样本经过的线。把**同一批答案**换一条切线重新计分（不重跑，只改阈值）：

| 门槛 | decider 首答正确 | 首答∈参照集 | 误拒 | 正确拒答 |
|---|---|---|---|---|
| 0.15（现行） | 95.4% | 96.9% | 0% | 88.6% |
| 0.01 | 95.4% | 96.9% | 0% | 94.3% |
| 0.005 | 95.4% | 96.9% | 0% | 100% |

这是**假设，不是结果**，理由就在同一张表里：0.005 时，"最小的应拒答 `none`（p037，0.005）"与
"最大的有答案 `none`（0.004）"只差 0.001。一条能把一个集合拟合到小数点后三位的切线，是被这个
集合拟合出来的。0.005 下 100% 正确拒答只说明 decider 自己在**这 100 道题上**是可分的，不说明新题
上的切线该在哪。要确认它得用留出集——第二批 gold，或者等 242 个技能的目录重出 gold 之后（§2）
——一半选门槛、另一半打分。

在那之前 `NONE_GATE_THRESHOLD` 保持 0.15。改它今天就是改 Jev 的产品行为，不能搭在模型对比里一起做。

## 5. 测试环境是怎么跑通的

本页上一版停在一条开放项上：`pplx-decider-v1.2` 在公开网关回 `model_not_found`，而
`https://test.future-os.cn` 不解析，所以那次评测在等一个 base URL 和一个模型 id。两个都有了，而
**记下"什么变了"比记下"能跑了"更重要**。

- **域名现在能解析。** `test.future-os.cn` 有 DNS 应答（116.62.200.165，与 `future-os.cn` 同一地址），
  并对外提供 `/api/v1/systemone`。
- **账号本来就指向它。** `~/.future/agent/auth.json` 的 `future` 项里 `base_url` 是
  `https://test.future-os.cn/api`，所以默认客户端（不带 `--base`）打的就是测试环境——这就是为什么
  `decider-run.mjs run … --model …` 就是全部命令。
- **模型 id 是 `pplx-decider-v1.2`。** 在部署上验过：`pplx-decider` 与 `decider-v1.2` 回
  `model_not_found`，`jev-latest` 也回，而 `jev` 能解析。`decider` 是它接受的别名、就是同一个模型：
  返回的答案逐字节相同，且响应的 `model` 字段写的是 `pplx-decider-v1.2`。本页所有运行都写全名。
- **公开网关不再是可用的对照。** 用本账号这把 key，`https://future-os.cn/api/v1/systemone` 回的是
  `auth_required` 而不是 `model_not_found`，所以"公开网关不提供它"已经不能用单次调用证明了。对比
  在测试环境上做，这与报告的意图一致。
- **首次跑通：2026-11-09。** 一次 5 题冒烟，然后同一时段内 Jev 一轮、decider 两轮（记录时间戳
  10:51–11:02，UTC+8）。

## 6. 两个模型之间卡住的是延迟，不是准确率

decider 的延迟不是长尾，是地板：100 道顺序题里最小 **3,481 ms**，中位 3,581 ms，p90 3,650 ms，
最大 3,976 ms。Jev 整条分布落在 575–877 ms 之间。

服务路径吸收不了这个。`agent/src/skill_reco/mod.rs:50` 把 `TIMEOUT` 定在 2500 ms，有意放在每个
客户端自己的死线**之内**（`RECOMMEND_TIMEOUT_MS = 3000`，
`desktop/src/features/agent/useSkillRecommendation.ts:63`），这样慢的推荐是**被判定**为失败，而
不是让用户白等之后才被放弃。每次调用 3.5 秒，这个判定每次都会命中。而且这不只是少一张卡片：连续
两次瞬时失败会让推荐器进入 30 秒停问（`agent/src/skill_reco/mod.rs`），那段时间连连接都不开——
所以照现状换模型，等于卡片**彻底不再出现**，而且是静默的，正好是那份诊断文档存在的理由。

准确率也补不回这个代价：总数是平的（93 对 93），错题不重叠，唯一明显领先的一项是首答多 3 道，
而 3 道正好是这批题的分辨极限。

所以结尾不是"选 Jev 还是 decider"，而是：**任何换成 decider 的动议都从死线开始**——要么服务路径的
超时提到约 5 秒、客户端预算提到约 6 秒（意味着用户要等约 3.6 秒才看到卡片，而这个特性目前 0.7 秒
以上就已经看不见），要么部署侧把这次调用砍掉约 1 秒。在这两件事发生之前，decider 的准确率是一个
关于产品用不上的延迟的数字。

## 7. 这些数能说明什么、不能说明什么

- 65 道正例 + 35 道负例，一次运行只能分辨约两道题的差异（§1，评测 §5.6）。§4.1 对 decider 收窄了
  这条——它两轮完全一致——但没有把集合变大："decider 首答好 3 道"是可复现的，同时也仍在 65 道题
  能证明的范围之内。
- gold 是 `kimi-k3` 的判断，不是人工标注。所以"有没有挑中出题时用的那个技能"（`source_skill`，
  独立于模型）比"第一个名字是否逐字相同"更硬。
- 延迟与价格属于服务这次请求的那个 endpoint。测试环境的数字只描述测试环境；能跨环境带走的只有
  token 数与决策本身。
- §4.2 的门槛实验是在评测集上拟合的；它作为假设报告，在留出集验证之前不得变成线上常数。
