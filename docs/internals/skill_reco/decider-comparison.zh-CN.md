# 用技能推荐这套评测换一个决策模型打分：先校验装置

[评测](evaluation.zh-CN.md)只给一个模型（Jev）打了分。要把另一个决策模型（例如 Perplexity 的
`pplx-decider-v1.2`）放到同一道题上比，第一件要确认的不是"它多强"，而是**这套装置现在跑出来的
数还是不是报告里那些数**。本页记这次校验、校验必须冻结的技能目录，以及换模型时用的那条命令。

状态：下面的装置校验已完成；**第二个模型还没跑**，它的测试环境在这台机器到不了（§4）。

## 1. 装置校验（2026-11-02）

把 Jev 整个重跑一遍——同一批 100 题、同一份 `dataset/gold-v1.json`、同一条服务路径（一个 Choice
+ `none_of_these` 门控，即 `Suggester.rank`）、同一份 141 个技能的目录（§2）——与
`dataset/score.json` 里记录的数逐项对照：

| 指标 | `dataset/score.json` | 重跑 | 差 |
|---|---|---|---|
| 决策一致（n=100） | 93.0%（93） | 93.0%（93） | 0 |
| 首答正确（n=65） | 90.8%（59） | 90.8%（59） | 0 |
| 首答∈参照集（n=65） | 93.8%（61） | **95.4%（62）** | **+1.6 个百分点** |
| 正确拒答（n=35） | 97.1%（34） | 97.1%（34） | 0 |
| 误拒（n=65） | 1.5%（1） | 1.5%（1） | 0 |
| 首答 = 出题所用技能（n=65） | 93.8% | 93.8% | 0 |
| 输入 token，每题中位 | 8,765 | 8,749 | −16 |
| 延迟，中位 / p90 | 488 / 1224 ms | 685 / 787 ms | 见下 |

决策、首答、拒答、成本四项与报告逐字对上。两处需要各补一句。

**唯一动了的那项指标（首答∈参照集）可以逐题解释，不是装置有偏。** 把重跑结果与
`dataset/score.json` 的 `per_question.jev` 逐题比：**首答相同 95/100，推荐/拒答判定相同 98/100**。
翻转的只有 5 道，而且除了这一项之外互相抵消：

| 题目 | 报告那次 | 重跑 | 参照 | 影响 |
|---|---|---|---|---|
| p015 | `future-web` | `future-paper` | `[future-web, future-paper]` | 首答错，但仍在参照集内 |
| p028 | `future-explore` | 拒答（`none` 0.18 ≥ 0.15） | `[future-explore]` | 首答错；本次唯一的误拒 |
| p035 | `dnanexus-integration` | `latchbio-integration` | `[latchbio-integration]` | 改对 |
| p043 | `pyzotero` | `paperzilla` | `[paperzilla]` | 改对 |
| n032 | 拒答 | `future-deep-research` | `[future-web]` | 两边都错；这次它的误拒位置挪到了 p028 |

净值：首答 +2 −2 = 0；首答∈参照集 +2 −1 = +1（61 → 62）；正确拒答与误拒都还是 1/35 与 1/65，
因为本次唯一那处误拒换了身份（n032 → p028）。这正是评测 §5.6 量到的运行间采样波动——同一个请求
两次独立运行，首答相同 91/100、判定相同 97–99/100——本次的 95/100 与 98/100 落在这个范围内，
所以那 1.6 个百分点是噪音，不是偏差。引用这组数时仍要这样读：**一次运行只能分辨约 ±2 道题的差异，
再细的差别它看不出来。**

顺带值得记一笔：p035 与 p043 恰好是 §2.2.5 归给**被移除的第二次调用**的那两道（胜利依赖 SKILL.md
正文措辞）。这次服务路径只有一次调用，两道都自己答对了。这进一步说明那"3 道题 / 4.6 个百分点"
的差距在采样噪音之内，不是稳定的能力差。

**延迟不能跨天比。** 重跑中位更高（685 vs 488 ms）、p90 更低（787 vs 1224 ms），同一个 endpoint、
不同网络、不同时间；token 数一致说明载荷没变。延迟只在同一时段、同一网关下测的两次运行之间可比
——§3 里的两个模型就是这样比的。

## 2. 目录冻结在 gold 答案所依据的 141 个技能

`dataset/roster.json` 就是那次评测用的 141 个技能。新模型必须用它而不是当前的 `skills/` 子模块，
有两条理由：

- gold 答案是照着这批技能出的；目录一旦增删或改名，题目和参照答案都变了，分数就与任何东西都不可比；
- 选项表就是模型看到的全部世界。141 个选项约 8.7k 输入 token，每多一个技能就是每个请求都多一行
  （评测 §4.1）。

子模块现在已经长到 **242 个技能**（17 内置 + 225 第三方，同样由 `loadRoster` 读出）。242 仍在 254
个选项的上限内，所以在当前目录上跑仍是"一个 Choice"——但那是**另一道题**：它需要先重出 gold
（`ground-truth.mjs`）才谈得上打分，而且两个模型必须在同一批里跑，因为新 gold 的分类与旧分数不可比。

所以 `bench/decider-run.mjs` 把 `dataset/roster.json` 铺成一份临时技能树，交给仓库里那个
`loadRoster` 读——选项文本、顺序、220 字符截断都走发布路径，而不是另写一份等价实现。

## 3. 换一个模型怎么跑

```bash
cd scripts/skill_reco
# 先 5 题：这个 endpoint 到底会不会答一个合法的 Choice
node bench/decider-run.mjs run pplx-test --base https://<host>/api --model pplx-decider-v1.2 --limit 5
# 再全量，再对比
node bench/decider-run.mjs run pplx-test --base https://<host>/api --model pplx-decider-v1.2
node bench/decider-run.mjs compare jev-prod pplx-test
```

- 凭据用 `~/.future/agent/auth.json` 里的 `future` 项（和 agent 自己用的是同一份）；
  `FUTURE_API_KEY` 可覆盖，用于自带 key 的 endpoint。
- `--limit 5` 不是客套。换模型最常见的失败不是答错，而是**格式不合**——返回自由文本、一次给多个
  选项、或者没有 `none_of_these`——而 `Suggester.rank` 会把缺失的概率读成空分布，于是每道题都变成
  "很自信地拒答"。这次冒烟把一个格式错误变成报错，而不是等 100 题跑完才发现全废；它还会断言自己
  发的请求与服务路径发出的请求逐字节相同，因此这项检查不会与它要覆盖的提示词走散。
- 成本与时间：每题约 8.7k 输入 token，整批约 87.5 万；按 pplx-decider-v1.2 公示的 $0.02/Mtok
  约 $0.018，顺序跑约两分钟（默认顺序，因为并发请求量到的是网关排队而不是模型）。
- 记录落在 `runs/<name>/`（gitignore），每条带自己的配置（endpoint、模型、目录、门控阈值、
  stage-1 版本）。换配置重跑会重录，不会把旧答案当成新结果续上。

## 5. 这些数能说明什么、不能说明什么

- 65 道正例 + 35 道负例，一次运行只能分辨约两道题的差异（§1，评测 §5.6）。落在这条线内的模型，
  正确说法是"在这批题上没有观察到差异"，不是"等价"。
- gold 是 `kimi-k3` 的判断，不是人工标注。所以"有没有挑中出题时用的那个技能"（`source_skill`，
  独立于模型）比"第一个名字是否逐字相同"更硬。
- 延迟与价格属于服务这次请求的那个 endpoint。测试环境的数字只描述测试环境；能跨环境带走的只有
  token 数与决策本身。
