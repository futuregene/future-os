# Jev 技能推荐 demo

一边打字一边推荐技能：输入问题，用 TypeSafe Jev（System One 模型，`POST /v1/systemone`）
**一次调用**，从 `skills/` 子模块的**全部 141 个技能**（15 内置 + 126 第三方）里挑出最合适的那个，
或者明确判定"没有合适的技能"。带 100 道题的评测：**[evaluation.md](evaluation.md)**。

## 跑起来

**前置条件（两步，缺一不可）**

```bash
# 1) 取到代码，带上子模块 —— 141 个技能目录来自它
git clone --recurse-submodules https://github.com/futuregene/future-os.git
#    已有的 checkout 则拉 main 并初始化子模块：
#    git fetch origin main && git checkout main && git submodule update --init skills

# 2) 启动 —— 凭据自动取自 Future 账号（~/.future/agent/auth.json），无需任何参数
cd scripts/skill_reco
node server.mjs                                   # 默认 http://127.0.0.1:8791
```

启动日志里必须出现这一行，否则第 2 步没生效（界面会是空的）：

```
roster: 141 skills (builtin 15 + third-party 126) from .../skills
```

**凭据就是 Future 账号本身的 key，没有单独的 Jev key。** 推荐走平台网关
`{future_base_url}/v1/systemone`（当前 `https://future-os.cn/api`），鉴权用「已登录的 Future
账号」——也就是说**登录过就有，不用配**。

关于凭据：

- **默认从 `~/.future/agent/auth.json` 的 `future` 项读**（和 agent、桌面端、TUI 用的是同一份），
  可用 `FUTURE_API_KEY` 覆盖成一把临时 key。仓库里**没有** `.env`、也没有 key 的示例值。
- **浏览器侧看不到它**。页面只与本地服务通信，凭据始终留在 `server.mjs` 这个进程里，
  请求由服务端转发给网关。
- **别把 key 贴进 issue / 日志 / 截图**。`probe.mjs` 打印时只显示掩码
  （头 4 位 + 长度 + 来源），方便确认当前用的是哪一把。
- **`.gitignore` 已挡住运行产物**：`runs/` 是评测过程的逐题缓存（含接口返回内容），不进仓库。

没有凭据也能把界面点起来：既没有 `auth.json` 里的 `future` 项、也没有 `FUTURE_API_KEY`
时，服务会退回**本地 BM25 启发式排序**（页面会显著标注"本地回退"，那不是 Jev 的结果），
只用来看 UI 和接口形状。

其他参数（都有同名环境变量）：`--port` / `PORT`、`--skills` / `SKILLS_ROOT`、
`FUTURE_BASE_URL` / `FUTURE_MODEL`（默认跟随账号的 `base_url`，模型为 `jev`）、
`LOCAL_ONLY=1`（强制本地回退）、
`NONE_GATE_THRESHOLD=0.15`、`CHUNK_SIZE=254`、`SHORTLIST=3`、
`MIN_QUERY_CHARS=6`。

`SHORTLIST` **不参与判定**（判定只看"第 1 名 + none 概率"）：它只决定 API 返回给界面的候选条数，
也就是界面上显示几个候选卡片。改成 1 只是少显示两行；设成 0 才会破坏判定（`verdict` 读第一名）。
早先"复核前 3 名"的那次调用还活着时，它决定的是**给谁做复核**，现在那次调用已移除。

命令行自检（同样从环境变量取 key）：

```bash
FUTURE_API_KEY=你的key node probe.mjs                        # 验证 key + 跑一遍完整流程
FUTURE_API_KEY=你的key node probe.mjs "把这个 PDF 的表格抽成 markdown"
```

浏览器里：输入 ≥ 6 个字符开始推荐；停顿后自动发起那次调用（也可 ⌘/Ctrl+Enter 立即触发）。
右上角徽标显示当前后端，`本地回退` 表示没走 Jev。底部三个 tab：候选 / 全部排名 /
调用详情（真实请求 JSON 与 usage）。

## 它怎么工作

```
用户输入
  │
  └─ 一次调用（路由）：一个 Choice，把 141 个技能做成选项，外加一个 none_of_these
        问："`request` 需要 `criteria` 中的哪个技能，还是都不需要？"
        题面：每个选项 = 技能名 → 一行描述（整张表只写一次，约 8.8k token）
        → 拿到两件事：谁最合适（对真候选的概率） + 是否都不合适（对 none 的概率）
     拒答：none 的概率 ≥ 0.15 → 判定没有合适技能；否则推荐概率最高的那一个
```

**为什么只有一次调用。** 曾经有第二次调用：把 top-3 候选连同完整 description 与 SKILL.md 正文再问
一遍，每题一道 noul（另有一个 fit 阈值）。它在 97% 的放行题上只是重复确认第一次的答案，却要求每次
请求多付一个网络往返。三种做法的实测（`bench/drop-stage2.mjs`，同一批记录上的配对比较）：

| 做法 | 首答正确 | 首答∈参照集 | 第二次调用 | 延迟 p50 | p90 | 费用/题 |
|---|---|---|---|---|---|---|
| **① 只一次调用（本版）** | 59/65 = 90.8% | 93.8% | **0/65** | **488 ms** | **1224 ms** | **¥0.00265** |
| ② 只在没把握时才发第二次（上一版） | 62/65 = 95.4% | 96.9% | 20/65 | 526 ms | 1338 ms | ¥0.00274 |
| ③ 总是两次调用 | 62/65 = 95.4% | 96.9% | 65/65 | 772 ms | 1410 ms | ¥0.00295 |

所以移除它的代价是 **3 道题（4.6 个百分点）**，换来 p50 −284 ms、p90 −186 ms、成本 −10.1%。

**注意 ② 在本次数据上严格优于 ①**：同样的质量，只比 ① 多 38 ms 中位延迟——因为那 3 道被改判的题，
路由 top-1 概率只有 0.77 / 0.36 / 0.39，全都远低于 0.95，② 一次不落全抓到了。本版按"只保留一次调用"
发布；恢复 ② 是一处改动，完整证据在 [evaluation.md](evaluation.md) §2.2.5 与 §4.5。

**一个要一起读的限定**：那 3 道里有 2 道（p019、p035）的题面用词与获胜技能的 SKILL.md 正文重合、
而与它的 description 不重合（p019：cloud / platform / sciences）。参考答案是照 SKILL.md 出的，题面
因此借了正文的词汇，而只有第二次调用能看到正文——所以那是真实优势的**上界**，不是期望值。

**单次调用的提示词已经调到头了。** 这一点单独测过：14 个变体、4 批、**放进同一个请求**成对比较
（这样运行波动会抵消，见下），没有一个比现在的写法更好——更短的提问会丢 4 道拒答（"选 none 不算
兜底"那句许可是承重的）、把提问写中立会丢 2 道拒答、把 none 选项写详细反而多推 2 道、描述减半会丢
4 道答案，而 description 长度扫过 110/150/180/190/220/240/不截断，**220 正好是拐点**（再短一道一道
丢答案，再长一道不多）。见 [evaluation.md](evaluation.md) §2.2.6。

所以**剩余与两次调用版的差距是信息差，不是措辞差**：那几道题需要读 SKILL.md 正文，而选项表里只有
description。要补回来只有把第二次调用加回去这一条路。


**为什么用 Choice 而不是 141 道并行的 noul**：两者质量相同（5 折留出验证都是 63/65），
但 Choice 只要**约一半的 token**（8.8k vs 21.4k/题）——noul 必须把"问题模板 + criteria"
重复 141 遍，Choice 只写一次。

**为什么 Choice 里必须有 `none_of_these`**：这是关键。Jev 不会说"都不合适"，而一个不含
none 的 Choice **必须**指认一个赢家。早先没有 none 时，只能另问一道"需不需要技能"来当门控，
结果造成 8–9 道误拒（首答正确掉到 84.6%）。把"都不合适"做成**选项**、让它在同一个问题上和
真候选同台竞争之后，拒答变得干脆（误拒 0），质量回到 95%+。

**为什么只有这一个逃逸选项**：试过再加"不止一个合适"和"需要的技能不在表里"（§2.2.7）。
前者 100 道题里**一次都没被选中**——流程要的是"调用哪一个"，而"好几个都合适"不是这个问题的答案；
后者用得很准（3 次全部命中"点了目录外工具"的题），但那些题原来就被 none 拒掉了，而它从 none 那里
分走概率、吃掉了门控的余量，反而多推 1 道。**根本原因**：门控读的是 none 占多少**份额**，
概率和恒为 1，所以**加选项会悄悄重新标定唯一的拒答信号**——加选项不是中性操作。

**为什么默认"全部放一块"**：141 个技能放进一个 Choice 就够用，实测与分块（每块 18/30/47 个）
**质量完全相同**（留出均 63/65），而单块省掉一次"跨块重排"请求，便宜 9%。
所以默认值是**一块能装下的最大技能数（254）**，含义是"不撞到 API 上限就不拆"。
唯一需要分块的情况是**技能表超过 254 个**：一个 Choice 最多 **255 个选项**（实测，见下），
而 none 选项也占一个名额。超过时设 `CHUNK_SIZE`（如 18）即启用分块 + 最终 Choice 的路径，
代码已就绪并有留出验证；`CHUNK_SIZE=255` 会在启动时直接报错并说明原因，而不是每个请求 400。

**"255 个选项"是实测的，而且 none 算一个**：`bench/option-limit.mjs` 发 253/254/255/256 个选项，
255 通过、256 被拒（`400 Too many choices. Must have at most 255 choices.`）。所以每块
**技能数上限是 254**，不是 255。

**拒答为什么是阈值**：Jev 只输出概率，所以"该不该推荐"必须由调用方决定。做成显式阈值的
好处是可解释（界面直接显示"none 概率 0.71 ≥ 0.15，所以拒答"）且可调。
这个阈值是个很宽的平原：0.1–0.9 的结果几乎一样，因为该拒的题 none 概率在 0.9 以上、
该推荐的接近 0，中间是空的。

| 阈值 | 默认 | 作用 |
|---|---|---|
| `NONE_GATE_THRESHOLD` | 0.15 | Choice 给 none_of_these 的概率，达到就拒答 |
| `CHUNK_SIZE` | 254（一块） | 每个 Choice 放几个技能；上限 254（255 个选项 − none），技能表超过它就必须调小 |
| `FITS_THRESHOLD` | 0.75 | **不参与服务**：被移除的那次调用的阈值，现在定义在 `bench/second-call.mjs` |

## 100 题上的成绩

评测细节、题集构造、成本口径、局限都在 [evaluation.md](evaluation.md)
（100 道题：65 道从技能文档生成、35 道手写"无技能可用"；参照答案由 `future/kimi-k3` 给出；
只评 top-1）。

| 系统 | 决策一致 | 首答正确 | 正确拒答 | 误拒 | 成本/题 | 延迟/题 |
|---|---|---|---|---|---|---|
| **Jev（本 demo，一次调用）** | 93.0% | 90.8% | 97.1% | 1.5% | **¥0.0027** | **0.49 s** |
| Jev（两次调用，已移除） | 96.0% | 95.4% | 97.1% | 1.5% | ¥0.0030 | 0.77 s |
| deepseek-flash | 95.0% | 93.8% | 97.1% | 0% | ¥0.0249 | 1.75 s |
| embedding 检索（本地 omlx） | 67.0% | 64.6% | 71.4% | 16.9% | 本地算力 | 0.015 s |

按"预测落在参照答案集合内"算（12/65 道题参照给了多个可选答案）：首答正确 **93.8%**；
按出题所用技能这个独立对照（65 题）：第一顺位命中 **93.8%**。

**⚠️ 这些分数的精度上限**：同一套代码三次独立运行给出的首答正确率是 93.8% / 93.8% / **90.8%**
——约 ±2 道题的波动。所以"Jev 与 deepseek-flash 孰高孰低"在这个题量上分不出来；报告里所有
"多个 X 就多对几道"的结论都是同批记录内的**配对**比较，不受此影响。
见 [evaluation.md](evaluation.md) §5.6。

错题都逐道查过根因（[evaluation.md](evaluation.md) §3.3）：7 道里只有 3 道是真正的推荐错误
——两道是两个同族库而题面不足以区分、一道是"问该用什么工具"的标注歧义；另有两道的预测其实落在
参照集合内（是评分只比第一个造成的假错），还有两道是被移除的那次调用当时能改对的。

成本口径（1 credit = ¥1；Jev 按公示价 $0.042/Mtok、输出免费，美元按 ¥7.2/$ 折算）。
演化过程：最初 141 道 noul 每题 21,357 token → 换成单 Choice + none 后 **8,765（−59%）**，
而且服务路径只剩这一次调用。

## 代码结构

```
scripts/skill_reco/
├── server.mjs        本地 HTTP 服务：静态页 + /api/suggest（key 只留在这个进程里）
├── roster.mjs        从 skills/builtin + skills/third-party 读 SKILL.md，拼出技能目录
├── suggest.mjs       一次 Choice + 一个门控阈值（Jev 与本地回退共用同一套判定）
│                     模块里只有服务路径：被移除的那次调用已移到 bench/second-call.mjs
├── jev.mjs           System One HTTP 客户端（凭据取自 Future 账号；429/529 退避重试）
├── localRank.mjs     key 不可用时的 BM25 字面回退（明确标注，不是 Jev）
├── probe.mjs         命令行：验证 key + 跑一遍完整流程
├── public/           前端页面（无构建、无依赖）
├── bench/second-call.mjs  被移除的那次调用（只为让评测可复现，服务路径不引用）
└── bench/            100 题评测（题集生成 / 参照答案 / 各系统作答 / 打分 / 报告）
                     读任何对比前先看 stage1-stability.mjs：同一套代码的运行间波动 ±2 道题
                     stage1-prompt.mjs 是提示词变体实验（同请求内配对，§2.2.6）
                     check-parity.mjs 断言本目录与 agent 的机制逐项一致（见下节）
```

`bench/` 里每一步都按题目 id 缓存，重跑只补缺失的题；缓存带配置指纹，改了阈值或请求形状
会自动重跑，不会把旧答案当新结果。

**两个守卫，改完这个目录应该跑一遍：**

```bash
node check-doc-refs.mjs                                     # 文档里提到的脚本必须都存在
AGENT_SKILL_RECO=.../agent/src/skill_reco/mod.rs \
  node bench/check-parity.mjs                               # 本目录与 agent 的机制逐项一致
```

两个都会在发现问题时退出码非 0，并且——这一点同样重要——**在"什么都没测到"时也报错**
（读不到文档、读不到 agent 源码），而不是打印一个通过。`check-doc-refs.mjs` 写完当天就抓出两个
引用已删脚本的悬空引用，`check-parity.mjs` 的默认路径也曾经少算一层、只有在显式传
`AGENT_SKILL_RECO` 时才工作。

## 与生产代码的关系

产品的推荐功能在 agent 里用 Rust 实现（`agent/src/skill_reco/mod.rs`），三端（桌面 / TUI / 移动）
都调它。这个 demo 是**另一份实现**（JS），所以必须说清两边各自负责什么。

**实验脚本必须留在 JS —— 这是设计，不是偷懒。** `bench/` 里那 37 个脚本存在的意义，就是**去改
生产特意固定下来的东西**：提示词措辞（宽松 vs 严格）、载荷形态（描述 220 vs 256、带不带中文）、
分块大小、门控阈值、选项集合。如果它们跑生产代码，就一个旋钮都没有——那么现在的这些常量
（0.15 / 254 / 220）**根本推导不出来**。它们是造出生产的工厂，不是产品本身。

**服务路径（`suggest.mjs` + `jev.mjs` + `roster.mjs`）与生产对齐，并由守卫逐项盯着。** 两边今天一致：

| 项 | demo | 生产 | |
|---|---|---|---|
| 端点 | `{账号 base_url}/v1/systemone` | 同 | 一致 |
| 凭据 | `auth.json` 的 `future` 项 | 同 | 一致 |
| 模型 | `jev` | 同 | 一致 |
| 门控阈值 | 0.15 | 0.15 | 一致 |
| 候选上限 / 描述长度 | 254 / 220 | 254 / 220 | 一致 |
| none 选项文案 | 逐字相同 | 逐字相同 | 一致 |
| `instructions` | 逐字相同的字符串 | 同 | 一致 |
| 计价 | `$0.042/Mtok`、`¥7.2/$` | 同 | 一致 |

`instructions` 那一项曾经**不一致**：demo 发的是对象 `{question, how_to_judge}`，生产发的是单个
字符串。网关两种都接受，所以不会报错——但也意味着 demo 不是生产的忠实替身，两边可以静默漂移。

现在这些值由 `bench/check-parity.mjs` **从两侧源码读出后逐项比对**（不是两边各写一个测试各自断言
自己的副本——两个都绿的测试互相矛盾，正是它要抓的失败）：

```bash
AGENT_SKILL_RECO=/path/to/agent/src/skill_reco/mod.rs node bench/check-parity.mjs
# 打印 11 项 + 一条上限不变式；任何一项漂移则退出码 1
# 默认路径是 <repo>/agent/src/skill_reco/mod.rs（两个分支都进 main 之后的位置）
```

守卫还查一条**内部不变式**：`CHUNK_SIZE + 1 == MAX_CHOICE_OPTIONS`（254 候选 + 1 个 none = 255，
正好是 API 上限）——两个数分处两个文件，靠这条把"改了一个忘了另一个"挡住。

demo 里的价格数字原本**散落在 9 个脚本里内联**（`0.042`、`7.2` 共 15 处）。这些也一起收敛到了
`jev.mjs` 导出的 `USD_PER_MTOK_INPUT` / `USD_TO_CNY`：报告里的钱数一旦用了过期单价，比不写钱数更糟，
而单价现在只有一处可改、且被守卫盯着。

**关于"能不能直接用生产代码"**：服务路径可以，但代价是 demo 会失去它最有用的部分——
`suggest_skill` 只返回**最终那一个技能**，不返回 top-3、概率和门控值（那些只在 agent 日志里）。
demo 的界面正是靠这些数字说明"为什么推荐它"。所以要把 demo 换成直接调 agent，就得同时给 RPC 加上
这些诊断字段（附加字段、不破坏兼容），否则界面只剩一行结论。**当前取舍：保留 JS 服务路径（能看排序
与门控），并用上面的守卫保证机制与生产逐项一致。**
