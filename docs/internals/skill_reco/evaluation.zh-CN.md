# 技能推荐评测：Jev 与检索式、通用对话式方案的对比

**任务**：给定 141 个技能的目录和一句用户请求，判断该用哪个技能，或判断不需要任何技能。
**结论**：Jev 用**一次调用**做到首答正确 90.8%、该拒答时拒答 97.1%、误拒 1.5%，每题 0.49 s、
¥0.0027。这个水平**与对照的通用对话模型持平或略低**，但明显更便宜更快，而且拒答是一个可解释的
概率而不是提示词行为。本地 embedding 不能被单独使用（它没有"该不该推荐"的概念）。

> **这一版把流程从两次调用收成了一次**：曾经的第二次调用（把 top-3 候选连同 SKILL.md 正文再问一遍）
> 已从服务路径移除。它当时能多对 3 道题（4.6 个百分点），但每次都要多一次网络往返。
> 移除的代价与理由、以及"只在没把握时才发第二次"这个中间方案的实测对比，见 §2.2.5 与 §4.5。

| 系统 | 决策一致 | 首答正确 | 首答∈参照集 | 正确拒答 | 误拒 | 成本/题 | 延迟/题 |
|---|---|---|---|---|---|---|---|
| **Jev（一次调用，本版）** | 93.0% | 90.8% | 93.8% | 97.1% | **1.5%** | **¥0.0027** | **0.49 s** |
| Jev（两次调用，已移除） | 96.0% | 95.4% | 96.9% | 97.1% | 1.5% | ¥0.0030 | 0.77 s |
| deepseek-flash（同题面同提示词） | 95.0% | 93.8% | 98.5% | 97.1% | 0% | ¥0.0249 | 1.75 s |
| embedding 检索（本地 omlx） | 67.0% | 64.6% | 72.3% | 71.4% | 16.9% | 本地算力 | 0.015 s |

**读这张表前请先看 §5.6**：同一套 stage-1 代码在两次独立运行里给出过 93.8% 与 90.8% 的首答正确率，
也就是说本报告的 65 道正例只能把差异分辨到约 ±2 道题。上面"持平或略低"的措辞就是按这个精度写的。

## 1. 背景：Jev 是什么

Jev 是 TypeSafe 的 System One 模型的品牌名。它和对话模型不是一类东西：**它不生成文字，
只对给定的内容做判断**。

### 1.1 调用形状

```
POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer <key>

{
  "state":     <要被判断的内容：字符串 / 对象 / 数组>,
  "model":     "jev-latest",
  "questions": { "<你起的名字>": <题目对象>, ... }
}
```

一次调用里可以放**任意多道题**，它们对同一个 `state` **并行求值**，返回按同样的名字索引：

```json
{ "model": "jev-1.13.0",
  "answers": { "<你起的名字>": <答案对象>, ... },
  "usage":   { "input_tokens": 272, "output_tokens": 20 } }
```

### 1.2 只有三种题型

| 题型 | 问什么 | 答什么 |
|---|---|---|
| **`noul`** | 一个是/否问题 | `noul`：0–1 的数 = "回答是 yes 的概率" |
| `choice` | 从你给的选项里选一个 | `choice`（选中的选项）+ `probabilities`（**各项概率之和恒为 1**）+ `confidence` |
| `score` | 按你给的等级给内容打分 | `score`（按概率加权的等级值）+ `legend` + `probabilities` |

`criteria` 是题目的补充说明：noul 里写"是/否各代表什么"，choice 里**每个选项一个 key**
（也就是选项清单），score 里是有序的等级描述。`instructions` 可以是字符串，也可以是
对象（把问题放一个字段、它要引用的数据放其他字段，再用反引号 `` `字段名` `` 指代）。

### 1.3 用 Jev 必须知道的三件事

1. **`noul` 之间互相独立，`choice` 是一个必须分配完 100% 的分布。** 前者天然可比大小
   （141 道并排也能排序），而后者永远会有一个"赢家"（哪怕所有选项都不合适）。
   本项目同一批题上的实测：三个并列 noul 的取值之和平均 1.78（范围 0.20–2.89），
   也就是说它们**不是**一个归一化的分布；换成 choice 就必然会被强制成和为 1。
2. **它不会说"都不合适"。** 这是设计使然——它只吐概率。所以"拒答"必须由调用方决定，
   而两条路本项目都用了：给 choice 一个 `none_of_these` 选项，让"都不合适"在**同一道题里**
   和真候选竞争（而不是另问一道"需不需要技能"，那样问会多出 8 道误拒），再对那个概率设阈值；
   复核那次调用则对 3 个候选的 fit 概率设阈值（见 §2.2、§2.3）。
3. **计费只算输入 token**（$0.042 / 百万 token，**输出 token 免费**，官网
   docs.typesafe.ai/models）。所以"把技能文档塞进题面"是主要开销来源。

## 2. 方法

### 2.1 技能目录

评测对象是 `skills/` 子模块里的**全部**技能，共 **141 个**：15 个内置（builtin）
+ 126 个第三方（third-party，覆盖生物信息、化学、临床、数据科学等）。每个技能可用的字段：

| 字段 | 来源 | `scanpy` 的实例 |
|---|---|---|
| `name` | SKILL.md 的 frontmatter `name:` | `scanpy` |
| `description` | SKILL.md 的 frontmatter `description:`（全文，不截断） | "Standard single-cell RNA-seq analysis pipeline. Use for QC, normalization, …"（434 字符） |
| `chinese_description` | 技能目录 `skills.json` 里的 `description_zh` | "标准单细胞 RNA-seq 分析：QC、标准化、降维、聚类、差异表达"（34 字符） |
| `instructions_excerpt` | frontmatter **之后**的正文前 900 字符 | "# Scanpy: Single-Cell Analysis ## Overview …" |

### 2.2 推荐器结构：一次调用、一个阈值

```
用户输入
  │
  └─ 调用 1（路由）：一个 choice，选项 = 141 个技能 + `none_of_these`
        题面：技能名 → description（截断 220 字符），整张选项表只写一次，约 8.8k token
        → 一个概率分布（各项之和恒为 1）+ 一个 none 概率
     门控：none 概率 ≥ 0.15 → 拒答；否则推荐概率最高的那一个
```

判定只用一处：`none_of_these` 的概率（`NONE_GATE_THRESHOLD`）。它是模型自己的答案——Choice 被要求
在"没有技能合适"时选它——而不是我们从某个打分上切的阈值。为什么用这种方式做拒答见 §1.3 第 2 条。

**曾经的第二次调用**（把 top-3 连同完整 description 与 SKILL.md 正文再问一遍，每题一道 noul，
另有一个 fit 阈值）已不再服务：它的取舍见 §2.2.5，完整证据见 §4.5。代码里保留了它，因为评测脚本
在用它生成记录下来的对照数据；`server.mjs` 从不调用它。

### 2.2.1 路由：一个 Choice（带 none 选项）就够，而且省一半钱

路由层试过四种写法。同一批 100 题、只换路由。**注意口径**：这些比较是在当时的两次调用设置下做的
（下游固定为那次复核），因为要比较的是"路由给出的候选好不好"；后来复核被移除（§2.2.5），但**路由
本身的选择不受影响**——它只取决于候选质量，而候选质量由本节度量。

| 路由写法 | 首答正确（留出） | 误推 | 每题 token | 费用/题 |
|---|---|---|---|---|
| 141 道并行 noul + 独立 needs_skill 门控 | 62/65 = 95.4% | 2/35 | 21,357 | $0.00090 |
| **一个 Choice（141 选项 + `none_of_these`）** | **63/65 = 96.9%** | **1/35** | **10,372** | **$0.00044** |
| 分块 Choice（每块 18 个，各带 none）+ 最终 Choice | 63/65 = 96.9% | 1/35 | 11,371 | $0.00048 |
| 一个 Choice（141 选项）**不带** none，另问一门控 | 55/65 = 84.6% | 0/35 | 10,410 | $0.00044 |

**两个发现，其中一个推翻了我早先的判断。**

**发现一：`none` 选项是必需的，而且它是唯一的拒答办法。** 对比最后两行：同样是单 Choice，
没有 none 时只能另问一道"需不需要技能"，结果 8 道该推荐的题被误拒（84.6%）；
把"都不合适"做成**选项**、让它在同一道题里和真候选竞争后，误拒归零、首答正确回到 96.9%。
原因在于问法：有具体候选摆在面前时，"这些都不行"是一个可以逐项比较的判断；
没有候选时，它变成一个抽象问题，更容易答偏。

**发现二（推翻早先判断）：概率饱和不影响结果，所以分块没有必要。**
我早先否掉单 Choice 的理由是饱和——141 个选项里只有中位 **2 个**拿到非零概率
（48/100 的题第 2、3 名恰好为 0），于是"前三名"看起来是并列的 0。这次实测发现：

```
正确技能进入交给复核的前三名：
  单个 Choice（141 选项）   65/65 = 100%
  分块 18（8 块）           65/65 = 100%
```

因为**正确技能通常就在赢家位置**（对真候选的概率中位 0.89），第 2、3 名的 0 只是填充。
饱和伤的是候选的**多样性**，不影响它**是否包含正确答案**——但这也是移除复核之后要承认的代价：
第 2、3 名既然多半是并列 0 的填充项，就没有可靠的"第二意见"可以拿来纠错（§2.2.5）。
既然拆块不带来收益，就不该付它的代价：分块要多一次"跨块重排"请求（+9%），
所以**默认不拆**。

**保留分块的唯一理由**：一个 Choice 最多 **255 个选项**，所以技能表超过 254 个时必须分块。
代码保留了这条路径（设 `CHUNK_SIZE` 即启用），并由本节的实验与留出验证覆盖。

**上限是实测的，而且 none 算一个名额**（`bench/option-limit.mjs`）：发 253 / 254 / 255 / 256 个选项，
255 通过、256 返回 `400 Too many choices. Must have at most 255 choices.`。所以每块技能数的上限是
**254**（= 255 − none），`CHUNK_SIZE` 的默认值就是这个 254，含义是"不撞到 API 上限就不拆"。
`CHUNK_SIZE=255` 会在**模块加载时**抛错并写出原因（`suggest.mjs` 的守卫），而不是让每个请求都
撞一次 400 —— 这个 off-by-one 是真实存在的坑，因为 API 文档只说"最多 255 个选项"，没说 none 算不算。

**阈值。** 门控读的是"最终 Choice 给 none 的概率"，阈值 0.15。它是个很宽的平原：
0.1–0.9 结果几乎相同，因为该拒答的题 none 概率在 0.9 以上、该推荐的接近 0，中间几乎没有样本
（`stage1-chunked-sweep.mjs`）。0.15 落在空带底部，不是调出来的尖峰。

**成本为什么能减半。** 技能正文（约 8.6k token）两边都要付，差别在模板：noul 版把
"问题句 + criteria"重复 141 遍（约 12k token），Choice 版只写一次。

### 2.2.2 留出验证

上面的阈值如果是在同一批 100 题上选出来的，就只能说明"没有观察到差异"。5 折留出
（`chunked-cv.mjs`、`onechunk-compare.mjs`：每折只在另外 4 折上选阈值，再用到没见过的第 5 折，
两边的误推预算一致）：

| 误推预算 | 141 道 noul | 单 Choice + none | 分块 18 | 分块 30 | 分块 47 |
|---|---|---|---|---|---|
| 0（零误推） | 40/65 = 61.5% | 55/65 = 84.6% | **57/65 = 87.7%** | 55/65 = 84.6% | 55/65 = 84.6% |
| **1（= 发布工作点）** | 62/65 = 95.4% | **63/65 = 96.9%** | **63/65 = 96.9%** | 60/65 = 92.3% | 60/65 = 92.3% |

**结论：单 Choice 与最好的分块方案在留出集上并列第一（63/65），成本低 9%；
两者都比原来的 141 道 noul 好一点、便宜一半。** 零误推预算下分块略好，但那个预算不是
发布版的工作点（发布版接受 1 道误推），所以不构成选择它的理由。
（这两行都是"两次调用"口径下测的，同 §2.2.1 的说明。）

**局限**：每折只有 13 道正例，65 道正例的 95% 置信区间是 [89.5%, 99.2%]，宽度近 10 个百分点。
所以正确的读法是"**没有观察到质量差异**"，而不是"证明了等价"。要钉死差异需要 300–500 道题。

### 2.2.3 只看路由：它能排出什么

这一节就是发布版的全部能力（`stage1-ranking.mjs`）。下面的两组数字分别来自两次独立运行，
差异本身就是 §5.6 要说的运行间波动：

| 看什么 | 单个 Choice（发布） | 141 道 noul（较早的方案，对照） |
|---|---|---|
| 正确技能排在**第 1 名** | 61/65 = 93.8%（另一次运行 60/65 = 92.3%） | 58/65 = 89.2% |
| 正确技能在**前 3 名** | 65/65 = 100% | 65/65 = 100% |
| 正确技能在**前 5 名** | 65/65 = 100% | 65/65 = 100% |
| 拒答（none ≥ 0.15 / top-1 noul < 0.70） | 34/35 = 97.1%，误拒 0–1/65 | 29/35 = 82.9%，误拒 1/65 |

以下是更早一次运行的同一张表（供对照，说明波动幅度）：

| 看什么 | 单个 Choice（发布） | 141 道 noul（较早的方案，对照） |
|---|---|---|
| 正确技能排在**第 1 名** | 61/65 = 93.8% | 58/65 = 89.2% |
| 正确技能在**前 3 名** | 65/65 = 100% | 65/65 = 100% |
| 正确技能在**前 5 名** | 65/65 = 100% | 65/65 = 100% |
| 拒答（none ≥ 0.15 / top-1 noul < 0.70） | 34/35 = 97.1%，误拒 0/65 | 29/35 = 82.9%，误拒 1/65 |

**但 Choice 那一行的"前 3/前 5"不能当召回率读。** 它是把 141 个选项的概率排序取前几名，
而这个分布会饱和：中位只有 **2 个**选项拿到非零概率，42/100 的题**只有 1 个**；
65 道有答案的题里有 **46 道**的第 3 名概率恰好是 0。也就是说除第 1 名以外，
"前 3"里的后两个位置是**并列 0 的填充项**，不是"另外两个候选"。
noul 那一行才是真正的排序（每个技能一个独立概率，中位 10 个非零），所以它的前 3/前 5 有意义。

两者的对比说明三件事：

- 发布的 Choice 版**第 1 名更准**（93.8% vs 89.2%），而且门控强得多（97.1% vs 82.9%）；
- 但候选**多样性**确实丢了：noul 版每题能给出多个真实候选，Choice 版只有 4/65 的题
  在第 2/3 名上有真候选（其余是填充）；
- 这**没有影响最终结果**——两种设计里正确技能都在前 3 名内，而复核对候选的要求只是
  "正确技能在名单里"（§2.2.1 最后一段）。

换句话说，花一半钱换掉 noul 版之后，代价落在了一个本次评测用不到的指标上。
成本拆分见 §4.4。

### 2.2.4 被移除的那次调用当时该放什么（记录用）

第二次调用是"同一句问法、更足的证据"：每个候选带上完整 description + SKILL.md 开头 900 字符。
这一节保留当时的字段取舍，因为**如果那条路重新启用，结论仍然适用**——已删的字段不要加回来：

| 字段 | 来源 | 长度 | 取舍 |
|---|---|---|---|
| `name` | SKILL.md frontmatter | 6 | 保留 |
| `description` | SKILL.md frontmatter `description:`（全文） | 434 | 保留（"招牌"） |
| `instructions_excerpt` | frontmatter 之后的正文前 900 字符 | 900 | **不能删**：只发 name+description 会让零误拒阈值从 0.79 坠到 0.29、拒答能力归零 |
| ~~`chinese_description`~~ | 技能目录 `skills.json` 的 `description_zh` | 34 | **已删**：成对 A/B（198 个「题×候选」配对）差值中位 0.000、端到端 0 道题变化；放进路由的选项表反而多出 1 道误拒 |
| ~~`tagline`~~ | — | — | **已删**：141/141 个技能里它都是 `description` 的字节前缀，纯重复 |

（`bench/stage2-zh.mjs`、`bench/stage1-zh.mjs`。测得 `instructions_excerpt` 与 `tagline` 两行的载荷实验
已随它们所研究的那次调用一起删除，结论保留在上表；本目录已没有脚本能复现那两个取舍。）

### 2.2.5 为什么只剩一次调用

第二次调用在 97% 的放行题上只是重复确认第一次的答案，却要求每次请求都多付一个网络往返。
三种做法在同一批记录上的实测（`bench/drop-stage2.mjs`，配对比较：三条路读同一批 stage-1 答案）：

| 做法 | 首答正确 | 首答∈参照集 | 第二次调用次数 | 延迟 p50 | p90 | p95 | 费用/题 |
|---|---|---|---|---|---|---|---|
| **① 只一次调用（本版发布）** | 59/65 = 90.8% | 61/65 = 93.8% | **0/65** | **488 ms** | **1224 ms** | **1401 ms** | **¥0.00265** |
| ② 只在没把握时才发第二次（上一版） | 62/65 = 95.4% | 63/65 = 96.9% | 20/65 | 526 ms | 1338 ms | 1542 ms | ¥0.00274 |
| ③ 总是两次调用 | 62/65 = 95.4% | 63/65 = 96.9% | 65/65 | 772 ms | 1410 ms | 1672 ms | ¥0.00295 |

三条结论：

1. **① 比 ③ 便宜、快、且只有 3 道题之差**（多对 3 道 = 4.6 个百分点）；这是移除它的直接理由。
2. **但 ② 严格优于 ①**：同样的质量（62/65），只比 ① 多 38 ms 中位延迟、3.4% 成本，却只在
   20/65 的题上付第二次调用。这次 3 道被 ① 丢掉的题，路由 top-1 概率分别只有 0.77 / 0.36 / 0.39
   ——**全都远低于 0.95，② 一次不落地抓到了**。
3. 所以"该不该有第二次调用"这个问题，答案取决于愿不愿意为 **+3 道题（4.6pp）** 换
   **+38 ms 中位延迟 / +114 ms p90**。本版按"只保留一次调用"的决策发布，理由是链路越短越好
   （少一次网络往返 = 少一种失败模式）。要恢复 ② 需要三处改动：把 `bench/second-call.mjs` 的
   `verifySecondCall` 接回 `server.mjs`、在 `suggest.mjs` 里加回那个"没把握才复核"的判断、
   以及它的阈值常量。代码还在（被移除的那次调用只是搬到了 `bench/`），证据在
   `bench/drop-stage2.mjs`。

**一个必须一起读的限定**：这 3 道"它多对的题"里有 2 道（p019、p035）的题面用词与获胜技能的
SKILL.md 正文重合、而与它的 description 不重合（p019：cloud / platform / sciences；
p035：python / cloud / automatic / no-code）。参考答案是照着 SKILL.md 出的，题面因此借了正文的
词汇，而只有第二次调用能看到正文——**所以它的优势是真实优势的上界，而不是期望值**（§4.5）。

### 2.2.6 提示词还能不能再调：14 个变体，4 批，结论是不能

这一节是**负结果**，但它有实际价值：一次调用的方案要再进一步，只能靠改提示词或改选项内容，
而这两条路都测过了，**没有一条比现在的写法更好**。同时它把两个"看起来可以删"的句子钉成了
承重结构，免得以后有人顺手删掉。

**方法比变体重要。** 同一套代码两次运行会在约 9% 的题上换第一名（§5.6），这个幅度和任何提示词
改动能带来的效果一样大。所以变体**不**分开发请求再对比，而是**放进同一个请求**作为多个 Choice
问题（`.state` 相同，各带自己的选项表），于是比较是配对的、运行波动抵消。代价是可能互相污染，
所以每一批都**包含发布版原文作为对照**，并与独立请求的同一份记录比对：

| 批次 | 变体数 | 对照 vs 独立请求的判定一致率 |
|---|---|---|
| A（怎么问） | 4 | **100/100** |
| B（选项写什么） | 5 | **99/100** |
| C（拆分 A 的混淆项） | 4 | **100/100** |
| D（描述长度扫描） | 4 | **100/100** |

污染可以忽略，所以批内比较可信。（`bench/stage1-prompt.mjs`，`--batch A|B|C|D|E`。
**E 批的用途不同**：它每次只放两张选项表，用来复核 D 批里“排在末尾”的变体——D 批五张表一个请求
（中位 30,526 token）把最后一个问题挤坏了，见下面的 D 批说明。）

**A：怎么问。** 发布版原文是最好的一行。

| 变体 | 首答正确 | 首答∈参照集 | 正确拒答 | 误拒 | 误推 |
|---|---|---|---|---|---|
| **发布版（对照）** | **61/65 = 93.8%** | **63/65** | **34/35 = 97.1%** | 0.0% | 1/35 |
| 更短的提问 | 61/65 | 63/65 | **30/35 = 85.7%** ✗ | 0.0% | 5/35 |
| 给"该选技能"下明确门槛 | 59/65 ✗ | 61/65 | 34/35 | 3.1% | 1/35 |
| 强调"通用助手能答就不用技能" | 56/65 ✗✗ | 58/65 | 34/35 | 6.2% | 1/35 |

两条要点：

- **"Choosing it is a normal answer here, not a fallback." 这句话是承重的**：删掉它（"更短的提问"）
  首答不变，但**拒答从 97.1% 掉到 85.7%**（多 4 道误推）。Jev 需要一个明说"选 none 不算兜底"的许可。
- **"强调通用助手能答就不用技能"看似对症下药，实际明显更差**（−5 道首答、误拒 6.2%）：
  它会过度拒答本该推荐的题。这与 §5.3 里那道"矩阵求逆"坏例的方向恰好相反——想靠提示词
  修它，代价是别的题先坏掉。

**C：把 A 里的混淆项拆开。** "更短的提问"同时改了两件事（缩短措辞 + 删掉那句许可），所以单独测
"只删掉'需要技能'这个前提"：

| 变体 | 首答正确 | 正确拒答 | 误拒 |
|---|---|---|---|
| **发布版（对照）** | **61/65** | **34/35** | 0.0% |
| 去掉「需要技能」的前提 | 60/65 | **32/35 = 91.4%** ✗ | 0.0% |
| 先问「要不要」再问「哪个」 | 60/65 | 34/35 | 1.5% |
| 选项描述放到 240 字符 | 61/65 | 34/35 | 1.5% |

**现在这句"有偏"的措辞（"The request needs a skill from `criteria`"）反而更好**：去掉它的前提
会让拒答掉 2 道。所以"把提问写得中立一点"这个直觉在这里是错的。

**B：选项里写什么。** 发布版的选项文本（品牌 description 截断 220 字符）也是最好或并列最好。

| 变体 | 首答正确 | 首答∈参照集 | 正确拒答 | 选项表规模 |
|---|---|---|---|---|
| **发布版（对照）** | **61/65** | **63/65** | 33/35 | 7,521 token |
| 选项描述减半（110 字符） | 57/65 ✗✗ | 59/65 | 34/35 | **3,890 token** |
| 选项描述不截断 | 60/65 | 63/65 | 34/35 | 13,279 token |
| 把 none 选项写清楚 | 59/65 ✗ | 61/65 | 34/35 | 7,551 token |
| 选项里加分类标签 | 61/65 | 63/65 | 34/35 | 7,960 token |

**"把 none 选项写清楚"是反效果的**（−2 道首答）：把"通用助手能答也算 none"写进选项描述里，
会推动模型过度拒答——和 A 批里"强调通用助手"那一条同因。"加分类标签"打平但更贵。

**D：描述长度扫到哪一格是拐点。** 选项表占整个请求的 86%，所以"短一点"是唯一有意义的成本杠杆：

```
110 字符 → 57/65      180 字符 → 59/65      240 字符 → 61/65
150 字符 → 58/65      190 字符 → 60/65      不截断   → 60/65
                        220 字符 → 61/65  ← 发布版
```

「256 字符」曾一度显示「100 道题全部拒答」，那是**实验装置的假象**，真因值得单独记一笔：

`stage1-prompt.mjs` 的缓存按**题号**索引（`runs/stage1-prompt-D/<id>.json`），而一个文件里存的是
**该批所有变体**。256 是在缓存已经写满 100 个文件之后才加进 `VARIANTS` 的，于是 `todo` 为空、
**根本没有重跑**，每份记录里都没有 `desc_256` 这个键；而评分函数里 `!r -> null -> 拒答`，
「没有数据」和「拒答」是同一个值，于是它被算成「100 道全拒答」。

已修两处：评分前先校验「题 × 变体」是否齐全，缺任何一个就**直接报错**并指出要删的缓存目录
（不再默默算出一组假分数）；另外写了 `bench/ctx-limit.mjs` 检验「一个请求里塞多张表」本身有没有问题——
把同一张发布版选项表重复 k 次放进一个请求，逐位置与单独请求的记录对比：

```
k=2  17,210 tok   位置 1:6/6  2:6/6
k=3  25,657 tok   位置 1:6/6  2:6/6  3:6/6
k=4  34,104 tok   位置 1:6/6  2:6/6  3:6/6  4:6/6
k=5  42,551 tok   位置 1:6/6  2:6/6  3:6/6  4:6/6  5:6/6
k=6  50,998 tok   位置 1:6/6  2:6/6  3:6/6  4:6/6  5:6/6  6:6/6
```

**每个位置都完全一致，包括第 6 张表**，所以「同请求内配对」（批次 A–E 的方法）在 5 张表
（约 34k token）以内是成立的。这一节早先归因的「上下文用满、末尾问题退化」是**错的**。

重跑后的 D 批（真实数据，对照 60/65）：

| 变体 | 首答正确 | 首答∈参照集 | 正确拒答 | 误拒 | 与对照不同的题 |
|---|---|---|---|---|---|
| 220 字符（对照） | 60/65 = 92.3% | 62/65 | 34/35 | 1.5% | — |
| 150 字符 | 58/65 = 89.2% | 60/65 | 34/35 | 1.5% | 4 |
| 180 字符 | 57/65 = 87.7% | 59/65 | 34/35 | 1.5% | 5 |
| 190 字符 | 60/65 = 92.3% | 62/65 | 34/35 | 0% | 2 |
| **256 字符** | **61/65 = 93.8%** | **63/65** | 34/35 | **0%** | 3 |
| （E 批独立复核）256 字符 | 62/65 = 95.4% | 64/65 | 34/35 | 0% | — |

所以 256 字符**不掉质量**（两次独立配对各多对 1 道，在噪音内），它的代价是纯粹的**价钱**。
单变体请求逐档量过（`bench/desc-cost.mjs`，同一批题、只发一张表，所以那个请求的
`input_tokens` 全属于该档）：

| 描述截断 | 选项表字符数 | 每题 token | 相对 220 | 费用/题 | 10 万次/天 |
|---|---|---|---|---|---|
| 110 | 15,510 | 5,705 | −3,077 | ¥0.0017 | ¥173 |
| 150 | 21,130 | 6,945 | −1,837 | ¥0.0021 | ¥210 |
| **220（发布）** | 30,036 | **8,782** | — | **¥0.0027** | **¥266** |
| 256 | 34,126 | 9,600 | **+818** | ¥0.0029 | ¥290 |
| 300 | 38,575 | 10,500 | +1,718 | ¥0.0032 | ¥318 |

**结论：256 字符值不回来那 9.3% 的价钱**（¥266 → ¥290/天），所以 `descChars` 保持 220。
注意这里的"贵"是**线性**的：描述长度每加 1 个字符，就是 141 个技能各加 1 个字符。

**方法上的教训（值得单独记一笔，因为这是同一个坑第三次咬人）**：缓存按「题号」索引、而记录存
「整批变体」，所以**往一个已跑满的批次里加变体，它不会跑、只会缺席**，而缺席在评分里长得和拒答
一模一样。前两次分别是「缓存指纹没含 stage-1 形状」（criteria 改写看起来毫无效果）和
「predict-jev 覆盖门控」。共同点是：**工具静默地把「没测」报成了「测了」**。
现在每个脚本要么带配置指纹，要么在评分前校验完整性——不修掉这一点，
「一个变体全体拒答」和「它根本没跑」是无法区分的。

**单调升到 220 然后走平**：再短就一道一道地丢答案（150 字符丢 3 道，110 字符丢 4 道），
再长一分钱不省、一道题不多。**220 就是这条曲线的拐点**，所以选项长度也没有可优化的余地。

**结论：单次调用的提示词已经在局部最优，评测里那个 90.8% 不是提示词写差了。**

把这一节和 §2.2.5 放在一起看，导向一个清晰的判断：**剩下与两次调用版的差距是信息差，不是措辞差。**
被移除的那次调用之所以能多对那几道题，是因为它能读到 SKILL.md 正文，而单次调用的选项表里没有
正文（§4.5 的 d 项：放开 description 长度也补不回来，因为胜利用的是正文里的词）。所以只有两条路：
接受那几道题的差距，或者把第二次调用加回来——**没有第三条"再调调提示词"的路**。

### 2.2.7 多给几个"逃逸选项"（不止一个合适 / 需要的技能不在表里）

一个自然的想法：`none_of_these` 只覆盖了"一个都不合适"这一种情况，但实际还有两种——
**好几个都合适**（65 道有答案的题里有 12 道的参照集就是多个技能），以及**需要的技能不在这张表里**
（用户点名了目录里没有的工具）。那就再加两个选项，让模型有地方放这些情况。

实测（`bench/escape-options.mjs`，100 题，4 个选项集放同一个请求里配对，污染检查 100/100）：

| 选项集 | 首答正确 | 首答∈参照集 | 正确拒答 | 误推 | 与对照不同的题 |
|---|---|---|---|---|---|
| 发布版（只有 none） | 61/65 = 93.8% | 63/65 | 34/35 | 1 | — |
| ＋「不止一个合适」 | 61/65 = 93.8% | 63/65 | 34/35 | 1 | **0 道** |
| ＋「需要的技能不在这张表里」 | 61/65 = 93.8% | 63/65 | **33/35** | **2** | 1 道（**变差**） |
| ＋两者都加 | 61/65 = 93.8% | 63/65 | **33/35** | **2** | 1 道（变差） |

**结论：加了没用，其中"不在表里"还略微有害。**

**为什么「不止一个合适」一次都没被选中（0/100）**：问题问的是"**哪一个**，或者都不合适"，
而"好几个都合适"**不是这个问题的答案**——流程需要选出**一个**要调用的技能，所以模型从不把它
作为赢家（只是拿来对冲：35/100 的题上概率非零，最大 0.27）。它也没有可修的东西：

| | 命中参照集 | 与参照首答一致 | 拒答 |
|---|---|---|---|
| 发布版 | 12/12 | 10/12 | 0/12 |
| ＋「不止一个合适」 | 12/12 | 10/12 | 0/12 |

**"多个都合适"这件事本来就没坏**——发布版在那 12 道题上一次不落全部命中参照集。

**为什么「不在表里」反而变差**：模型确实会用它，而且用得准——被选中 3 次（n013 / n014 / n016），
全都是"用户点名了目录里没有的工具"那类题目。**但这 3 道题原来的 none 概率是 0.38 / 0.34 / 0.40，
发布版的门控早就把它们拒掉了**，所以新增这个选项一分钱都没赚到。它付出的代价在别处：

```
n026  「BRCA1 蛋白一般有什么生物学功能」  参照：拒答
  发布版    gget=0.35  future-database-lookup=0.22  none=0.16  → 拒答（门控拦下）
  ＋不在表里  gget=0.38  future-database-lookup=0.18  none=0.14  → 推荐 gget（假推荐）
```

**同一个模型判断、同一个错误答案，只是归一化变了**：新增的选项从 none 那里分走了 0.02 的概率，
none 掉到阈值以下，门控于是放行了它本来拦住的错误推荐。

**这是本设计里最容易踩的一个结构性约束**：门控读的是"none 占多少**份额**"，而一个 Choice 的
概率和恒为 1 —— 所以**往选项表里加任何东西都不是中性操作，它会悄悄重新标定唯一的拒答信号**。
整批数据能看到这个摊薄：该推荐的题里 none 最大值 **0.14 → 0.09**，该拒答的题里 none 最小值
**0.16 → 0.14**，空带整体下移。模型判对趋势没变，但门控的余量被吃掉了。

两个补救方向都试过，都没有价值：

* **把「模型选了逃逸选项」当作拒答**：`＋不止一个合适` 从 61/65 掉到 **56/65**（7.7% 误拒），
  因为"好几个都合适"的概率抬高并不等于"没有技能该用"。
* **每个选项集各自重调门控**（`escape-options.mjs` 第 7 节扫过 0.05–0.30）：`＋不在表里` 在
  门控 0.10–0.12 时能回到 61/65、拒答 34/35、误推 1 —— **与发布版完全一样**。
  也就是说：加了选项必须**重新标定**，而标定回来之后**收益为零**。
  还要额外承担"阈值是在这 100 道上调的"这个风险。

（真正"需要的东西不在目录里"的请求，现在由 none 承担，效果已经够：n013/n014/n016 都被拒了。
如果想让它更显式，正确的做法不是加选项，而是把这种情形写进 `criteria` 里 none 的描述——
而 B 批已经证明"把 none 写得更清楚"会推动过度拒答，掉 2 道首答。）

**这套结论的效力范围**：100 道题只能分辨约 2 道题的差异，所以这里的"打平"应读作
"没有观察到大于 2 道的效果"，不是"证明等价"；而所有"更差"都是相对对照在**同一请求内**测的，
方向可信。另外这些变体只针对**这个技能目录和这批题型**；换目录（尤其技能之间更相似时）值得重跑
`bench/stage1-prompt.mjs`。

### 2.3 为什么拒答是一个阈值，而不是交给模型

因为 §1.3 第 2 条：Jev 不会说"都不合适"。它能做的是**在被给出 `none_of_these` 选项时选它一下**，
而那仍然只是一个概率，所以最终需要一个阈值。好处是**可解释**（界面直接显示"none 概率 0.71 ≥ 0.15，
所以拒答"）和**可调**（技能目录换了重新标定即可，不必改提示词）。

它只被设置了一次：`NONE_GATE_THRESHOLD = 0.15`。而它是个很宽的平原——该拒答的题 none 概率在 0.9
以上、该推荐的接近 0，中间几乎没有样本，0.1–0.9 的结果几乎一样（`bench/stage1-chunked-sweep.mjs`）。
0.15 落在空带的底部。

（曾经的第二次调用自带一个 fit 阈值 `FITS_THRESHOLD = 0.75`。它在本次 100 题里**一次都没触发**：
35 道该拒的题有 34 道在门控就被拦下了。所以那个阈值从来不是拒答所必需的，见 §4.5。）

### 2.5 参照答案（"金标题"）

由 `future/kimi-k3` 只看 141 行的技能目录 + 题目，给出最多 3 个技能名，或明确"不需要技能"。
**它看不到那道题是从哪个技能生成的**，所以这是一次独立判断。它是 LLM 判断，不是人工标注
——这一点在 §5 里当作限制列出。

**参照答案自身可靠性**：同样的 100 题独立跑两遍，**第一个答案 99/100 相同**（唯一翻转的是
p037：一次拒答、一次给 `matlab`）；2–3 名会飘（完整答案相同 84/100）。所以"该不该拒答"和
"第一顺位是谁"这两项可信，"把列出的名字全部覆盖住"这项受它自身抖动限制。

两次生成都留在仓库里供核对：`runs/gold-v1`（= 本报告所有分数所用的那一版，也是
`dataset/gold-v1.json` 的内容）与 `runs/gold-v1-b`（另一版，仅供比较）。因为参照来自 LLM，
**换一次生成就会得到 1–2 道题不同的分数**，所以 `dataset/gold-v1.json` 必须与产生
`dataset/score.json` 的那一版一致——否则从仓库里读到的参照和分数对不上。

### 2.6 对比系统

| 系统 | 说明 |
|---|---|
| **embedding 检索** | 本地 omlx 上的 `Qwen3-Embedding-0.6B-4bit-DWQ`。把问题向量与 141 个"技能名 + 一行描述"向量做余弦，取最近邻。**它没有拒答机制**——余弦永远有最近邻，所以拒答要靠阈值；该阈值在偶数号题上拟合、在奇数号题上评估（否则等于用同一批数据既调参又报成绩）。 |
| **deepseek-flash** | `future/deepseek-flash`，与参照答案**完全相同的提示词和名单**，只是换个模型，用来回答"这件事是不是随便一个对话模型都能做"。 |

两个 LLM 的调用都在空目录、`--no-tools` 下跑，避免 agent 自带的技能目录或项目记忆
泄漏进提示词。

### 2.7 评分口径：只看 top-1

每个系统最多给 3 个名字，但**只评第一个**：

- **决策一致**：该拒答时拒答，该推荐时第一顺位与参照相同；
- **首答正确**：在有答案的 65 题上，第一顺位与参照相同；
- **正确拒答**：在没有答案的 35 题上确实拒答；
- **误拒**：在有答案的 65 题上拒答了。

不按集合相等评分，因为参照多数只给 1 个名字，比较集合会把"列表更长"当成错误。
金标题本身的质量（是否覆盖第 2、3 名）不作为分数。

另有一项**独立于 LLM 判断**的对照：对那 65 道生成题，直接看出题时用的是哪个技能
（`source_skill`），它不经过任何模型。

误推（该拒答却推了技能）方面：Jev 1/35（`p037`）、deepseek-flash 1/35、embedding 10/35。

|---|---|

**"首答∈参照集"这一列**：65 道题里有 12 道的参照答案给了多个可选技能，而"首答正确"只比对参照的
第 1 个。两者之差（93.8% vs 90.8%）来自 `p019`（预测 `biopython`，参照 `["benchling-integration",
"biopython"]`）和 `p052`（预测 `rdkit`，参照 `["datamol", "rdkit"]`）。两个口径都列出，是为了不把
评分方式的差别当成分数差别；报告其余各处沿用更严的那个（top-1）。

**⚠️ 这些数字的精度上限**：同一套一次调用的代码，三次独立运行给出的首答正确率是 93.8% / 93.8% /
90.8%。所以"Jev 与 deepseek-flash 孰高孰低"在这个题量上**分不出来**，§5.6 有完整测量。

| 题目 | 参照 | Jev | 性质 |
|---|---|---|---|
| 3x3 矩阵求逆 + 数值积分该用什么工具 | 拒答 | `matlab` | **误推**（唯一一处） |
| 在本地跑 RNA-seq 步骤的可扩展云端流程 | `latchbio-integration` | `dnanexus-integration` | 同类平台混淆（**被移除的第二次调用能改对**） |

### 3.3 这些错题到底是推荐器错了，还是评测本身的问题

逐道查过，**7 道里只有 3 道是真正的推荐错误**：

**两道是评分口径造成的假错。** `p019` 与 `p052` 的预测都落在参照集合内（见 §3.1），只是不是参照的第
一个。`p052` 的 `datamol` 自己的描述就写着 "Preferred for standard drug discovery including SMILES
parsing"，两个答案都站得住。

**两道是被移除的那次调用当时能改对的**（`p035`、`p043`），也就是这次决策付掉的代价。其中 `p035` 的
题面与获胜技能的 SKILL.md 正文共用词汇（python / cloud / automatic / no-code）——见 §2.2.5 末尾的限定。

**一道是标注歧义。** `p037`「矩阵求逆 + 数值积分用什么工具」：用户问的是"该用什么工具"，而参照按
"不需要技能"判。Choice 两次都认为 `matlab` 是答案，这不算荒谬；要拒掉它需要把门控抬到 0.96，代价是
同时误拒十几道真该推荐的（§5.3）。

**两道是两个同族库，而题目本身不足以区分。** `p042`（两个实验室机器人类库，复核给赢家与第二名的差距
只有 0.01，而题面**没提硬件品牌**）、`p035`/`p043`（两个云端平台、两个文献管理工具）。补充一点结构性
弱点：65 道题是按某个技能的文档出的，参照答案因此天然偏向那个技能；当题目无法区分姊妹工具时，错的到底
是谁其实无法判定。**改进方向不是调推荐器，而是让题目自带判别信息**（如 p042 应写明硬件品牌）。

### 3.4 被移除的那次调用当时做了什么（同样的 65 道题）

只看门控放行的题，两次调用给出同一个第一名的比例、以及它改判的净效果（`bench/stage2-diff.mjs`）：

| | 数量 |
|---|---|
| 两次调用选出**同一个**第一名 | 62/65 = 95.4% |
| 改对 | 3 道（p019、p035、p043） |
| 改错 | 0 道 |
| 把可推荐的改成拒答 | 0 道 |
| 自己触发拒答（fit 阈值） | 0 道 |

也就是说，它买到的就是 **+3 道题（+4.6 个百分点首答正确）**，代价是每次请求多一个网络往返
（p50 +284 ms、p90 +186 ms）与 +10.1% 的成本；其中 2 道题的胜利依赖 SKILL.md 正文里的措辞（§2.2.5）。

## 4. 成本与延迟

### 4.0 计价口径

| 系统 | 计价方式 | 折算 |

| Jev | TypeSafe 公示价 **$0.042 / 百万输入 token，输出 token 免费** | 按 **¥7.2/$** 折成人民币（假设的汇率，换一个汇率整列等比缩放） |

| 系统 | 输入 token | 费用/题 | 计价依据 |

| **Jev（一次调用）** | **8,765** | **¥0.0027**（$0.00037） | 公示价 $0.042/Mtok，输出免费 |

三点必须说清楚：

- **Jev 的输入 token 比 deepseek-flash 少 30%**，因为整张技能表只在选项表里写一遍

  这个结论依赖 ¥7.2/$ 这个假设汇率。
- **成本几乎全在这一次调用**：唯一可省的那部分（被移除的第二次调用）占 10.1%，§4.5 说明为什么不再省。

### 4.4 一次调用的成本构成

不存在"两次调用各占多少"这个问题了——服务路径只有一次调用，成本就是它的成本：

| 阶段 | 每题中位 | 每题均值 | 100 题合计 | 占比 | 费用（100 题） |
|---|---|---|---|---|---|
| 路由（1 个 Choice，141 选项 + none） | 8,765 | 8,763 | 876,252 | **100%** | $0.0368 |
| ~~第二次调用~~ | — | — | ~~98,948~~ | — | ~~$0.0042~~ |

被门控拒掉的 34 道题同样只付这一次——没有第二次调用可省。

**注意口径**：评测脚本 `predict-jev.mjs` 仍然对每道题探测被移除的那次调用，好让
§4.5 的对比能被复现；那是**评测开销**（每题中位 10,250 token），不是服务成本。
`dataset/score.json` 里发布那一行按服务口径计价。

### 4.5 移除第二次调用的完整证据

三门路线的正面对比见 §2.2.5 的表；这里补齐支撑那个决定的其他测量（都用 `bench/drop-stage2.mjs`
与 `bench/stage2-budget.mjs` 离线从缓存重算，不重新调接口）：

**a) 那条路能多对 3 道，而且不是靠运气。** 两道调用的第一名有 62/65 相同，改判的 3 道全部改对、
没有一道改错、也没有一道被它拒掉——它在这批题上的改判记录是 3:0。这是真实的配对收益（同一批
stage-1 答案，不是两次运行的比较）。

**b) 它的 fit 阈值从没触发过，所以拒答从来不依赖它。** 35 道该拒的题里 34 道在门控就被拦下，
剩下 1 道它也没拒。→ **移除它不会让拒答变差**，这一点在 §3.1 得到确认：两个版本的"正确拒答 97.1% /
误拒 1.5%"完全一致。

**c) 它的优势有评测偏置。** 3 道胜利里 2 道（p019、p035）的题面用词与获胜技能 SKILL.md 正文重合、
而与 description 不重合：

```
p019 题面: "...pulls all registered DNA sequences ... from our cloud-based life sciences R&D platform"
     benchling 的 description: "Benchling Python SDK and REST API integration for registry entities, ..."（不提云端平台）
     benchling 的 SKILL.md:    "Benchling is a cloud platform for life sciences R&D."
p035 题面: "...scalable cloud pipeline with automatic ... no-code UI ..."
     latchbio 的 SKILL.md 里出现、description 里没有的实词: python, cloud, automatic, no-code
```

题集是照 SKILL.md 生成的，所以题面借了正文的词；而只有第二次调用能看到正文。**这是真实优势的
上界，不是期望值**——但它也不是纯粹的假象：这些词（cloud / python / no-code）本来就是真实用户会说的
话。诚实的说法是"3 道里 1 道（p043）干净、2 道打了折扣"。

**d) 放宽路由的描述长度补不回来。** 141 个技能里 83% 的 description 被截断在 220 字符（中位长度 329），
全部放开只多约 5,758 token（+66%）。但上面那 2 道题的胜利用的是**正文里的措辞，description 里根本没有**
（benchling 的 description 不提"cloud platform for life sciences R&D"），所以加长 description 补不回来。
唯一能补的办法就是把带正文的那次调用加回来——也就是 ②。

**e) 候选数不能减。** 如果保留第二次调用，它至少要拿到 3 个候选：只复核 top-1 或 top-2 各自都会再丢
2 道题，因为被改判的题里路由把正确答案排在了第 2、3 名（`bench/stage2-budget.mjs`）。

### 4.6 用"第 1 名与第 2 名的差距"代替 top-1 概率，会更好吗？

直觉上应该会：一个**第 2 名紧跟在后面**的分布比一个"第一名很高"的分布更可疑，
而"两个候选都很像"恰好就是那两道改判题的形态。所以把跳过规则从 `top-1 概率 ≥ T` 换成
`1–2 名差距 ≥ T` 是个合理的猜想。实测结果：**两者完全等价，没有收益。**

**先看两道改判题在三个信号上的取值**（`stage1-confidence.mjs`）：

| 题 | 金标题 | 路由第一名 | top-1 | 1–2 差距 | confidence |
|---|---|---|---|---|---|
| p019 | `benchling-integration` | `biopython` | 0.81 | **0.72** | 0.79 |
| p043 | `paperzilla` | `pyzotero` | 0.40 | **0.04** | 0.38 |

注意 p019 的差距高达 0.72——**用差距做信号，它看起来"很有把握"**，而它恰恰是需要复核的那道。

**要抓住全部 2 道改判，每个信号最少要复核多少题：**

| 信号 | 需复核 | 阈值 |
|---|---|---|
| top-1 概率 | **10/66** | 0.82 |
| 1–2 名差距 | **10/66** | 0.73 |
| `confidence` | **10/66** | 0.80 |
| `none` 概率 | 59/66（无用） | 0.03 |

**而且三个信号选出的是同一批 10 道题**（逐题比对完全相同）：两个方向的差异都是 **0 道**——
"top-1 高但第 2 名很近"的情形 **0 道**，"差距大但 top-1 低"的情形也 **0 道**。
组合规则（`top-1 < T1 或 差距 < T2`）反而更差：17/66。

**为什么等价，有三个原因：**

1. **选项分布会饱和**：66 道放行题里 **31 道**的第 2 名概率恰好为 0，于是差距恒等于 top-1，
   两个信号在构造上就无法不同（而饱和是因为模型把全部概率压在了一个选项上，见 §2.2.1）。
2. 在剩下的 35 道里，两个信号对题目的排序仍几乎一致，所以操作点上选出同一批。
3. **本想当第三个信号的 `confidence` 不是独立的数**：Choice 的响应同时返回
   `probabilities` 和 `confidence`，实测 **|confidence − 选中项概率| 的平均值仅 0.006**
   ——它基本就是选中项的概率，不携带额外信息。

严格说这不是数学恒等：`p1=0.90, p2=0.30` 这种"第一名高、第二名也高"的题会让两者分歧
（此时差距会复核、top-1 会跳过），但**本次 100 题里一道都没有**。所以结论是
"在这批数据上等价"，不是"永远等价"；**保留 `top-1`**，它更简单（已经是门控在用的量、
也已经在界面上显示）。

## 5. 局限

### 5.1 参照答案是 LLM 判断，而且对照系统里有另一个 LLM

参照答案来自 `kimi-k3`，对比系统之一是 `deepseek-flash`——两者做的是同一道分类题，
**互相一致是它们的强项**，而 Jev 是个小决策模型，用"和另一个大模型一致"当尺子对它不利。
要真正判定需要人工标注。

**更强的限定：参照答案自己就带着 1–2 道题的噪声。** §2.5 量过它自身的抖动（首答 99/100 一致、
**整个集合只有 84/100 一致**），而本报告的错误分析用的正是集合。两个具体后果：

- **`p037`（"矩阵求逆该用什么工具"）在这两次生成之间就是从"拒答"翻成 `['matlab']` 的**——
  这一道题决定它是"误推"还是"答对"。报告在 §3.3 说它"到底算不算该拒答本身就存疑"，
  现在有了直接证据：**连参照答案自己都不同意**。
- **`p019` 在两次生成里分别是 `['benchling-integration']` 与 `['benchling-integration',
  'biopython']`**——前者把 Jev 的 `biopython` 判为错，后者判为"在集合内"。§2.2.5 里
  "被移除的那次调用多对 3 道"这个数，按不同的参照版本是 3 道或 2 道。

所以 1–2 道题量级的结论，无论它来自系统还是来自参照，都落在噪声里；报告在给出差值时一律标注
是否为同批记录的配对比较，理由就在这里。

### 5.2 题集仍然偏简单，且只有一侧

65 道生成题都是"这个技能确实该用"的正例，不含"技能存在，但通用帮助更好"的边界情形。
按出题所用技能算，一次调用的第一顺位命中 **93.8%**（即 61/65；两次调用版是 98.5%），说明题目难度中等偏易。

### 5.3 拒答有已知上限

唯一被放过的该拒题是"3x3 矩阵求逆 + 数值积分该用什么工具"：门控给了它很低的 none 概率（0.02），
所以它被推荐了 `matlab`。它在复核里的 fit 是 0.95，而真该推荐的题最低是 0.76、第 10 百分位是 0.94
——**两类在这个区间重叠**，要拒掉它必须同时误拒十几道真该推荐的（离线扫阈值：拒答阈值 0.96 时误拒
14 道，换来首答从 95.4% 掉到 75.4%）。而且这道题到底算不算"该拒答"本身就存疑，见 §3.3。

### 5.4 统计精度

65 道正例、35 道负例的样本量，95% 置信区间（Wilson）大约为：

| 指标 | 点估计 | 95% CI |
|---|---|---|
| 决策一致（n=100） | 93.0% | [86.1%, 96.6%] |
| 首答正确（n=65） | 90.8% | [81.2%, 95.8%] |
| 首答∈参照集（n=65） | 93.8% | [85.2%, 97.6%] |
| 正确拒答（n=35） | 97.1% | [85.5%, 99.5%] |

（两次调用版的首答是 95.4% = 62/65，CI [87.3%, 98.4%]；embedding 最近邻首答 76.9% = 50/65，
CI [65.4%, 85.5%]。）

### 5.5 成本口径

- Jev 按公示价自算，实际账单可能因账户等级/网关而不同。
- 两个对话模型只有平台 credits（1 credit = ¥1），无法折算成美元。
- embedding 的"¥0"是**边际 API 费用为零**，不包括机器与电费；如果换成托管 embedding API，
  按 token 计费也不到 Jev 的百分之一。

### 5.6 同一套代码的运行间波动（读任何对比前都要看）

这是本报告里**最容易被忽略、但最影响结论**的一条限制。`runs/` 里有三份**同一个请求**的独立记录
（`bench/stage1-stability.mjs`），它们的差异只来自 Jev 的采样：

| 对比 | 首答（第一名）相同 | 判定（推荐/拒答）相同 | 各自的首答正确率 |
|---|---|---|---|
| 早先 vs 另一次 | 91/100 = 91.0% | 99/100 = 99.0% | 93.8% vs 93.8% |
| 早先 vs 本次 | 91/100 = 91.0% | 97/100 = 97.0% | 93.8% vs 90.8% |
| 另一次 vs 本次 | 90/100 = 90.0% | 98/100 = 98.0% | 93.8% vs 90.8% |

三条推论：

1. **同一套代码两次运行会在约 9% 的题上给出不同的第一名**，在 1–3% 的题上改变"推荐/拒答"。
2. 因此**首答正确率本身有约 ±2 道题（±3 个百分点）的波动**——这就是为什么 §3.1 把"Jev 与
   deepseek-flash 孰高孰低"写成"分不出来"。
3. **但它不影响配对比较**：本报告里所有"加了 X 之后多了几道题"的比较，都是在**同一批记录的
   stage-1 答案**上再做的（如 §3.4、§4.5），所以那些差值不受这个波动影响。把两次独立运行拿来比较
   （"这次 90.8% vs 上次 96.9%"）才是无效的，报告里没有这样做。

上面的波动来自**推荐器**一侧；参照答案一侧也有同量级的抖动（整个集合 84/100 一致，§5.1），
两侧叠加就是本报告所有"1–2 道题"结论的精度上限。

举一个具体的例子：本次运行里 `n032`（"蛋白质折叠进展"）的门控 none 概率是 0.15，**正好压在阈值上**，
于是从"推荐 future-web"翻成"拒答"；上一次运行它是 0.12，放行。这类题在阈值附近的题只有个位数，
但它们决定了 1–2 个百分点的差别。

（`p035` 也换了第一名：一次给 `dnanexus-integration`、另一次给 `latchbio-integration`，
两次的正确率一样——都是参照集合之外的那一个。）

## 6. 结论

1. **Jev 在这个任务上可用，而且快、便宜、可解释**：一次调用首答正确 90.8%（按"预测在参照集合内"
   算是 93.8%）、该拒答时拒答 97.1%、每题 0.49 s、¥0.0027，拒答是一个可以指给用户看的概率。
2. **它没有赢过通用对话模型**：93.0% vs 95.0% 的决策一致。但两者付出不同——Jev 的拒答是**显式阈值**
   （可解释、可调、可审计），对话模型的拒答是提示词行为（不可调、只能整体重问）；Jev 快 3.6 倍、
   便宜约 9 倍。
3. **"少一次网络调用"是有代价的，而且代价可以量化**：移除第二次调用换来 p50 −284 ms、
   p90 −186 ms、成本 −10.1%，代价是 3 道题（4.6 个百分点）。三种做法的完整对比在 §2.2.5，
   其中"只在没把握时才发第二次"（20/65 次）在本次数据上**严格优于**彻底移除——本版按"只保留一次
   调用"的决策发布，恢复那个中间方案是一处改动。
4. **拒答完全由这一次调用完成**：门控的 none 概率拒掉了 34/35 道该拒的题，而被移除的那次调用自带的
   fit 阈值在 100 题里一次都没触发。所以两个版本的拒答指标完全一致（97.1% / 误拒 1.5%）。
5. **embedding 不能单独用**：它排序尚可（最近邻首答正确 76.9%），但没有"该不该推荐"的机制，
   任何阈值都同时带来大量误拒（≥0.56 时误拒 16.9%、正确拒答仅 71.4%）。合理定位是**召回层**。
6. **省钱靠改请求形状，不靠加组件**：最初的 141 道 noul 每题 21,357 token，改成"一个 Choice + none
   选项"后降到 8,765（−59%），且没有引入任何新依赖。载荷里只该留真正提供信息的字段：`tagline`
   （141/141 都是 description 的前缀）与 `chinese_description`（删掉后端到端 0 道题变化）都已去掉。
7. **报告里的差值要按配对比较读**：同一套代码两次运行会在约 9% 的题上换第一名、在 1–3% 的题上翻转
   判定（§5.6）。所有"多个 X 就多对几道"的结论都是同批记录内的配对比较，不受此影响；跨运行比较
   绝对分数则是无效的。
8. **提示词和选项文本已经没有可挖的余地**（§2.2.6）：14 个变体、4 批、同请求内配对比较，
   没有一个比现在的写法更好——更短的提问会丢掉 4 道拒答（"选 none 不算兜底"那句许可是承重的），
   把提问改中立会丢 2 道拒答，把 none 选项写详细反而多推 2 道，把描述减半会丢 4 道答案，
   而 description 长度扫过 110/150/180/190/220/240/不截断，**220 正好是拐点**。
   也就是说：**剩余与两次调用版的差距是信息差（SKILL.md 正文），不是措辞差**——只有"接受差距"或
   "把第二次调用加回来"两条路，没有第三条靠调提示词的路。
9. **选项表里只该有"回答这个问题的合法答案"**（§2.2.7）：再加"不止一个合适"一次都没被选中
   （0/100），因为流程要的是"调用哪一个"，而它不是这个问题的答案；"需要的技能不在表里"虽然
   用得准（3 次全部命中那类题目），但那 3 道题原来的门控已经拒掉了，它唯一的净效果是**从 none
   那里分走概率、把门控的余量吃掉**，反而多推 1 道。更一般的结论是：门控读的是 none 的**份额**，
   而概率和恒为 1，所以**往选项表里加东西会悄悄重新标定唯一的拒答信号**——加选项不是中性操作。

## 7. 复现

```bash
cd scripts/skill_reco/bench
node build-dataset.mjs                      # 生成 65 道不含技能名的题 + 35 道手写题
node check-dataset.mjs                      # 独立复查：题目里不许出现技能名
node ground-truth.mjs                       # kimi-k3 产生参照答案
node gold-stability.mjs gold-v1 gold-v1-b   # 参照答案自身的抖动（需跑两遍 ground-truth）
node predict-jev.mjs                        # Jev 的答案 + 对被移除那次调用的探测（需 FUTURE_API_KEY）
node predict-embed.mjs                      # omlx embedding
node predict-llm.mjs                        # deepseek-flash
node stage1-ranking.mjs                     # 只看路由：top-1/3/5、拒答质量、成本
node stage1-stability.mjs                   # 运行间波动（§5.6，读任何对比前先看）
node stage1-prompt.mjs --batch A|B|C|D|E|all # 提示词/选项文本变体（§2.2.6，同请求内配对；E 每次只放两张表）
node option-limit.mjs                       # 一个 Choice 到底能放几个选项（255，none 占一个）
node option-limit.mjs 253 254 255 256       # 扫边界
node desc-cost.mjs 110 220 256 300          # 描述长度每档的价钱（§2.2.6 D 批）
node drop-stage2.mjs                        # 一次/两次/中间三种做法的配对对比（§2.2.5、§4.5）
node escape-options.mjs                     # 逃逸选项（不止一个合适 / 不在表里）（§2.2.7）
node ctx-limit.mjs                          # 一个请求能塞几张选项表（配对方法的前提）
node stage2-diff.mjs                        # 两次调用逐题对比 + 每道错题的解剖（离线）
node stage2-budget.mjs                      # 候选数能不能减（离线）
node stage1-onechunk.mjs                    # 路由形状：单 Choice 的原始响应（供离线扫阈值）
node onechunk-compare.mjs                   # 单 Choice 与 141 道 noul、分块方案的对比
node chunked-cv.mjs                         # 分块大小与两个方案的 5 折留出验证
node stage2-zh.mjs --ab                     # 中文描述成对 A/B（同一请求内）
node stage1-zh.mjs                          # 反面验证：把中文描述放进路由的选项表
node stage1-compact.mjs --ladder            # 历史：已退役 noul 路由的压缩阶梯
node compare-runs.mjs <目录A> <目录B>        # 两次运行逐题对比
```

每一步按题目 id 缓存在 `runs/<步骤>/`，重跑只补缺失的题；缓存里带配置指纹
（两个阈值 + 请求形状版本），配置一变就重跑，不会把旧答案当新结果。改了题目文本则先用
`node drop-changed.mjs <步骤...>` 清掉对应缓存。
