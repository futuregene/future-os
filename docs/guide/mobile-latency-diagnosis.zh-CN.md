# 移动端历史加载延迟：复现与验证

> 本文是历史快照 [Mobile history-loading latency: reproduction and verification](./mobile-latency-diagnosis.md)（2026-09-12，commit `a5117d57`）的忠实逐段中文翻译，保留原文结论、时间与 commit 边界；译文不是新的复核结论。

日期：2026-09-12。基线：`c5e87eec`。本地平台：Windows。

## 已诊断的原因

1. 移动端冷启动同步在提交已经可用的历史之前，先等待整个活动 run 的重放。因此即使历史成功加载、且每个单独的重放请求都成功，其 15 秒历史加载计时器仍可能超时。
2. 每个远程重放页默认最多消费 100 个事件，但桌面端先读取完整的剩余 Agent 尾部，再对之进行分页。长 run 会在本地 gRPC 上反复解码并传输相同的后缀。

基础探测未复现传输中断：近期历史读取约耗时 5–151 ms；另 8 个长历史样本约耗时 82–415 ms。计算机侧 NATS WebSocket 连接耗时 145/158 ms，PING/PONG 约 15–18 ms。这些并非对手机网络、握手或渲染的测量。

## 修复

- 在等待重放之前先发布冷启动历史预览。不推进重放游标、不将通道标记为已建立。重放失败时历史仍可读，并重试其完整前缀。通道被替换后忽略过期的状态/历史完成事件。
- 保留现有重放协议：第一次完整尾部读取建立其固定水位线。携带该水位线与事件游标的后续请求只请求一个有界的 Agent 分页，而不是排干整个后缀。保留 Agent 的 `hasMore` 以及远程字节预算；当任务持续生成时，停在该原始水位线处。
- 原生完整尾部消费者与旧的偏移量调用方保持现有行为。无需修改 protobuf、新凭据或配对变更。

首个快照仍是完整尾部读取；本次改动消除的是重复的完整尾部读取，而非那份初始成本。超大的单次交换历史/投影加固与这两个已验证修复是相互独立的工作。

## 测量

一个只读探测通过当前用户命名管道调用真实运行中的 Agent，针对同一保留任务与固定水位线：7,290 个事件，73 个游标页。

| 读取策略 | 读取事件总数 | 本地探测耗时 |
|---|---:|---:|
| 基线：每页读取完整剩余尾部 | 269,370 | 6,649 ms |
| 修复策略：初始完整快照 + 有界续页 | 14,480 | 496 ms |
| 处处有界的对照（无初始快照成本） | 7,290 | 280 ms |

该探测复现 100 事件游标推进，以隔离本地读取放大；它并非手机端到端基准。耗时包含本地 RPC 与探测的 protobuf 处理，但不包含桌面端 JSON 处理、中继/手机网络与 React Native 渲染。真实字节预算裁剪可能需要额外分页。探测期间未重启或替换任何服务。

一个确定性探测执行了实际的移动端 `SyncEngine` 与 `fetchEventsSince` 代码，使用 4,800 个合成事件，并显式模拟每页 350 ms 延迟：

| 观测项 | 基线 | 修复后 |
|---|---:|---:|
| 历史可用 | 0 ms | 0 ms |
| 首次时间线提交 | 16,800 ms | 0 ms |
| 15 秒时时间线缺失 | 是 | 否 |
| 重放请求数 | 48 | 48 |

这里的零是假时钟时间，不是真实世界零延迟渲染的声明。持久的自动化回归现已覆盖早期历史、重放失败/重试，以及实际的历史加载钩子在重放延迟 20 秒时仍不超时。

## 后续：切换与前台同步（无物理设备）

下一个仅移动端的改动在模型控件与同步引擎之间共享初始 `get_state` Promise，移除冗余的打开时附件历史拉取，并拒绝过期的导航响应。模型/思考命令在异步偏好写入之前捕获目标会话。草稿偏好加载不能导航覆盖更新的选择。

只有选中的会话执行历史/重放/投影工作。隐藏文本事件不创建时间线通道，而标题、终端与审批通知仍会更新目录。重新打开总会刷新持久历史与活动前缀，因此一个在隐藏期间完成或请求审批的任务可以被恢复。重连会重启可见通道，重放在每一页前后都会检查通道有效性。已发出的请求可能完成或超时；不会为过期通道发出后续分页。这**不**改变通配传输订阅，也不消除其入站 JSON 解码成本。

确定性回归使用实际的移动端 hooks/sync/重放代码，配合脚本化的 RPC Promise 与假计时器：

- 在模拟 350 ms 状态响应与 350 ms 历史响应下，打开状态只请求一次、历史只请求一次，历史在 700 ms 时提交。这验证的是两次顺序往返，而非先前那种重复状态依赖；它不是手机渲染基准。
- 100 个隐藏会话收到 10,000 条文本增量时，产生零次历史/重放请求、零个新时间线分配。打开其中任意一个会加载其最新持久状态。
- 带多个缓存通道的重连只刷新选中通道；重新打开一个空闲隐藏会话会刷新其已完成历史。
- 迟到的 A 成功/失败不能覆盖 B 的模型，也不能清除 B 的待处理状态。延迟的偏好保存不能把 A 的命令发给 B。
- 隐藏/被替换的重放停在当前在途页；审批在打开时恢复；打开期间到达的实时事件不会重复排队一次打开读取。
- 一个热会话的十次交换显示窗口在立即重启后仍保持有界，更早的历史仍可通过分页访问。

本地验证：移动端 typecheck 与 ESLint 通过；50 个套件 / 718 个测试通过。一次初始完整运行撞上一个未改变的 SessionList beforeEach 5 秒超时；其单独重跑与后续完整运行均通过，未更改超时设置。未使用物理设备、模拟器帧率测量、生产服务重启或模型请求。Markdown 增量渲染与细粒度 Context 订阅仍是独立的优化工作。

## 后续：增量 Markdown 与渲染隔离（无物理设备）

移动端现在使用共享流式解析器，每条消息/片段维护一个当前检查点。它保留已完成顶层节点，重新解析可变尾部，并增量重析最后一个 GFM 表格行，同时保留已完成行与表头/对齐对象。瞬时片段绕过共享的已定稿文档缓存。替换、定稿、带括号的源码（保守的引用定义安全性）以及不支持的检查点形态使用规范全量解析。一个巨大的单段/列表/代码块仍可能需要解析整个可变块；这不是声称对任意 Markdown 输入都能常数时间解析。

`MarkdownText` 记忆化已完成的块与表格行。远程控制状态与转录状态分离，同时为转录消费者保留 `useRemote`。导航与分享导入只订阅控件。编辑器收到稳定的控制状态/回调，并通过比较审批条目身份来避免普通文本提交触发重绘，但流式状态、回调与审批内容的变化仍然可观察。

共享解析器的 28 个测试包括：对 21 个混合 Markdown fixture 逐字符等价于规范解析、不可变块/行身份、替换/引用/定稿处理、缓存隔离、深层嵌套回退，以及两个有界工作量负载。Windows 上一次隔离的 Node/Vitest 运行测量了初始内容加 100 次追加：

| 负载 | 全量解析输入字符 | 增量解析输入字符 | 全量解析耗时 | 增量耗时 |
|---|---:|---:|---:|---:|
| 200 个稳定段落加增长尾部 | 721,544 | 12,544 | 2,337 ms | 49 ms |
| 200 行表格加追加行 | 516,367 | 10,598 | 3,081 ms | 74 ms |

两条路径在此对比中均绕过已定稿文档缓存；全量解析使用规范解析器，增量解析使用实际生产代码。字符数断言是确定性的。计时是单次运行的主机观测，不是手机 FPS、p95 延迟、渲染时间或通用提速保证。

React test-renderer 检查显示 100 次转录提交没有额外的控件消费者渲染；流式开始/结束仍会渲染控件。一个编辑器测试同样检查 100 次未变化的审批数组重建不会重绘其停靠卡片，而新回调与流式状态会。增量渲染并定稿的 Markdown 与普通渲染一致。

验证：移动端 typecheck/ESLint 与 **51 个套件 / 720 个测试**通过；桌面端 typecheck/ESLint/Stylelint 与 **107 个文件 / 943 个测试**通过；共享 Markdown 包 typecheck 通过。Android 与 iOS 生产 Expo 导出均成功，包括 Hermes 字节码生成。未执行原生应用构建/安装、物理设备测试、模拟器帧率测量或服务重启。

## 后续：超大读取、缓存预算与刷新合并

历史/重放调用方声明 `chunkedRead`。当一次逻辑读取结果超过 512 KiB 时，桌面端保留一份不可变 JSON 快照，并返回以 base64url 编码的 192 KiB 二进制切片。移动端在重组并解码完整结果之前，检查快照身份、精确偏移、分块大小、总长度与当前同步通道。这保留了现有的历史页分组与投影游标：把一个 run 拆成独立投影的消息页，可能丢失一个跨页重叠的助手气泡。普通回复与旧桌面端回复保持兼容。

限制是显式的：每次重组读取 16 MiB、缓存快照载荷 32 MiB、120 秒过期，按 bridge/会话/run 归属。分块请求通过常规鉴权/访问检查，但不会在十分钟命令回复缓存中重复缓存每个分块。快照随传输生命周期维护而被清理和清除。所有最终命令回复额外强制 1 MiB **未压缩 JSON** 上限；不支持/超大的结果返回显式错误，而不是依赖 NATS 拒绝发布。这并不移除 Agent 现有的 gRPC 限制或现有的逐条目展示内容上限。超出新读取限制的数据显式失败；不会被此传输层静默截断。

移动端导航现在按最近打开顺序驱逐非活动会话缓存，目标为八个会话 / 16 MiB 估算序列化 UTF-16 载荷。游标状态、重试、排队操作以及钩子对应的时间线/分页/错误记录一起移除。选中的会话与乐观草稿受到保护；这些是显式例外，而不是截断正在读取的内容。大小估算在时间线变化前保持缓存，在导航时评估，而不是在每个流式 token 上评估；它们不是精确的 JavaScript 堆测量。

并发会话列表刷新共享一个在途请求，并在请求期间又有事件到达时追加一次尾部读取。100 次调用的突发测试只产生两次请求而非 100 次，并以最新结果结束。客户端/纪元变化会屏蔽旧响应。

## 后续：大型重放折叠与历史预取

移动端重放 reducer 现在每次重放拥有一个去重集合，而不是逐事件复制不断增长的集合。共享 run 投影器支持到达顺序追加而无需构建快照、显式快照以及独立分叉。连续 run 事件构建一个显示快照；用户/审批/错误/通知与 run 边界会冲刷它，以保留单事件 reducer 的排序。现有 `ingest` 批量排序/去重语义保持不变。

重放以协程方式折叠，在 512 个事件、约 256 KiB 事件数据或 8 ms 工作目标之后于切片之间让出。这些检查发生在事件之间：初始状态分叉、单个巨大载荷与最终快照构建不可抢占，因此 8 ms 不是保证的最大任务时长。已提交的时间线/投影器与游标在重放运行期间保持不变。完成的结果将时间线与游标一起安装；取消/重启丢弃部分工作。投影快照保留其累加器，使后续实时文本追加到其前缀而不是替换它。

历史分页不再等待固定的 1.5 秒标记截止。它仍等待请求的 ID 提交、一次原生布局观测以及现有的 100 ms 静默窗口（布局持续变化时该窗口可延长）。刻意滚动可在历史边界的一个视口内请求一页（上限 600 布局点）。现有事务与逐手势守卫可防止程序化滚动/惯性滚动级联触发多页。空闲文本更新不再重建整个分页 ID 索引。

验证使用真实的 reducer/投影器/钩子实现配合合成事件，而非物理设备：

- 10,000 / 50,000 / 100,000 条文本事件（加开始/结束）各自产生一个显示快照与精确的文本/token 总数。一个独立计时器在完成前运行（记录运行中在 1,024 个事件之后）。
- 一个 5,002 事件的对比中，单事件折叠产生 5,002 个快照，批量则只产生一个。一次记录的完整套件运行测得单事件 210 ms、同步批量 15 ms、含计时器调度的协程批量 136 ms。这些是主机观测，不是手机延迟或 FPS，且没有任何墙上时间比值作为测试门禁。
- 测试覆盖 300 个交错的工具调用、思考、用量、压缩、审批、错误、截断、重复/乱序/未跟踪事件、不改变已提交前缀的取消、不发布部分游标的重启，以及投影到实时尾部的延续。
- 分页测试覆盖提前一页预取、无需旧冷却的快速翻页、原生布局屏障、过期会话完成，以及 1,000 行上的 100 次空闲文本更新且无 ID 索引读取。
- 移动端 typecheck/ESLint 与 **53 个套件 / 752 个测试**在同步 main 后通过；桌面端 typecheck/ESLint/Stylelint 与 **109 个文件 / 959 个测试**通过。共享 thread-projection typecheck 与 Android/iOS 生产 Hermes 导出通过。

这优化的是拉取重放后的重建，而不是现有的首次完整尾部读取或对所有已拉取事件页的保留。巨型消息内部的块级虚拟化、数据源字节分页以及有界活动历史窗口仍是独立工作。未执行原生安装或物理设备性能测量。
