# Desktop Agent 生命周期与恢复

[English](desktop-agent.md)

GUI 和 `future host` 默认在自身进程中运行完整 Agent。CLI、TUI、手机和其他客户端仍通过同一 RPC 使用服务，现有配置、数据库、会话和凭据格式不变。打包的 `future` CLI 继续用于技能、维护和独立 `future agent`，不再是 Desktop 默认启动 Agent 的必需进程。

## 启动与外部服务

Desktop 先检查当前系统用户、数据根及端点上的外部 Agent。兼容且就绪则连接它；默认端点没有服务且成功取得实例锁时，才启动内置 Agent。版本、协议或存储契约不兼容，以及实例锁被占用但服务不可用时，直接报告错误，不启动另一份 Agent，也不删除锁或打开第二份业务数据库。

显式设置 `FUTURE_AGENT_GRPC_ADDR` 的连接和 `FUTURE_DESKTOP_AGENT_MODE=external` 都只连接外部服务，失败不会自动接管。开发环境可先在另一终端运行 `future agent`，再以 external 模式启动 Desktop。默认 `auto` 同时支持兼容外部服务和内置服务，没有强制绕过外部 owner 的开关。

release Desktop 配置的 Future 平台为非生产环境时拒绝连接外部 Agent；外部 owner 持有数据根时，不改写认证文件或删除 key。应独立退出该 Agent，再重开 Desktop，由本地所有者执行原有生产环境策略。开发版本保留明确选择的环境。直接账户、登录和技能指南请求也执行同一检查，不因 Agent 启动失败而绕过。Agent 正在停止时也阻止连接和本地启动，应等待它退出后重试。

CLI/TUI 连接内置服务时，必须使用同一系统用户、`FUTURE_HOME` 和端点设置。需要独立常驻服务时，先退出 Desktop，再独立启动 `future agent`，然后重新打开 Desktop。不能通过更换端口绕过同一数据根的实例锁。

CLI、TUI、Desktop 和 Channels 使用同一业务连接门禁。RPC 协议 2 要求业务命令和订阅携带完整的版本、协议、存储契约及实例/数据根信息；readiness 可先探测，但未验证客户端不能执行业务。旧客户端需同步升级，不能因为版本不匹配就启动另一份服务。数据库 schema 和文件格式不变。

Unix socket 旁的 `.owner.lock` 是端点租约文件，独立于 Agent 数据根锁。文件保留是正常现象，占用由 OS 锁判断；不要手动删除。活跃或无法判定的端点不会被替换，只有确认陈旧的 socket 才可回收；退出时只清理当前 listener 自己创建的端点。

## 退出、重启与升级

- 内置宿主退出会停止所有客户端的活动、排队和审批任务，包括从 CLI/TUI 发起的对话。GUI 检测到工作或无法确认活动状态时会提示；选择强制退出会先执行清理，再退出。其他客户端会观察到取消或断线。
- 连接外部 Agent 时，只取消本 Desktop 提交的运行并关闭自身远程入口，外部服务和其他客户端继续运行。
- 排队中或状态无法确认的运行保留所有权，直到收到终态事件或核实终态；collector 失败不会让这些任务从退出取消范围中静默消失。
- 外部模式取消后必须核实对应 run 的终态；超时、断线或错误 run 的终态不能算成功。未确认的任务保留诊断并阻止更新、重置和重启。用户强制结束 Desktop 不能保证一个失联外部服务已停止这些任务。
- 主机模式的 Ctrl+C，以及 Unix 的 SIGTERM/SIGHUP，走有界停止流程。登录和配对数据保留，再次启动通常无需重新配对。
- 更新先下载、验签并确认中断范围，再完整清理。清理失败不启动安装器，也不在同一进程启动第二份 Agent。重启同样要求上一实例完成清理。
- 系统强杀、崩溃或开发工具链中断可能绕过正常退出；下次启动按已有事务恢复和权限回收机制处理。不要手动删除数据库、WAL、锁文件或 capability metadata 来“修复”启动。

Windows 自动更新使用独立观察进程等待 Desktop 退出，再运行安装器。安装失败且原程序完整恢复时才重启旧程序；回滚不完整时保留诊断，用户可重新运行可信完整安装器修复。便携版手动完整替换文件，避免混用不同版本的 Desktop 和 CLI。详细安装门禁见 [Windows 安装器预检](../internals/desktop-windows.zh-CN.md)。

退出、更新、重置和重启共享同一次停止操作，后来的请求不会重新清理或延长期限。清理在后台进行，主窗口保持响应并显示当前阶段；主机模式在 stderr 报告阶段。停止结果有 20 秒总期限，超时会报告失败并继续禁止安装或进程内重启，不会为了满足期限强杀写入线程或提前解锁。正常退出遇到失败时可选择是否结束整个进程；已确认的强制退出会记录失败后退出。维护动作执行到安装器接管期间，关窗不会抢先结束 Desktop。

启动时可在旧会话导入期间请求退出。取消会保留已经提交的会话，不把未读完的源记成损坏或提前标记全部导入完成；未提交事务回滚，下次启动继续导入。无法立即打断的系统 I/O 仍受安全门禁约束，不应手动删除 WAL 或锁来催促退出。

## 排障与日志

默认数据根是 `~/.future`；有效绝对 `FUTURE_HOME` 替换整个根。内置宿主日志在 `<数据根>/app/logs/desktop.log`；独立 CLI Agent 的日志仍在 `<数据根>/agent/logs/agent.log`（开启文件日志时）；Windows 更新恢复日志在 `<数据根>/app/logs/update-recovery.log`。

Desktop 的 `app/app.db`、`app/desktop.lock`、GUI 单实例范围、聊天临时工作区、配对和设备身份也遵循同一数据根。默认路径和存储格式不变。旧版本在使用覆盖目录时，可能仍把 Desktop 数据放在默认目录，而 Agent 数据位于覆盖目录；这些旧文件原样保留，本次不复制、合并或搬迁。选择默认数据根可访问其中的 Desktop 数据；覆盖目录使用自己的隔离状态。

| 现象 | 处理 |
| --- | --- |
| 外部服务版本不兼容 | 核对报错中的版本/协议，正常退出或升级外部服务，再重开 Desktop |
| 实例锁占用、服务无响应 | 确认是否还有 GUI、主机模式或独立 Agent 使用同一数据根；正常退出它，必要时重启系统；不删除锁 |
| 显式端点不可达 | 检查地址、对应服务和用户环境；不需要远端时取消显式覆盖，再重开 |
| 缺少 CLI，但 Agent 正常 | 放回匹配 `future` 或加入绝对 PATH；这影响技能和维护，不代表内置服务需要另一个 Agent 进程 |
| 清理失败，更新未安装 | 保存报错和日志，正常退出相关客户端后重试；持续失败时重启系统并运行完整安装器 |
| 宿主把进程杀掉（没有任何报错输出） | 主机的 OOM killer 或按用户 CPU/内存配额会直接发 SIGKILL，进程内无法报告。日志会保留被杀前记录的每个启动阶段；再查主机侧记录（`dmesg -T`、`journalctl -k`，或节点自己的配额/作业日志） |
| 安装失败且没有自动重开 | 查看恢复日志与安装诊断，完整修复安装；不强行启动混合或不完整回滚的程序 |

更新设置页会显示实际选择的 CLI 路径和版本。Desktop 通过只读 `future version --json` 核验连接契约及工具能力；开发提交后缀不同不必然不兼容。CLI 缺失、不兼容或缺少技能初始化能力时，修正该路径或放回匹配版本，不通过启动另一份 Agent 解决。

每次更新的阶段和结果保存在 `<数据根>/app/updates/<操作 ID>/result.json`，`latest.json` 指向最近操作。Windows 观察进程 ready 只表示接管就绪；最终结果以持久记录为准。停止页面也可查看更新结果，并在已安装或原程序完整恢复且门禁允许时重启。结果未知或回滚不完整时，不自动重试安装或重启；先检查记录和恢复日志，使用可信完整安装器修复。完成手工修复后可在更新设置页明确确认；这保留原失败记录，不代表自动验证成功，活跃观察进程仍会阻止确认。重试会重新下载、验签和清理，不直接执行遗留暂存包。

反馈时提供版本、平台、服务模式、错误和相关日志片段，去除 API key、配对链接等凭据。`future doctor` 可辅助检查环境；它不授权绕过实例锁。

## 开发启动入口

macOS/Linux 使用 `scripts/dev/start-desktop-macos.sh` 或 `scripts/dev/start-desktop-linux.sh`；Windows 使用 `scripts/dev/start-desktop-windows.bat`（委托 PowerShell）。它们构建/暂存 CLI，再启动 Tauri，服务选择由 Desktop 完成。移动端的 iOS/Android 脚本只管理移动开发会话，不启动 Desktop Agent。

`DRY_RUN=1` 只打印配置；`BUILD_CLI=0` 跳过 CLI 构建；`RUN_CHECKS=1` 运行静态检查，不跑单元测试；`DESKTOP_DEV_PORT` 指定 Vite 端口。端口占用直接失败，不自动换端口或结束占用者。相对 `CARGO_TARGET_DIR` 从仓库根解析并转换为绝对路径。

三个桌面端启动入口都会在构建前恢复 Cargo 编译器信息中残留的 sccache 失败记录。Cargo 可能把失败的 `sccache rustc -vV` 写入 `<target>/.rustc_info.json`，之后即使 sccache 已恢复，也会直接重放旧错误。CLI 与 Desktop 默认使用不同的 target，因此可能出现 CLI 持续失败、Desktop 正常构建的现象。

脚本检查两个默认 target，或显式设置的 `CARGO_TARGET_DIR`；只有发现失败探测中包含明确的 `sccache: error:` 诊断，才把这一个元数据文件改名为同目录的 `.sccache-failure-<id>.bak`，保存原始错误，让 Cargo 重新生成元数据。恢复路径和诊断记录在 `.logs/rust-cache-preflight.log`。

该处理不会关闭 sccache、清空编译缓存、停止共享服务或修改全局配置；正常元数据、无关编译错误和自定义 wrapper 保持原样。如果当前仍有权限或服务故障，需要修复实际运行环境，脚本不会通过无缓存编译掩盖问题。从 agent 的受限沙箱调用 Cargo 时，应为构建提供访问所配置缓存目录及本地缓存服务所需的权限。

应用内退出用于协调清理。开发脚本的 Ctrl+C 中断开发工具链；Unix 清理仅作用于本次启动的进程组，超时可能强杀。它不保证等同应用内正常退出，不扫描、终止外部 Agent，也不改写数据库或锁。真实主机程序直接处理 Ctrl+C，参见[主机模式指南](desktop-host.zh-CN.md)。

## 验收范围

Desktop 默认在自身进程内托管完整 Agent；外部连接、独立 CLI/TUI 使用、工具能力与存储格式都仍然可用，退出内置宿主会中断该宿主的其他客户端。

三平台原生生命周期 CI、Windows 离线更新 fixture、macOS ad-hoc 包和 Linux/Windows daily 未签名包已有通过记录。正式签名/公证、真实安装升级/回滚、完整 GUI 工具交互、原生 Linux Bubblewrap 及性能对比仍需验收；代码收尾不等于发布批准。证据与剩余清单见[开发计划](../architecture/embedded-agent-development.zh-CN.md)。
