# 会话归档：运行日志清理与自动归档设计

> 状态：运行日志清理方案基本定稿；自动归档为待评审的设计建议。尚未开始实现。
> 日期：2026-11-13。
> 范围：桌面端（`desktop/`）、共享宿主（`host/`）与 Agent 历史存储（`agent/`）；远程会话沿用宿主侧规则。

## 1. 术语与现状

### 1.1 两种“归档”必须分开

1. **运行记录归档**：截图中的“归档已结束的程序”，当前仅设置 `runs.archived_at`，把终态 Run 从运行面板隐藏。它不删除历史，也没有“取消归档运行”的入口。本方案不改变其语义。
2. **会话归档**：归档一棵会话 fork 树，归档态只读，取消归档后可继续对话。运行日志清理和闲置自动归档都发生在这一层。

工作区归档仍是容器级隐藏。本方案不修改现有 fork 血缘、工作区唤醒、审批可见性和只读恢复规则。

### 1.2 当前数据位置

| 位置 | 内容 | 本方案是否改变 |
|---|---|---|
| `~/.future/app/app.db` 的 `runs` | Run 身份、会话关联、状态、起止时间、错误和 `archived_at` 等元数据 | 保留，并增加清理完成状态 |
| `~/.future/agent/agent.db` 的会话正文 | 用户消息、助手正文、`tool_call`、工具结果及关联内容体 | 保留正文和命令；清理指定输出 |
| 同一数据库的流式回放数据 | `stream_*`，旧格式另有 `run_events`、`run_snapshots` 等 | 清理受影响 Run 的回放数据 |
| 工作区文件、Artifacts、Review | 代码文件和其他独立成果 | 完全不动 |
| `~/.future/agent/logs/agent.log` 等诊断日志 | Agent 运行诊断，不是右侧运行详情的数据源 | 不属于本期范围 |

这里的“运行日志”是产品术语，指**点击聊天中的命令后，在右侧看到的原始输出、错误详情和运行回放**。它不是命令标题，也不是助手回答正文，更不专指 `agent.log`。

## 2. 目标与非目标

### 2.1 目标

- 会话归档后自动减少无用运行详情的长期留存。
- 归档前后，聊天中的提问、助手回答、命令标题、命令顺序和完成状态保持一致。
- 已归档会话中点击命令，右侧明确提示“运行日志已清理”，而不是空白、报错或假装命令从未运行。
- 取消归档后，历史正文仍可读，能正常发送新消息并调用新工具。
- 提供默认开启的“归档时自动清理运行日志”设置，首次实际清理前友好告知，并可跳转设置。
- 提供独立、默认关闭的闲置自动归档设置，按有效对话活动时间而不是创建时间判断。

### 2.2 非目标

- 不恢复已经清理的旧 Run 输出，也不承诺旧失败任务能依据原始 stderr 无损续跑。
- 不改变“归档已结束的程序”的现有行为。
- 不删除代码文件、撤销命令副作用或清理 Git 工作区。
- 首版不做工作区容器的自动归档，只自动归档其中的会话树。
- 首版不承诺安全擦除或隐私意义上的全副本清除；压缩摘要、旧版迁移来源、独立备份和已经导出的文件不属于同一删除契约。
- 首版只把 Shell 命令输出纳入正文清理，不顺带删除 Fusion 报告、Artifacts 等结果型内容。

## 3. 归档时清理运行日志

### 3.1 保留与清理边界

| 数据 | 归档清理后的状态 |
|---|---|
| 用户提问、助手文字回答、附件 | 原样保留 |
| 会话 ID、工作目录、模型、权限等会话记录 | 原样保留 |
| “已运行”、命令文本、工具类型、执行顺序 | 原样保留 |
| Shell `tool_call` 及其 `command` 等参数 | 保留 |
| `runId`、`toolCallId`、原成功/失败状态和时间戳 | 保留 |
| Shell 的 stdout、stderr、原始输出和详细 `shell_result` | 删除 |
| 受影响 Run 的流式事件和回放快照 | 删除 |
| 其他会话正文、代码文件、Artifacts、Review | 保留 |
| 清理完成标记，例如 `logs_purged_at` | 新增并持久化 |

命令和完整调用参数仍然保留，因此该功能定位为**删除执行输出与回放详情**，不是清除全部工具历史，也不是敏感信息擦除。Write/Edit 参数中的代码内容不因本功能删除；磁盘上的代码文件更不受影响。

### 3.2 模型历史：保留调用，结果去内容化

不能只删除 Shell 的 `tool_result` 并留下孤立的 `tool_call`。模型供应商要求工具调用与结果正确配对，现有“工具执行丢失”修复占位还可能把已完成命令误显示为中断。

推荐的历史重写单位是：

1. 保留原 `tool_call`、参数和身份；
2. 保留对应 `tool_result` 的记录骨架，将原始输出替换为固定的“归档时已清理”占位内容；
3. 保留该结果的 `tool_call_id`、`is_error`、时间戳和 Run 关联，使命名、数量和完成状态不发生变化；
4. 删除原始输出对应的大字段、详细 Shell 事实和内容引用；
5. 退役受影响 Run 的回放流，防止已删除输出经 replay 重新出现；
6. 重写后重新加载 Agent 内存历史，确保下一轮请求使用重写后的版本。

占位结果只用于维持协议与状态，右侧 UI 不把它当作真实输出展示。

Agent 仍是唯一的历史写入方。可复用现有 session reset 的历史规划、原子重写和内容回收思路，但不能直接照搬其长期保留全量 `session-backups` 的策略，否则清理后的输出仍完整留在备份中，违背减负目标。

### 3.3 设置与默认值

| 设置 | 默认值 | 说明 |
|---|---|---|
| 归档时自动清理运行日志 | **开启** | 手动或自动归档会话时，按 3.1 的边界清理 |
| 运行日志清理首次提示已读 | 未读 | 每个安装实例记录一次，不按每个会话重复提示 |

设置说明建议：

> 保留聊天正文、命令标题和生成的文件，清理命令输出和运行回放。取消归档后仍可继续对话，已清理的运行日志无法恢复。

### 3.4 首次告知与归档设置入口

默认开启意味着功能上线后的首次实际清理必须明确告知。提示只出现在**首次真正会清理日志的归档**；没有可清理内容的会话不弹无关提示，也不消耗这次引导。

建议文案：

> **归档会话？**
>
> 提问、助手回答、命令标题和生成的文件都会保留，取消归档后可以继续对话。
>
> 本次将清理点击命令后看到的输出和运行回放，清理后无法恢复。此功能默认开启，可以在归档设置中更改。

按钮：

- **查看归档设置**：只跳转到对应设置项，不执行归档；
- **取消**：留在当前会话；
- **归档并清理运行日志**：按当前设置执行。

从设置返回后，按钮和提示遵循最新设置：若用户已关闭清理，后续就是普通“归档”。首次提示是全局一次，不是每棵会话树一次；功能上线前已经归档的会话不做追溯清理。

### 3.5 归档后的展示

- 聊天中的“已运行”和下面的命令文本保持原位置，可增加低强调的“日志已清理”状态，但不显示原始输出。
- 点击命令后，右侧显示：

  > **运行日志已清理**
  >
  > 该会话归档时已删除此命令的输出和运行回放。命令记录、聊天正文和生成的文件仍保留，已删除的日志无法恢复。

- 不用 `tools.length === 0` 推断已清理：有些 Run 本来就没有工具调用，清理失败也可能造成不完整状态。
- 只有实际清理成功的 Run 才写入 `logs_purged_at` 并显示该提示。旧归档、清理中、清理失败和恢复后产生的新 Run 必须分别按真实状态展示。

### 3.6 清理执行与恢复

- 会话归档与 Agent 历史重写是两个存储边界，不能假设它们共享一个数据库事务。
- 清理可以作为可重试的后台任务执行；清理失败不应把会话锁死在归档态，也不应阻止取消归档和继续对话。
- 清理中不能提前显示“已清理”；部分成功必须按 Run 记录，不能把整棵会话树一刀切标记完成。
- 取消归档只恢复会话可见性和输入能力，不恢复旧日志。之后的新消息、新工具调用及其详情正常保存，下一次归档时再次按设置处理。
- 若用户恢复后立即继续对话，历史中的工具配对必须仍然有效，不能依赖前端跳过错误。

## 4. 闲置会话自动归档

### 4.1 设置项与默认策略

| 设置 | 建议默认值 | 说明 |
|---|---|---|
| 自动归档闲置会话 | **关闭** | 只有用户主动开启后才后台归档 |
| 闲置天数 | **30 天** | 可提供 7 / 30 / 90 天及自定义整数，建议允许 1–365 天 |
| 扫描频率 | **每天一次** | 首版不开放更高频率或 cron 配置 |

自动归档和日志清理是两个独立开关：自动归档控制“何时收起”，日志清理控制“收起时删除什么”。

### 4.2 归档单位与范围

- 归档单位与手动操作一致，是**完整的会话 fork 树**，不是单个后代节点。
- 同时覆盖临时聊天和工作区内的会话。
- **首版不自动归档工作区容器**。一个工作区可以包含新旧不同的多棵会话树，且目录可能仍在 FutureOS 之外被频繁使用；整个容器隐藏应继续由用户主动决定。
- 已归档、已删除对象不重复处理；运行记录归档不参与候选。

### 4.3 时间基准：最后一次有效对话活动

不使用会话创建时间作为主要判断。一个创建多年但昨天仍有对话的会话显然是活跃的。

单个成员的基准为：

```text
member_activity = max(
  last_message_at（没有消息时使用 created_at）,
  restored_at（如果发生过恢复）
)
```

整棵树的基准为：

```text
tree_activity = max(树内全部成员的 member_activity)
```

当 `now - tree_activity >= N × 24 小时` 时，该树才进入候选。

具体规则：

1. **有效活动**包括新提问、助手回复、新 Run 以及其他端产生的真实消息活动；`last_message_at` 已覆盖的主要就是这些事件。
2. **恢复视为一次活动**，从恢复时刻重新计算同一个 N 天，避免刚恢复的旧会话在下一次扫描立即再次被归档。现有模型可增加 `restored_at`，不必复用含义宽泛的 `updated_at`。
3. **从未产生消息的空会话**使用 `created_at`，因此长期未使用的空会话也能被整理。
4. **打开、重命名、改模型或普通元数据修改不算对话活动**。`updated_at` 太宽泛，不能作为自动归档基准。
5. **当前正在前台查看的会话当轮跳过**，避免在用户阅读时突然变成只读；但打开行为本身不刷新长期活动时间，关闭后仍可能在下一轮被归档。
6. **任一后代最近有活动，整棵树都不归档**，防止父会话看似闲置但派生工作仍在继续。

### 4.4 永远跳过或当轮跳过的情况

- 树内任一成员置顶；置顶是用户显式保留的快捷入口，首版不提供“连置顶也自动归档”的额外选项。
- 树内存在 `running`、`queued`、`waiting_approval` 的 Run，或 Agent 快照仍显示 streaming。
- 当前前台正在查看的会话树。
- 宿主尚未完成启动恢复、运行状态尚未收敛时。
- 候选生成后、真正归档前又出现了新消息或新 Run 的会话树。

自动归档必须复用手动归档的活跃性检查，并在提交前重新核验活动时间与状态，而不是只依赖每天扫描开始时的旧快照。

### 4.5 扫描频率与时间语义

建议调度：

1. 应用启动、Store 与 Agent 状态收敛后做一次扫描；
2. 应用持续运行期间每 24 小时再扫描一次；
3. 应用退出时不执行任务，下次启动按当前时间补算；
4. 候选分批处理，每批重新核验并允许其他会话操作穿插执行。

“30 天”表示**至少闲置 30 个 24 小时周期**，不是本地时间的准点日历提醒。每日扫描意味着实际归档可能发生在 30–31 天之间，应用长期未打开则更晚。首版不提供按小时扫描，因为天级整理没有必要增加频繁后台工作和通知干扰。

### 4.6 与运行日志清理的联动

自动归档遵循执行当时的“归档时自动清理运行日志”设置：

- 清理开启：后台归档后按同一规则清理运行日志；
- 清理关闭：只归档，不删除日志。

开启自动归档的页面必须直接展示该联动，例如：

> 自动归档将遵循当前的运行日志清理设置。当前：**归档时清理运行日志（已开启）**。[查看归档设置]

开启自动归档即授权后续后台按该策略执行，不再为每棵会话树弹确认框。若用户不希望后台删除任何内容，应先关闭日志清理，或不要开启自动归档。

首次自动归档完成后给一次汇总通知，不逐条弹窗：

> 已自动归档 3 个超过 30 天未活跃的会话，并按设置清理运行日志。[查看已归档]

没有新归档时不通知。清理失败不改变归档结果，在详情中呈现真实状态并允许后续重试。

### 4.7 恢复、远程与重复执行

- 用户取消归档后，以 `restored_at` 重新获得完整的 N 天闲置周期；旧日志不会因恢复而回来。
- 恢复后的新消息和新 Run 正常更新 `last_message_at`，下一轮按最新时间计算。
- 远程会话只能由拥有该会话 Store 与 Agent 的宿主执行自动归档，远程控制端不各自跑一套规则，避免多设备竞争。
- 其他端在归档后继续产生消息时，沿用现有“不自动复活已归档会话”的规则；这些新时间会用于之后的判断。
- 已归档树再次扫描应保持无操作、无通知、无重复清理占位，保证幂等。

## 5. 建议的设置信息架构

设置中的“会话与归档”区域可以按以下顺序呈现：

1. **归档时自动清理运行日志**：默认开启；
2. **自动归档闲置会话**：默认关闭；
3. **闲置天数**：仅自动归档开启时可编辑，默认 30 天；
4. 联动说明与“查看归档设置”入口；
5. 当前自动策略摘要，例如“超过 30 天未活跃的未置顶会话将每天检查一次”。

自动归档天数变更只影响之后的候选计算，不要求立即执行一次扫描，也不把已经归档的会话恢复。

## 6. 边界情况汇总

| 情况 | 处理 |
|---|---|
| 老会话早已归档，但日志未清理 | 不显示“已清理”；不追溯删除 |
| 清理失败或只完成一部分 | 会话仍可恢复；按 Run 记录真实状态并允许重试 |
| 命令原本就没有输出 | 可标记清理完成，但不虚构输出曾经存在 |
| 运行本来没有工具调用 | 不生成“已运行”占位，不把空工具列表等同于已清理 |
| 会话创建很旧，但最近有回复 | 不归档，使用最后有效活动时间 |
| 空会话从未提问 | 使用创建时间，满 N 天后可归档 |
| 只打开或重命名旧会话 | 不刷新长期活动；当前查看时当轮跳过 |
| fork 父旧、子新 | 整棵树不归档 |
| 恢复一个很久以前归档的会话 | 从恢复时刻重新计算 N 天 |
| 应用关闭 60 天后重新打开 | 启动状态收敛后补扫描，满足条件的才归档 |
| 自动归档开启、日志清理关闭 | 只隐藏会话，不删除日志 |
| 自动归档和手动归档同时瞄准同一棵树 | 提交前重新检查状态；已是 archived 的操作幂等返回 |
| 工作区仍包含一棵活跃会话树 | 其他符合条件的树可独立归档，工作区容器不自动归档 |

## 7. 验收标准

### 7.1 运行日志清理

1. 默认设置在首次实际清理前弹出说明，三个按钮的行为与文案一致，设置跳转准确。
2. 归档前后用户消息、助手正文、命令文本、命令数量和原完成状态一致。
3. 点击已清理命令只显示清理说明，不再返回原始 stdout、stderr 或 replay。
4. 原始输出不能通过会话重载、运行详情或旧事件游标重新出现。
5. 代码文件与独立 Artifacts 内容不变。
6. 取消归档并重启应用后仍能发送新消息，模型供应商不因工具配对拒绝请求，新工具可以正常运行。
7. 老归档、清理中、清理失败、清理成功和新 Run 的 UI 状态不混淆。
8. 重复归档与重复清理不会生成重复占位或误删新正文。

### 7.2 自动归档

1. 默认关闭；开启后才产生后台归档，默认阈值为 30 天。
2. 29 天候选不归档，达到 30 天的候选在下一次每日扫描归档，时间不承诺准点。
3. 创建很旧但最近有消息、Run 或恢复的会话不归档。
4. 重命名不续命；当前打开的会话当轮跳过；空会话使用创建时间。
5. fork 树内最新活动保护整棵树，置顶、活跃、等待审批和当前查看的树被跳过。
6. 应用离线时不执行任务，重启后按规则补扫描，重复扫描不重复通知。
7. 自动归档严格遵循当时的日志清理设置，开启页面能看到联动状态。
8. 恢复后重新获得完整闲置周期，正文可继续对话，已清理日志不恢复。
9. 工作区容器不被自动归档，远程控制端不重复执行宿主任务。

## 8. 后续可选项

- 单独增加“自动归档闲置工作区”设置：只有其中全部会话树都满足同一闲置规则、无置顶、无活跃且工作区近期未打开时才允许，不能与首版的会话规则共用一个开关。
- 提供“仅归档建议”模式：把候选列表交给用户批量确认，而不是真正后台归档。
- 提供排除特定工作区或会话的持久例外，而不是要求用户通过置顶表达全部排除意图。
- 若未来目标从减负升级为隐私清除，需要另行定义命令参数、压缩摘要、备份、旧格式来源和导出文件的完整保留策略。
