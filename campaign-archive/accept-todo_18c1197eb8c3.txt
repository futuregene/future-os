  never fixed by weakening an assertion):

    bounded loop (0..64 of advance + yields + 1 ms real sleep). The diff touches ONLY the drive loop, and

    vanished client is an ordinary end of stream, not an error"). The comment documents why one advance is
    insufficient (a post-close write is not refused synchronously; the reset is a kernel event, not a
    virtual-time one) and states the measured rate (3 of 4 instrumented whole-suite runs red at load 16-55,
    passing standalone). Legitimate.
  * `run_server_serves_and_broadcaster_ticks`: the connect-poll loop changed from `for _ in 0..500 { if let
    Ok(c) = connect() { client = Some(c); break; } yield_now().await; }` to a `while client.is_none() &&
    attempt < 500 { attempt += 1; client = connect().await.ok(); yield_now().await; }`. Still bounded at 500,
    the `client.expect("server binds and accepts")` and every assertion after it are unchanged (the diff
    has no other lines).
  **BUT I AM NOT ACCEPTING ITS STATED MECHANISM FOR THE SECOND ONE, and this is the one item carried
  forward**: it says "the loop no longer `break`s early, so the retry path runs every time". Removing the
  early `break` does NOT make the retry run more often - both shapes retry exactly when a connect FAILS, and
  whether the first connect fails still depends on whether the server task has bound yet (the very race it
  describes). The likely real change is an ATTRIBUTION flip: an explicit `attempt += 1` line now carries the
  loop bookkeeping that the `for` iterator's increment used to hold, and llvm attributes it to a different
  line/region. If that is what happened, the row belongs in `attribution-artifact` (as `shutdown.rs` 273/303
  and `journal.rs` 202/203 do), not "now covered by my fix". I am NOT calling it a fall: no assertion was
  weakened and the loop is still bounded. REV-GOAL-2 must rule on which of the two it is, with evidence.
