## The `ws://` fact, which is the reason this worked at all

It did not use a plaintext `nats://` listener for the broker's refusal, and explained why: in the
**non-test** build `async-nats` skips the mandatory TLS upgrade **for WebSocket addresses only**, so a
plaintext `nats://` listener can never deliver a broker-level refusal — only an IO/TLS error, which is
retryable. A `ws://` listener can speak the protocol and answer `-ERR 'Authorization Violation'`.

That is the kind of detail that makes a fixture possible instead of "impossible": the earlier
`unreachable-in-this-environment` verdict on those lines was not lazy, it was **correct for the address
scheme someone would naturally try**. My authorisation to build the fixture was necessary but not
sufficient — the unit still had to find the one address scheme whose semantics allow the refusal to be
observed.
